## 服务器结论

第一对 `screen-b-v1 / screen-c-v1` 两臂均正式1024/1024到达，但8格首Path P95 +13.6%、分配+2.2%，28格首Path P95 -9.4%、分配-1.4%。自然全进程CPU下降不能解释成worker改善，固定窗和非主线程CPU未同步下降。

随后仅为补worker归因缺口追加一对 `worker-screen-b-v1 / worker-screen-c-v1`。复用相同生产/probe Jar，仅共用新增场景边界计数的Trace helper。精确筛选计算worker-1/-2，IO另列；不启用热点或每任务记录。

该对正式8/28格worker CPU观察到 -23.1%/-30.8%，分配 -11.5%/-5.0%，两臂仍各1024/1024到达；64实体预热CPU反而+50%/+66.7%。任务数发生变化，CPU有15.625ms粒度，不能视为逐算法因果或稳定性能结论。线程账本用 `worker-resources-v2.json`，全进程账本用 `worker-screen-resources-v1.json`；前一对保持独立。
