# 节点切换计时修正的隔离候选方案

日期：2026-10-23。状态：方法收敛，尚未实现或验证修复。
依据：[研究及停止原因定位](../reports/2026-10-23-detail-next-cost-stuck-research-zh.md)。

## 1. 问题与目标

在真实执行路径索引推进后，原生只更新下一节点的超时阈值，
未清此前累计timer。本场4次超时的新节点等待均为0tick，
却用旧89/92tick与新约63.36tick阈值比较而停止。

目标是让节点等待按当前节点计时，减少无依据的停止及后续恢复。
不改变目标点、A*邻接、启发式、搜索限额或物理到点标准。
不将方法上的确定性等同于修复后的物理完成或性能收益已验证。

## 2. 单变量承载与实现

从冻结NS复制隔离候选；保持原2/1连接，不直接从L扩长版叠修复。
NS有有效历史及搜索降本证据；L同时涉及跨度和未定位分配异常，
不适合用来判断这次计时修正自身的净结果。

优先在原`doStuckDetection`本就存在的“下一节点坐标变化”分支注入，
对执行中的`NavigationRequestPath`，在后续超时比较之前仅执行：

```java
timeoutTimer = 0L;
```

利用原分支判断，不复制整方法、不新建节点Map或每tick身份/代次检查链。
只在原节点变化分支增加路径类型判断和赋值，为每次节点转换O(1)额外工作，
不增加对象分配、worker往返或排队。
实现时核对字节码注入位置，保证先清timer、再运行原阈值判断。

项目真实路径索引由原advance推进；publish/clear才重置索引，
其中publish已有完整reset。临时同步搜索不执行此跟随检查。
不为并未出现的新问题扩写搜索期保存/还原字段。

同节点累计、原limit公式、3倍阈值、100tick总体进展、
LANDING_TTL、publish/clear reset、取消/替换、partial处理及恢复限额保持原语义。
非项目执行路径不应用该修正。

## 3. 必要正确性核验

新增检查仅针对本次改变的计时分支；旧性能测试项不扩矩阵：

1. 节点确实前进且坐标变化时清timer，保留原limit/cached更新与后续lastTimeoutCheck。
2. 同一节点等待仍按原gameTime差累计；速度正且阈值有效时，
   真实阻挡仍通过原节点超时停止。
3. 在不断小幅移动/推进节点却总体进展不足的情形，
   原100tick总体进展停止仍生效，不被清timer绕过。
4. 原publish、取消、替换、路径完成及partial控制保持；
   不把恢复当作物理到达。

复用仍适用的旧控制，缺失分支才补针对性控制并说明理由。
任一关键控制失败即停止，不以加阈值、减速度或删除检查继续验证。

## 4. 性能验证与扩长边界

修正控制通过后才使用原性能接口、原负载和计量，
先核对并复用NS/U/P/N有效历史，不为配对重跑基线。
LD是观察型诊断，不充当修复的性能基线。
首Path、完成和到达、恢复数、搜索/完整查询成本及tick尖峰一并保留正负结果；
不只看某个搜索窗口或删除不利样本。

验证修正后实际物理完成与成本，再决定独立扩长候选。
若随后从修正母版验证4连接，必须明示母版变化；
复用旧L只能作有效历史背景，不能称两者仅跨度不同。
不将旧14次长段恢复全数预判同因，也不因本次修正便普遍启用L。

L分配增量约88.20%来自未扩长请求的旧事实仍保留，
不能用计时机制解释全部分配/JIT/外层CPU。
200ms是项目整体目标，不为本分支制造独立收益比例或时延门槛。
