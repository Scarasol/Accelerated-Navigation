# GPU 导航加速可行性研究

日期：2026-10-26。按用户“评估项目是否适合GPU加速，并确定适用部分”研究。
本轮只复核源码、有效历史和一手资料，没有实现GPU后端或新增性能测试。

后续状态：同日已按用户授权完成[独立GPU构图原型研究](../reports/2026-10-26-gpu-topology-isolated-feasibility-zh.md)。
用户指定后续以RTX5060为目标，核显不继续探索；GPU接入可配置，保留CPU路径。
后文“未实测”等描述为本份初始研究的时间边界，实际原型结果以新报告为准。

## 1. 判断

项目中部分批量、纯数据阶段具有GPU并行化条件；目前不建议把详细寻路整体迁到GPU。
最适合先考察的是大量section的冷构图/预热，随后才是大量跳跃候选的批量几何计算。
这是按计算形状和工程边界给出的探索优先级，不是已经证明存在端到端收益。

GPU适合提高大批工作吞吐，但不自动降低单个请求的首Path延迟。
等待凑批、上传、设备队列、回读和主线程发布均可能抵消计算收益。
不能为了利用GPU，给正常前台请求增加整tick等待或额外选点队列。
GPU也不能缩短实际行走距离、修正选路质量，或直接消除测试注入的35ms主线程硬占用。

## 2. 当前量级及证据边界

复用[最后目标合并修复验证](../reports/2026-10-26-final-target-merge-isolated-validation-zh.md)
及[生产接入身份核对](../reports/2026-10-26-validated-navigation-production-integration-zh.md)。
接入后的73份源码/资源与已验证候选相同，279个非manifest包条目相同，
本次研究不重新启动候选或基线JVM。

原35ms/sigma5/seed20261021、64/128/256并发各8/28格六场：

- 896次详细搜索累计wall为123.1280ms，算术平均约0.137ms/次。
- 该平均不是单次P95或最大值，也不代表超长路线和大批冷构图的成本。
- 896/896到达；原生为802/896。共同到达请求相对原生延后中位60.5981ms、
  P95为138.5555ms，最大217.3150ms。
- 自然完成窗CPU为31109.375ms，但含注入硬占用、其它服务及行走，
  不能当作可卸载到GPU的导航计算量。
- CPU探针有15.625ms量化限制，本研究不用它精确划分GPU可节省的CPU。

这些数据不支持“搬走详细搜索就能普遍消除百毫秒响应差”的判断。
即使设备内核很快，当前实测搜索自身可节省的计算量也很小。
反过来，不能据此否定尚未计量的大规模冷图或超长搜索的潜在价值。

## 3. 模块适配性

| 部分 | 判断 | 原因及边界 |
| --- | --- | --- |
| 大批section冷构图、预热 | 最值得先考察 | 不可变快照可转为连续数组，能跨section/体型层批量计算净空、合法位图、连接和组件；需先确认该纯计算阶段确为热点 |
| 大批跳跃轨迹及静态几何筛选 | 条件适合 | 不同起落点/运动原语可独立推演；当前按需候选少，不能为了凑批改成全量弹道预计算 |
| 大量同目标查询的距离场 | 特定工作负载适合 | 在目标、体型、能力、代价和快照一致时可复用一次反向搜索；CPU也能获得复用收益，不能全部计为GPU收益 |
| 当前详细A* | 当前不优先 | 已测查询计算量很小；邻点语义依赖Java实体、世界及Forge钩子，需重建数据后端而非简单换线程 |
| 小规模宏观图及少量交接点选择 | 当前不优先 | 现有压缩图/位图已减少工作量；少量位运算不值得逐次经过设备提交与回读 |
| 实时世界采样、动态模组钩子、路径执行 | 保持CPU职责 | GPU内核不能直接调用当前Java/Forge方法或操作实体；实际世界语义仍需正确交付和执行 |

### 3.1 大批冷构图/预热

源码入口：

- `TopologyService`：真实方块、流体、碰撞信息采集及事实快照发布。
- `BaseClusterTopology.build`：`deriveLegalAnchors`、`labelComponents`、
  `buildGroundEdges`及边界快照。
- `TopologyTaskExecutor`：当前为两个CPU worker，构图有串行许可。

候选边界为：CPU继续采集世界语义，GPU仅处理已经冻结、可序列化的事实与几何。
先评估合法位置/净空位图和规则连接等规则计算，再决定是否迁组件标记。
不能仅凭粗四位事实重建所有精确几何；`EXACT_REQUIRED`及碰撞形状需要保留原语义。

单section为16x16x16单元，一个4096位成员位图仅64个long/512字节；
这是单个位图，不是整个section快照大小。逐section提交很可能不足以覆盖设备成本。
应跨已有待办section批处理，上传一次后尽量完成连续阶段，再回读真正需要的结果。
低负载和零散更新仍由CPU处理，不人为延迟前台来积攒批量。

若替换组件标记，必须保持原邻接、能力及方向语义，
并规范化组件编号、锚点和边顺序，避免GPU并行完成顺序改变宏观输入及路线。
cuGraph的弱连通例程只说明GPU图处理可行，不能直接替代有向跳落的可达性判断。

### 3.2 与跳跃方案的衔接

沿用[跨隙跳跃研究](2026-10-26-gap-jump-navigation-implementation-plan-zh.md)：
稀疏有向动作边、位图恢复成对起落候选、当前搜索内按需验证，不每跳一次重新入队寻路。

未来若真实热点变成大批动作候选，可将其表达成
`候选动作 x 物理步 x 几何测试`的独立计算，用GPU推演和筛选。
需上传足够精确的碰撞形状及物理参数；仅粗占用或近似距离场不能直接证明真实动作可执行。
模组动态钩子和起跳前局部世界复核仍保持现有CPU语义。

GPU先筛一遍、CPU再完整计算一遍可能只是增加成本；
是否采用粗筛，取决于它实际排除的工作量和传输费用。
当前尚未实现跳跃候选，更没有该阶段已成热点的数据，不因此改写为全量预计算。

### 3.3 同目标距离场

在反向有向图上由目标执行一次最短路，可供多个起点读取距离/后继。
有权边使用适当的非负权最短路算法；只有等权场景才直接用BFS。
跳跃方向、实体代价、体型和快照身份不同不能共享同一场。

这首先是算法复用，CPU同样可以做；GPU是否值得取决于图规模、更新率和复用量。
现有组件宏观图不等于完整合法详细动作图，不能只凭宏观连通直接输出逐格最优路径。
本研究没有假设当前64/128/256并发请求全部拥有同一个目标。

## 4. 工程约束与投入门槛

当前详细入口`NativeNavigationSearch`使用实际Mob、ServerLevel及原生evaluator；
`NeighborSafety.bind`的优化入口要求服务器主线程，并有BlockState、FluidState、
Forge路径类型钩子和实体上下文。迁GPU需要把对应语义转换为纯数据算法，
不是将现有Java代码交给另一种worker。

若后续推进，采用可选GPU后端，CPU能力继续完整可用。
部署前确认计算发生的服务器是否有受支持设备、驱动和计算API；
无界面不等于不能计算，有客户端渲染显卡也不等于远端服务器可直接利用它。
单机还需计入渲染争用，核显共享内存也不会自动消除派发、同步和一致性成本。
本轮没有调查目标部署机器硬件，也没有选择CUDA/OpenCL/Vulkan实现栈。

保留现有CPU worker与完成发布机制，纯数据批次携带原快照身份。
世界修改只增量更新相关数据，发布时按批次核验身份，不增加每节点重复整链检查。
CPU和GPU可以使用不同内部编号，但交付给宏观/导航的可见结果必须符合原契约。

实际盈亏按同一工作量端到端核对：

`打包 + 上传 + 排队/凑批 + GPU计算 + 回读 + 校验/发布 < 原CPU阶段`

集成显卡或常驻数据可减少部分复制，不取消其它项。
需要同时观察前台首Path尾部、主线程峰值、后台吞吐、内存和客户端帧时间；
不能只用内核时间作为准入依据，也不预设固定的“多少section必然划算”或加速倍数。
后续若进入验证，仍优先复用有效历史，原测试不改；仅补GPU后端必须新增的缺失证据。

下一步若用户决定探索GPU，应先用已有构图/预热分项证据确认热点和批量。
只有证据缺失才做对应阶段的最小计量，随后用冻结快照研究一个纯数据批处理内核。
目前没有足够证据建议将GPU开发设为详细寻路优化的主线。
