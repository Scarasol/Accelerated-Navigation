# GPU宏观寻路后端任务定义与CPU架构对齐方案

日期：2026-10-27。以用户本轮重新说明的任务为准：

> 让GPU承担起宏观搜索的任务，并且在CPU的基础上，根据GPU的特性（比如并发等）进行优化。

这是后续实现和验收的统一目标。已有冻结图原型及其数据保留，
不能用“已经在GPU上执行若干搜索内核”代替整个宏观后端完成迁移。
本轮完成任务边界及源码架构核对，尚未实现本方案，也没有新增性能结果。

## 1. 迁移对象和职责

2026-10-27用户补充：服务器可能没有独立GPU，CPU与GPU两种模式必须同时保留。
CPU继续提供完整、独立的宏观寻路后端，GPU是可选计算后端；
纯CPU模式不要求安装GPU运行时或成功初始化OpenCL。
两者沿用相同请求身份、依赖、结果语义和走廊交付接口，
不将后续GPU接线理解为删除CPU构图/搜索能力。
可通用的算法精简应另外评估CPU实现，不能用GPU实测代替CPU收益验证。

2026-10-27用户进一步明确CPU预热边界：
CPU后台预热只采用现有默认体型，不提前批量枚举混合体型。
实际寻路请求到来后，根据该对象的体型、移动能力及所需区域，
复用有效事实和派生资产，仅补齐当前请求缺少的数据；
不为一个对象把其他体型或无关地形一起构建。
当前源码`PREWARM_GEOMETRY`为地面1.0×2.0、可开门的默认几何，
`admitPrewarm`只请求该几何，实际依赖由`profile.geometry(channel)`按需请求。
移动能力沿用`MovementKey`筛选已有能力边，不表示每种能力都重建相同几何。
本次是明确既有行为和后续约束，不是修改生产预热实现。

隔离测试中的“混合体型”表示多种实际体型需求的总工作量，
不能解释为CPU生产预热策略；100轮等JVM预热轮数仅用于稳定测量，
也不是游戏后台预热了100轮或提前构建了100批体型。
GPU混合体型批量实验同样不能自动改变CPU这一边界。

迁移对象是现有宏观寻路计算链，包含按需基础图、共享邻接、边界连接、
父图构建、两路宏观搜索、缺图续行、分层具体连接及走廊恢复。
以生产请求与依赖流程为骨架，针对GPU调整计算任务的粒度、并发和存储。

CPU继续承担世界/Forge交互、事实采集和发布、请求接收、优先级、
缓存及版本生命周期、完成通知和最终接入。世界访问沿用现生产线程约束。
这些控制职责留在CPU，不表示把宏观搜索计算退回CPU。

GPU承担相应派生计算和搜索，搜索暂存保留在设备；
既有有效派生图和已完成走廊命中仍直接复用，不为了使用GPU重复计算。
设备保持所需图及事实常驻，回传现有生产接口要求的实际走廊、
成员/边界位图和身份资料。详细寻路A*及实体移动不是本次迁移对象。

## 2. CPU已有能力与GPU当前缺口

| 必须继承的能力 | CPU源码依据 | 当前GPU原型与修正要求 |
| --- | --- | --- |
| 图就绪即唤醒实际依赖者 | `TopologyWorkerRuntime.publish/completeDemand`、`MacroFlight.resume` | 目前完整流程为全批基础图、边界、父图再查询；改成实际依赖就绪推进 |
| 多个独立请求同时在途 | `macroFlights`、`TopologyTaskExecutor` | 逐请求历史测试只有一个在途；后端不能把等待某条返回作为接收下一条的条件 |
| 同请求合并和完成走廊复用 | `MacroQueryKey`、`MacroFlight`、`completedCorridors` | 不能仅运行物理查询数组而绕开生产缓存及合并模型 |
| 缺图时保留搜索状态，依赖补齐后续行 | `MacroQuery.requestDependency/completeDependencyRequest` | 冻结图原型没有真实缺图状态机；不能预先构建全部未来所需图才开始搜索 |
| 优先级、老化及预热隔离 | `TopologyTaskExecutor.bestForeground/effectiveRank/foregroundIdle` | GPU不能把所有任务无差别压入一个不可调整的大批次 |
| 快速搜索及长搜索续行 | `MacroFlight.runWorkerTask/requeueWorkerContinuation` | 设备保留frontier/open、距离和前驱，续行不重开搜索 |
| 同section共享查询及跨section分层查询 | `SharedRows`、`MacroQuery`及`TopologyGraph` | 两条路径及分层具体连接恢复都属于迁移范围，不能只覆盖组件点对点搜索 |
| 版本、halo、取消、持有和回收 | `publish`、`isCurrent`、各waiter及持有对象 | 现有隔离槽控制不等于实际世界接线；沿用生产身份，设备事件完成后才回收在途槽 |
| 生产结果资产完整 | `prepareWorkerResult`及走廊快照 | 不能只返回抽象节点编号，迫使CPU再构图或再搜索才能用于详细寻路 |

核对入口：

- `src/main/java/com/scarasol/acceleratednavigation/topology/TopologyTaskExecutor.java`
  第15、301、349、380、434、442行附近。
- `src/main/java/com/scarasol/acceleratednavigation/topology/TopologyWorkerRuntime.java`
  第138、3011、3076、3140、4305、4878、4975、4999、6451、6508行附近。
- `.tmp/gpu-macro-direct-query-isolated-20261026-v1/GpuFullFlowMeasure.java`
  的`gpuRound`，以及`GpuDerivedSession`、`GpuQueryBatch`。

CPU的BUILD/PREWARM串行许可保护共享BuildScratch；
不能把这项资源所有权约束误当成GPU也只能同时构一张图的算法要求。
同样，不把CPU两个worker的数量原样限制为GPU两个执行任务。

## 3. 统一的执行架构

沿用生产请求身份、任务种类、优先级、依赖去重及完成订阅。
GPU后端提供计算及设备资产句柄，不另起一套互不对应的导航请求语义。
调度和完成处理由有明确所有权的主机控制逻辑执行，不依靠多个Java线程
并发修改同一个kernel参数或主机暂存来制造“GPU并发”。

热图请求直接提交GPU搜索。冷图或缺图请求只补实际依赖：

1. 为缺失的事实版本、图、边界及父图建立去重任务与依赖。
2. 独立构图任务可同时在途；某个结果只解除它实际依赖者的等待。
3. 搜索具备推进条件就执行，不等其他实体或无关地形。
4. 搜索发现新的缺失依赖时保留设备状态并汇总必要依赖；
   通过现有控制流程补齐后继续同一个请求，不逐节点主机往返。
5. 完成的请求独立交付，其他构图/搜索继续进行，不用全局收尾屏障阻塞交付。

跨区域查询等待的是其实际图、连接及恢复资产，不是任意一张基础图完成即可搜索，
也不是必须等所有可能涉及的区域构完才允许开始。

CPU现有快速/后续搜索512/256展开量是worker搜索切片，不是主线程墙钟预算。
初始迁移保留可续行、取消和公平性语义；若调整GPU切片粒度，单独说明理由和实测，
不借迁移恢复已经取消的主线程时间预算。
本方案也不新增凑批窗口、下一tick等待或独立选点重排队阶段。

## 4. GPU适配方式与性能边界

优先采用主机侧乱序队列和显式事件依赖，表达就绪任务之间的必要顺序。
已封存的`.tmp/gpu-topology-isolated-20261026-v1/hardware.json`
记录RTX 5060 Laptop、驱动577.05、主机乱序队列支持为Yes；
设备侧队列数量为0，不把主机乱序能力误称设备端enqueue支持。
后端初始化仍读取当次能力；不更换驱动或假定任意设备相同。

当前GPU队列创建属性为2，只启用profiling；
改变队列属性本身不会自动消除全批完成边界。
OpenCL完成事件对应一条命令，不能直接表示该命令内某个工作组已经完成。
因此依赖完成粒度、任务组织和并发暂存必须一起调整：

- 将发布单位改为独立图/连接/父图或具有共同就绪边界的有限任务组，
  而不是整套语料的全阶段完成事件。
- 只合并当前已经就绪、可共享完成边界的工作，不额外等请求凑满。
  有独立交付需求的前台任务不能因无关后台任务被放入同一全局屏障。
- 任务之间通过事件等待必要生产者；主机提交线程不阻塞等待设备计算。
  完成回调仅通知原状态所有者，不在驱动回调里执行阻塞等待或重入修改导航状态。
- 为并发构图及搜索使用互不冲突的工作区、结果槽和主机上传暂存；
  共享只读事实及已发布图。提交用kernel/参数的修改也必须有清楚的所有权。
- 在途容量按设备资源和配置限制；超过容量的请求沿现优先级排队。
  不能把容量限制做成每条请求完成前不接收下一条。

队列事件的官方依据为Khronos `clEnqueueNDRangeKernel`的事件及wait list定义：
`https://registry.khronos.org/OpenCL/sdk/3.0/docs/man/html/clEnqueueNDRangeKernel.html`。
已保存统一规范原件位于
`.tmp/gpu-submission-research-20261026-v1/references/opencl-api.html`。

上述方案允许独立任务并发，但不保证每条内核实际同时占用GPU。
不能为了获得单图事件而不计成本地拆出大量细碎命令；
实现时同时记录任务/派发数量、主机准备与提交时间、设备事件及回读量。
进一步合并同图内部阶段或改为工作组协作时，仍保持原几何、编号、边顺序和选路语义。
不在本次架构迁移中同时更换启发式或用测试路线拟合策略。

## 5. 缓存、变化和交付

复用生产loadIdentity、revision、fingerprint、GeometryKey、MovementKey、
halo依赖、在途请求和走廊缓存身份；事实、体型差异行及边界都参与有效性。
变化只重建受影响资产和实际依赖者，新旧设备槽按发布身份区分。

取消请求可停止后续派发，已提交GPU命令不能被假定立即结束；
旧槽、上传暂存及结果槽持有到实际完成事件之后再复用。
取消一个订阅者不能破坏其他仍订阅同一计算的请求。
版本检查放在接收、发布、完成交付等现有业务边界，
不为迁移增加逐节点或每若干项反复跨主机检查。

结果仍进入现有详细寻路接口。GPU恢复的具体连接、成员及边界资料应随结果交付，
不能仅返回“已连通”后再让CPU宏观算法算一次。
原已完成走廊命中也不必为了后端一致性再提交GPU。

## 6. 实现和验证的交付边界

后续隔离实现先以现生产请求/任务接口及依赖状态机为依据，
把GPU计算和设备资产管理作为后端落实；未接线项目必须逐项标明。
仅完成冻结图流水线时，只能称该部分验证通过，不能宣称完整宏观迁移完成。
未经生产接入阶段，不修改生产默认路径或发布包。

验证沿用有效历史输入、原两组59地形、图/边界/父图及610/3216物理查询口径。
CPU生产执行器参考和旧GPU数据继续复用，不因新候选出现而失效。
旧逐请求单在途数据仍是单请求延迟参考，不能代替多个请求同时在途的数据。
必要新增项只覆盖这次改变的依赖推进、在途并发、实际请求合并/缓存、
缺图续行、优先级和发布生命周期；对应范围缺少历史数据时才补缺。
不默认重跑CPU、原生或游戏矩阵，也不自行扩展地形、体型或实体数量。

应分别确认：

- 图、路径、代价、同分选择及生产所需交付资产与CPU语义一致。
- 无关图未完成时，已就绪请求能否推进及独立交付。
- 多个请求同时在途，构图与搜索的依赖是否正确，设备事件区间是否发生重叠。
- 冷图、热图、缓存命中、真实缺图续行各自范围的耗时与资源，
  不能把一种口径的收益外推为完整迁移收益。

已有中位CPU16.4687/302.3657ms与GPU29.4608/46.2247ms，
继续描述各自已测冻结流程，不删负项，也不拿它们证明修正架构必然更快。
当前没有足够分项数据把单体型约12.99ms差额定因为调度或某个串行内核。
