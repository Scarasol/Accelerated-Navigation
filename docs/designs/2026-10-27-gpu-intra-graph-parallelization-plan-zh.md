## 1. 已有证据与新发现

### 1.1 优先解决的是图内工作

有效历史继续复用。最终依赖候选fresh中位44.5870/163.0758ms，
旧GPU29.4608/46.2247ms；当前候选未通过性能准入。
中位样本的设备事件区间累计如下，单位ms：

| 内核 | 单体型 | 混合体型 |
| --- | ---: | ---: |
| 组件 | 1.4576 | 27.9940 |
| 连接边 | 5.6000 | 72.1009 |
| 边界 | 21.5060 | 44.4762 |
| 父图 | 14.0916 | 14.3894 |
| 宏观搜索 | 0.3487 | 0.6965 |

这些不是严格可加的端到端分账，也不是SM利用率测量。
目前没有为热搜索再加复杂协作的收益依据；先解决上表构图部分。

### 1.2 源码中的串行位置

- `boundary_graph`：一个边界对只有一个work item，枚举入口层、256个面位置、
  方向、距离和落差，再执行几何检查。
- `super_graph`：一个父图只有一个work item，顺序构CSR、反向CSR、SCC、元数据和凝缩图。
- `graph_components`：没有门时一组64项并查集；`has_doors`为真时全图交给lane0串行BFS。
- `graph_edges`：含门或启用精确共享行时，全图交给lane0枚举；不是只有困难的那条边串行。
- 无门组件的编号和元数据收集还由lane0扫描4096格，可进一步并行化。

不计时的同语料结构提取确认：单体型59图中18图进入含门支路，
混合472图中144图进入该支路；对应合法格4655/86053。
这是分支覆盖计数，不能据此断言它们贡献了27.99/72.10ms中的多少。

### 1.3 父图移植遗漏了CPU已有的成员索引

生产`SuperClusterTopology.condense`已建立：
`nodeOffsets + groupedNodes`，按原节点顺序分组，然后只访问当前分量的成员。
GPU却仍是：

```text
for 每个强连通分量:
    for 全部节点:
        如果节点属于当前分量:
            处理它的出边
```

这使成员判断从O(V)退化为O(KV)，K为分量数。
边遍历本身并非重复K遍：每个节点的出边仍只在所属分量内处理。
不能误写成整个算法O(KE)。

旧语料中两个较大父图都是392节点，分别314/270分量，
因此执行123088/105840次成员判断。补回CPU已有成员索引后，
成员枚举只需各392次，另有线性建索引成本。
不能将14ms的父图耗时全部定量归因于这项遗漏；
但这是明确的结构缺口，应先修，不必先更换SCC算法。

### 1.4 直接复制几何暂存不可行

每份旧精确几何暂存：

```text
矩形与坐标轴：(128*4 + 260*2)*8 = 8256字节
visited和queue：260*260*2*4 = 540800字节
合计：549056字节，约536.19KiB
```

若为每个边界的64个工作项分别复制，111/222边界仅此一项就需
3,900,493,824/7,800,987,648字节，尚未加其他图和搜索资产。
因此不能把串行函数复制到64个lane上就称并行方案完成。

## 2. 确定的下一候选

一个区域的多个独立候选位置由GPU协作计算，完整几何工作使用有上限的暂存池。
最终结果保持原编号、原边顺序和原代价。
不是扩大到整场凑批，也不增加CPU提交队列或恢复主线程预算。

### 2.1 含门组件改为精确平面检查加并查集

组件中的普通相邻连接为`distance=1, dy=0`。
现几何定义在此情况下`lowY=highY=0`，上下折线路径退化成同一条水平线。
因此只需检查这条线的严格矩形相交，几何安排图BFS不能增加任何可行路径。
这个结论来自原数学定义，不按地形名称或测试路线选分支。

实现步骤：

1. 沿用合法位图，为每个合法格初始化并查集。
2. 64个工作项分担正方向相邻格；保留生产内区“未触及门直接可连接”的原判定，
   需要精确检查时流式枚举碰撞盒，判同高度一格连接是否畅通。
3. 只合并实际可连接格。根始终向较小格编号合并。
4. 全组完成合并后，把根写入独立暂存，再计算根标记的前缀和；
   组件ID继续按最小根格递增，匹配生产BFS编号。
5. 逐格回填标签；分量坐标界限用32位min/max归约，最终按原位宽打包元数据。

合并阶段parent的并发读写采用一致的原子协议；
根压缩与编号不能一边覆盖parent一边让其他lane读取被改变的森林。
可先把根写入标签暂存，barrier之后复用parent做前缀和。
编号完成后再合并元数据，阶段之间全组一致到达barrier。

内区原有“是否触及门”的检查必须保留：
不能把边界的一般碰撞检查直接套到所有内区步子，
否则会改变原合法位图和门处理语义。

### 2.2 几何先作确定判断，剩余工作用有界GPU池

对一般跨高差/跳跃候选，先流式读取同一批精确碰撞盒，仅保留标志和计数：

- 起点或终点在障碍内部：确定不通；
- 原上折线或下折线未被挡：确定能过；
- 原覆盖全高度的单障碍条件成立：确定不通；
- 其他情况：继续原完整几何检查。

双精度表达式、严格不等号、门、halo缺失及128矩形容量处理沿用原规则。
不能把“还没判出来”当不通，也不把超过原容量当可直接放行。
上述都是原函数已有的充分判据，无新增启发式、近似或碰撞膨胀。

已做主机证明原型，与生产`BoundaryGeometry`对旧五组共320查询核对：

| 旧夹具 | 可精确判定 | 需完整检查 |
| --- | ---: | ---: |
| zigzag | 0 | 64 |
| grid-blocked | 0 | 64 |
| door | 64 | 0 |
| mixed | 53 | 11 |
| open | 64 | 0 |
| 合计 | 181 | 139 |

全部181个已判定值与生产一致；夹具中14个同高度一格查询全部可判定。
这不是一般输入的穷尽证明，也不是GPU实现验证。
不能把56.56%当生产快速路径命中率；尤其困难夹具全部仍需完整几何。
因此下一候选同时包含完整检查的协作，而不是只新增快速分支。

完整检查执行方式：

1. 当前有限任务组的预处理内核写“已通过位”和“待检查位”。
   仅为非空的待检查字建立紧凑索引；索引顺序可以变化，结果位置固定。
2. 设备几何工作组从该索引领取工作。每个工作组独占一份约536KiB暂存；
   整个设备池的槽数由显存预算限制，不为每个图、每个lane复制。
   可先使用32槽作为隔离资源配置，约16.76MiB，不宣称跨设备最优。
3. 碰撞盒收集、坐标轴准备先保留原逻辑；
   安排图BFS由组内64项分担当前frontier，用32位CAS标记访问、
   原子分配下一frontier位置，组内barrier后推进下一层。
4. 几何只交付能否通过，不交付BFS访问顺序，因此frontier领取顺序可变；
   每条线段判定、坐标轴及最终可达性保持原定义。
5. 把结果写回固定候选位，再由输出阶段统一生成图资产。

该池是有限GPU命令内的工作分配，不是增加OpenCL提交通道。
生产者内核完成事件是消费者开始的前提；池内工作组不等待尚未运行的生产者，
没有跨工作组barrier或占位自旋。
命令结束后仍按既有完成事件和持有规则释放槽。

跨命令共享的槽由主机明确分配不重叠范围；再次使用时依赖上个持有命令的完成事件。
不依靠多个工作组争抢空槽并自旋，不逐候选回CPU，不读取计数后再绕一轮Java回调。
工作不足的组直接退出；池不足时按现有任务优先级和有界资源规则推进。

### 2.3 连接边与边界按位置并行，稳定生成输出

基础图：

- 每格的72种方向/距离/落差候选独立，使用最多96位的固定候选位记录。
- 先并行判定，再处理待检查项，最后按原目标格升序生成精确行；
  不在每个工作项内复制原72项临时排序数组。
- 能力掩码用32位OR，非负有限代价用与原版等值的min。
  不更改平方根或代价精度，不用浮点加法原子归约。

边界：

- 面上每个入口格及内缩层独立；统一候选编号可编码
  `((方向序号*4 + distance)*6 + dy+4)`，最多96位。
- 入口顺序保持`inset/v/u`；候选顺序保持原`方向/距离/dy`。
- 每入口统计通过数，用工作组前缀和确定写入区间，然后并行写band记录。
- 矩阵代价/能力使用原等值min/OR，band不能靠原子追加的执行先后决定顺序。

单边界最多1024入口，接受位和待检查位约24KiB，
另有非空待检查字索引；不会产生64份完整几何网格。
前缀和可用约4KiB local存储，避免为每个位置建立独立命令。
最终必须按设备和kernel实际local/private内存核对，不仅看线程数。

预处理、完整几何池、最终输出通过原生事件连接。
调用者只看到最终图完成事件；不新增独立选点任务、凑批窗口或CPU结果往返。
相比原一条连接边/边界命令会增加有限的阶段命令，
这项成本必须纳入完整流程计时，不能只报内核加速。

### 2.4 父图先恢复CPU线性成员索引，再协作构CSR

父图改为每图一个64项工作组，工作组内分工：

1. 按节点并行统计出度、前缀和、填充CSR。
   每个节点内仍按原本的本地边、连接序列、目标组件顺序输出。
2. 首份候选保留原SCC遍历与编号。DFS顺序、反向边顺序及分量编号均不改。
3. 用生产相同的线性计数、前缀和、稳定写入建立`nodeOffsets/groupedNodes`，
   直接修复当前O(KV)的成员枚举。
4. 凝缩仍按原成员顺序和原出边顺序处理，
   保留首遇目标顺序、最小代价和unsigned witness同分规则。
5. 分量anchor及出口位按组协作；先完成anchor的min，再barrier，最后OR出口位，
   防止两种归约同时改同一个打包字。

成员索引可以复用SCC完成后的counts、cursors、order等暂存；
不为每个分量分配一张V大小的seen表，不引入K×V稠密暂存。
首份候选的SCC及部分凝缩依然串行，这个限制明确保留；
先删去CPU早已避免的额外工作，再判断串行尾部是否值得更换算法。

当前模板父图复用child内容，但新方法不能利用“八个child恰好相同”删去通用计算。
后续完整后端的不同child图通过描述表访问，
不把这批模板结果外推为任意大世界层级已经支持。

## 3. 为什么暂不选择另外几种做法

- 扩大整个批次：会恢复无关请求共享完成边界，没有解决单图串行。
- 每lane一份完整几何暂存：显存成本已明确不合适。
- 只添加精确快速路径：139/320旧夹具仍需要完整检查，不足以覆盖困难部分。
- 直接换全并行SCC：现规模只有数百节点，且编号关系影响后续结果；
  bitset传递闭包会增加工作量与大量barrier，尚无优于先修成员索引的证据。
- 持久内核里让消费者自旋等生产者：引入跨组驻留和进度风险，
  当前有限命令加事件已能表示生产顺序。
- 为共享邻接逐行建立CPU任务：违背原请求/依赖架构，也会放大提交成本。

## 4. 文献与跨厂商边界

NVIDIA《Scalable GPU Graph Traversal》强调拓扑相关的任务粒度及工作分配，
采用细粒度任务管理和局部前缀和；支持“按实际工作组织并行”的方法依据，
不代表其BFS实测加速率可以移用到Minecraft几何。

GPU Gems第39章给出工作有效的前缀和、stream compaction和分段处理方法。
本候选借鉴算法，使用OpenCL C 1.2实现，不引入CUDA运行时。
前缀和既用于减少串行索引工作，也用于保持输出位置确定。

AMD官方occupancy说明指出VGPR、LDS等资源影响可驻留工作量；
所以要同时约束工作组、private数组和local内存，不把“64项”直接当利用率保证。

Khronos规定barrier由整个工作组一致到达；本方案只用组内协作，
图之间和阶段之间通过命令事件组织。
不依赖NVIDIA warp宽度、AMD wave宽度、subgroup扩展、设备enqueue或64位原子。
64项是现有两厂商路径可表达的协作粒度，仍须具体kernel编译和能力核对。
没有其他NVIDIA或AMD独显实测，原支持结论不扩大。
