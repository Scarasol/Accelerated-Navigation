# RTX 5060数据准备与提交开销优化研究

日期：2026-10-26。响应用户“时间主要浪费在提交上，这部分有没有办法优化，结合网上资料”。
本轮读取源码、复用完整地形覆盖历史数据并核对一手资料，没有实现新候选或补跑性能。
前提以[覆盖量对齐与更正](../reports/2026-10-26-gpu-coverage-alignment-correction-zh.md)为准：
两组都覆盖相同59种地形，分别计算59/472份不同输出，不能只比较局部256任务。

## 1. 当前瓶颈的准确表述

可以优化，但尚不能将全部时间称为“GPU命令提交”或“PCIe传输慢”。
当前统计将多种主机端准备混在一个生命周期内。
按全覆盖原始11条样本逐条累加后除以样本数，得到可相加的均值分账，单位ms：

| 范围 | 单体型59输出 | 混合472输出 |
| --- | ---: | ---: |
| 地形序列化 | 2.0671 | 2.1705 |
| 缓冲分配、复制与上传准备/完成等待 | 0.6649 | 0.6793 |
| 查询打包、上传、GPU计算、回读与位图复制发布 | 0.2124 | 1.4532 |
| 测量内结果比较与资源关闭等剩余部分 | 0.2235 | 0.4906 |
| 全流程 | 3.1678 | 4.7936 |

单体型序列化占65.25%、第二项占20.99%；混合分别45.28%/14.17%。
这里使用均值，不相减不同范围的中位；四舍五入后可能有末位误差。
最后一项由同一组样本总量减前三项得到，包括检查、释放和区段边界等，
不是纯驱动释放，也不是生产导航必需的全部业务开销。
原始中位仍保持单体型3.1228ms、混合4.6816ms；没有将均值改名成中位。

数据来源：
`.tmp/gpu-coverage-alignment-20261026-v1/result-v1.json`。
纯上传设备时间、纯驱动调用CPU时间、排队等待尚未分开测量；
不能用约0.65ms这一混合范围推算PCIe带宽。

## 2. 从源码确认的可删除成本

`GpuResidentTopologyStudy.Atlas`当前逐事实遍历4096格，
每格查`geometry.shape(cell)`及`HashMap<Shape,Integer>`，
将原压缩flags和局部形状索引重新展平成32位全局形状ID/flags。
59事实对应241,664次逐格形状查询和哈希表查询，另有少量halo映射与palette整理。
这是原型输入格式引入的准备工作，不是GPU碰撞计算本身必须在CPU完成的事。

生产已有：

- `PackedFacts`：两格共一字节的4bit flags，或uniformFlags常量。
- `SectionGeometry`：4096个16位局部形状索引、局部palette、精确量化盒坐标。
- 不可变冻结事实与既有版本/指纹机制。

研究原型另外每批创建四个事实buffer和三个查询/工作/输出buffer，
分配对应JNA Memory，创建prepare kernel、设置参数及临时参数Memory，
结束时逐个释放。context/program本来就复用，并非每批都重新编译。
事实上传后还有一次`clFinish`，最终阻塞回读后资源关闭又调用`clFinish`。
这些实际存在，但本轮没有单独量出各API耗时，不能给它们分配虚构的毫秒数。

## 3. 第一候选应优先做什么

### 3.1 保留原压缩表示，删除逐格全局形状哈希

GPU输入优先直接由现有4bit flags、16位局部索引、局部palette和盒坐标组成；
CPU按数组块复制、记录偏移，GPU通过局部索引解释形状。
不先按4096格重建全局形状ID，不为传GPU再调用逐格位压缩序列化器。
palette可以按项整理，成本随形状表大小而变，不再每格做Shape哈希。
保留真实宽高、门、流体、unknown和严格相交，不能用粗占用换速度。

GPU需要多做flags解码及索引，这部分也必须纳入完整实测。
若保留所有非均匀flags与索引，不含header/palette时每事实约10,240字节，
原展平每事实16,384字节；并非宣称所有输入或总传输都固定下降37.5%。
已有可靠uniform信息可用常量记录，不为了识别常量再新增一次完整扫描。

### 3.2 复用缓冲与kernel，第一次数据也使用复用资源

context/program沿用现有复用；新增复用事实存储容量、查询/行/输出缓冲及prepare kernel，
按容量不足扩展，正常批次不逐个create/free。
固定buffer参数随资源绑定，不每批重绑全部参数；标量参数、实际长度与偏移按需更新。
主机暂存、kernel参数小块与可复用Java数组一起精简，避免新增包装或逐格对象。

必须分开报告一次性资源建立和每批完整处理；
“资源复用”不意味着地形事实首传成本为零。
同一个59地形的新内容首次装载仍完整计算序列化/复制/上传和最终回读。

### 3.3 删除中间全队列等待，保留一次结果完成点

同一有序队列内按“上传→prepare_rows→legal_anchors→回读”提交，
事实上传后的主机`clFinish`不作为阶段边界。
最终消费输出时才等待完成；若使用非阻塞回读，由对应完成事件确认结果可用。
在对应上传/回读完成前，不覆盖、重映射、释放或复用其主机/设备数据。
关闭服务时保留必要同步。

这不引入新tick等待窗口，也不只是把阻塞挪出计时范围；
端到端仍量到输出真正完成并可发布。
原型最终阻塞回读已确认前序完成，同批没有其它待执行命令时，
每批释放前再全队列等待也没有必要；采用长期资源后主要在关闭时同步。

### 3.4 同一冻结事实只上传一次，更新按现有版本替换

以后生产后端可维护事实到设备槽位的映射，直接复用已上传的同一冻结对象；
新版本仅更新变化事实及受影响映射，不重新整理未变的全部地形。
复用身份和发布约束沿用现有业务，不凭单一哈希声称内容必然相同。
完整拓扑缓存命中应直接返回现有结果，不触发重复GPU构图。

对首次覆盖全部地形仍上传全部事实；不能用长期复用场景替代首次装载结论。
这项为未来真实worker集成，不把离线语料反复回放当作生产必定存在的复用率。

## 4. 第二优先级与暂不优先的方案

可补测OpenCL host-accessible暂存buffer：
使用`CL_MEM_ALLOC_HOST_PTR`分配并通过map/unmap填充，比较实际5060上的上传/回读成本。
普通JNA Memory使用malloc，不能冒称已是页锁定GPU暂存。
OpenCL标准只保证host-accessible语义，不保证该flag在任意设备上都物理页锁定或零拷贝；
收益必须按本机驱动实测。缓冲可复用，不能每批重新锁页抵消收益。

有多个实际待处理批次时，可用两个暂存槽重叠下一批CPU准备和本批GPU执行，
避免无谓串行；不为了重叠额外积攒任务或延迟前台。
重叠可能改善吞吐，不代表单批完成延迟或CPU总量同比减少。
资源、队列依赖与事件规则必须完整计入，不能先记录异步返回就称任务完成。

不优先将5060改成GPU反复跨PCIe读取主机数据的“零拷贝”路径：
本算法对同一地形有重复读取，NVIDIA官方也限制离散GPU此类访问的适用情形。
这与页锁定暂存后一次拷入显存是两种方案。

CUDA Graphs/OpenCL command-buffer能减少重复的驱动命令提交，
但不会自动消除CPU端约2ms的序列化。
本机已保存的5060 OpenCL扩展没有`cl_khr_command_buffer`，
不能把规范里存在的扩展当当前驱动已支持；
若改CUDA Graphs，需要单独后端，不是现有OpenCL开关。
当前只有两个内核阶段，先解决数据格式/资源生命周期，再判断命令重放是否值得。
也不为省一次启动直接合并成需要额外全局同步的大内核。

## 5. 验证边界与收益判断

第一候选建议合并3.1至3.3及临时对象精简，不再只做一个小的API替换候选。
生产业务源码不动，在新隔离目录实现，旧研究原件及封存继续保留。
性能继续对齐完整59地形：单体型59输出、八配置472输出，各组CPU/GPU输入输出相同。
沿用3预热11正式样本及既有508组行/位图正确性。
有效CPU、GPU旧候选数据直接复用；不重跑游戏或基线矩阵。

至少保留“新内容首次装载（资源已建立）”与“同事实已常驻”两个范围。
补纯上传/内核/回读事件时间与主机准备分项，是为拆开此前混合范围的必要诊断，
不扩展导航场景。所有异步计量结束于完成，不将queued时间当执行时间。
一次性buffer建立、context/编译成本仍另记。
动态替换只在真正实现设备事实缓存时补必要正确性，不在当前方案阶段空增矩阵。

既有CPU单体型阶段中位0.7234ms，本候选要在首次装载也划算，
完整GPU范围须低于它；从原3.1228ms出发，仅减少少量启动调用远远不够。
现有0.1444ms常驻值说明重数据准备之外的该阶段较轻，
不是首次装载也能达到0.1444ms的证明。
不承诺未验证的目标值，不宣称可以省掉全部约2.7ms准备成本。
即使该阶段转正，完整构图的组件、能力边、haloUsed和稳定发布仍需后续接线验证。
