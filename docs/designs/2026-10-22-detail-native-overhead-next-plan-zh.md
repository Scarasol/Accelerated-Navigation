# 详细寻路下一候选：精简临时能力还原数据

日期：2026-10-22。

状态：源码和文献研究、官方1017所用flash/max三轮方法讨论完成。
双方认可下述单项隔离实验边界；没有实现、构建或测试，没有代码/数据或生产批准。
[研究依据与讨论记录](../reports/2026-10-22-detail-query-navmesh-1017-research-zh.md)。

## 1. 选择及边界

下一最小候选只优化 `NativeNavigationSearch.find` 中的临时 `previous`。
以取消预算隔离母版U为起点，生产P保持，T/QG/TC停止结论保持。

这次从改变搜索顺序，转向减少每次详细查询必经的外层数据处理。
不改原生A*、邻点、代价、八目标、分段跨度、worker或派发时机。
它是常数开销优化，没有证据表明能独立解决项目200ms目标，
也不将其包装成新的最短路算法。

当前代码在每次详细搜索前执行：

```java
NavigationCapabilities previous = NavigationCapabilities.capture(mob);
```

这会捕获完整能力、构造 `EnumMap<BlockPathTypes, Float>`，
并在record构造时 `Map.copyOf`。搜索退出后，对这份临时数据只执行：

```java
previous.apply(mob);
```

`apply`只使用四个evaluator开关和全部malus。
临时副本的width/height/step/drop/pose/evaluator类、
不可变Map和完整能力record的契约，对这个用途没有必要。
请求intent中的完整能力快照仍有必要，必须保持。

## 2. 具体改动

仅为 `previous` 增加请求私有的还原状态：

- 四个boolean：openDoors、passDoors、floats、overFences。
- 一个 `float[m]`，m为BlockPathTypes数量，保存每种类型的有效malus。
- 不增加持久图、共享表、池、失效机制或每节点检查。

捕获时依旧对全部m种类型调用公共 `mob.getPathfindingMalus(type)`。
读取顺序、四开关捕获时机应在实现时与原捕获流程逐项对齐，
不擅自改变带副作用getter的调用关系。
物理字段不再为临时还原副本采样；原入口的 `physicalMatches` 保持。

还原时：

1. 与原 `apply` 一样重新取得当前navigation的evaluator，不使用事前保存的旧实例。
2. 按原顺序调用四个开关setter。
3. 对全部m种类型调用公共 `mob.setPathfindingMalus(type, savedValue)`。

可以使用私有且不向外暴露的枚举常量数组，避免反复 `values()` 克隆。
不把该优化扩散成所有能力快照的迁移。

明确保持：

- 原intent的 `NavigationCapabilities`、Map接口、不可变性及全部调用者。
- getter现有载具继承语义；setter现有写回本mob的语义。
- 全量写回，包括默认值；不跳过同值，不只还原差异项。
- float原值，不为NaN或负零新增比较、过滤或量化。
- 原try/finally嵌套、清理异常与suppressed处理、profiler、
  navigation字段/乘数/timeout还原、RAW设置及移除、proof。

不把现有“读取有效malus，再写回自身map”的行为顺带改成载具状态恢复，
也不改变原先最终会写入的默认键。那属于另一个行为变化。

## 3. 成本账与风险

| 项目 | 现状 | 候选 |
| --- | --- | --- |
| 捕获全部malus | m次公共getter、装箱存Map | m次公共getter、写primitive数组 |
| 临时结构 | EnumMap及其存储、不可变Map、能力record | float数组及必要的私有还原状态 |
| 四开关 | 捕获并还原 | 捕获并还原 |
| 物理字段 | 临时副本再次采样 | 不为还原用途采样 |
| 还原全部malus | m次公共setter | m次公共setter |
| setter内部装箱 | 保留 | 仍保留 |
| 节点热循环增量 | 无此候选工作 | 无此候选工作 |
| 常驻/失效 | 无详细图 | 无详细图、无新失效协议 |

复杂度仍为每次查询O(m)读写，仍有小数组分配。
源码可以确认哪些临时表达被去掉，不能据Java源码分配语句
直接断言JIT后实际节省的对象数、字节数或CPU份额。
新状态类初始化、数组及还原成本必须计入，不称零分配。

原 `Map.copyOf(...).forEach` 不承诺枚举顺序。
按枚举顺序调用普通原生setter时最终值相同；
自定义setter副作用、调用顺序或中途抛异常下的部分还原，
不能据此声明全模组100%等价。
实现审查要核实实际调用关系及异常行为；不能解决的具体兼容问题就暂停该变体，
不为此新增全局资格体系、每节点防御或隐藏回退成本。

## 4. 为什么暂不叠加其他方向

“读取合并”能够在本项目unknown检查后，复用已定位的chunk，
省掉原region第二次定位。但known提前返回可能绕过region其它注入，
JIT后的实际节省也未知，暂不和本候选同时实施。

原生已有位置路径类型和AABB碰撞缓存。
floor/raw/邻域的新语义缓存需要处理动态Forge钩子、有效键与失效；
没有重复热点证据时，不增加另一层命中检查和缓存。

不恢复T同分规则、QG几何终端代价、全走廊距离场、
全门户配对、32格缩段或删点策略。
不把这些具体候选的停止结论外推为所有新算法无效。

## 5. 后续核验边界

本轮不执行以下检查。

以后若获准实现，先建立一个独立变更，再做最小必要能力与异常控制：
全部类型/四开关、当前evaluator、正常与异常清理、RAW/profiler、
navigation字段和公共getter/setter行为。
需要处理的兼容风险是具体的setter及生命周期关系，
不铺与改动无关的全套新测试矩阵。

性能首先沿用原35ms的六场（64/128/256并发，各8/28格），一次有限筛测。
先核对版本、接口、参数和计量，U/P/N有效历史直接复用，
不为新配对重跑基线，不自动扩15/25ms或新增冷启动前N次场景。
候选改动不使原历史自动失效。

重要计量边界：

- 原搜索探针只包 `PathFinder.findPath`。
- `previous`捕获和事后apply都在这个搜索窗之外。
- 需结合原整场CPU/分配、drain、首Path和共同路线到达等外层字段。
- 若必须归因，才补覆盖捕获、完整find及还原的必要外层观测；
  说明历史缺失的具体新字段。不得把新外层值与旧search值直接作差，
  不因增加字段重跑所有有效基线。

若语义控制失败，或实际需要更复杂兼容层，停止该变体。
若完整成本/结果没有可保留收益，或一次筛测含混，暂不保留或暂停归因，
不自动重复、扫参数或挪计量窗。
没有凭空设置的3%/5%门，也不以单次观察构造置信区间。

## 6. NavMesh的后继地位

长期值得研究的是压缩详细搜索的表示：
从已有section几何及成员定位，派生分层凸域和完整公共边区间，
另将台阶/跳落等表示成有向动作。
这不同于在旧八点之间补全配对，也不同于反复调整A*朝向。

但目前缺少按真实能力、clearance、动态钩子与惩罚认证的凸域，
现有量化几何和成员位图不能直接代替它。
构建、大小、更新、路径展开及复杂地形回退成本尚未闭合。

平面均匀且采用连续欧氏代价的部分，Polyanya是比通用视线检查更值得研究的方向；
它不是当前可直接替换原生的后端。
固定channel上的funnel不提供全图最优保证，
连续欧氏最短也不等于原生离散带malus动作最优。
该资产方向不是本候选结束后自动实施的下一项。
