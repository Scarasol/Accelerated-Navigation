# 阶段调度合并候选的成本定位

日期：2026-10-20。对象：隔离S1 V4相对生产S9L。
本轮只读取已有净测、V3机制诊断及当前冻结代码，未修改候选或生产实现，
未启动游戏JVM，未重跑基线。

## 判断

本次没有定位到能够解释28格主线程CPU增加93.75 ms的确定代码缺陷。
已确认存在每八单元重复完整准入检查的调用放大；
但没有该检查的独立计时，不能把它认定为主要原因，也不能预告削减后会省93.75 ms。
既有诊断没有出现窗口反复重建、同一选择器无故重扫或阶段循环空转。

按此前约定，本轮不据一个尚未定量的热点猜测继续修改或补跑整个候选矩阵。
保留隔离候选与首Path的小幅收益证据，停止扩大该候选；
200 ms长期目标保留。

资源快照跨度比上一报告中的提交至收尾跨度略长，两者取点不同；
这里明确使用costStart/costEnd，不覆盖上一报告数字。

约70%的进程CPU增量落在“进程减主线程”的余量里。
该余量没有逐线程明细，包含拓扑工作线程及JVM运行时等，
不能直接命名为无关背景工作，也不能指定为JIT编译。
Windows历史CPU计时有15.625 ms粒度，表格是范围定位，
不是各函数CPU的精确守恒分账。

`mainThreadCpuNanos`的实现实际调用 `ThreadMXBean.getCurrentThreadCpuTime()`，
由 `TimelineScenarioProbe` 的服务器tick START/END事件回调执行快照。
这里按“资源快照调用线程，即服务器tick回调线程”解释，
不是按JVM线程名称查找主线程。
原始快照未存threadId，不能把这一调用位置判断说成独立逐线程身份采样。

逐实体核验64条路线：搜索次数、空/部分/可达结果数量、
各实体最大返回节点数均一致。
这不证明内部搜索逐节点相同，但没有搜索次数或结果规模放大的证据。

旁证B的28格主线程CPU为234.375 ms，S1相对B为+31.250 ms，
而S9L相对B为−62.500 ms。
这是不同实现和不同历史运行，不能当作同版本重复测量或方差估计；
仅说明不能把S1与S9L这一对的全部差额直接当成新增代码成本。

## 差额出现的时间段

复用原costSamples，以整批提交为共同相对起点，
只使用指定时刻前后的真实采样值作为累计CPU上下界，不插值：

|提交后时刻|S1减S9L的累计服务器回调线程CPU差额范围|
|---|---:|
|1秒|0～15.625 ms|
|2秒|0 ms|
|5秒|125～156.250 ms|
|各自整场结束|93.750 ms|

两版所有实体的首Path最晚分别在75.084/78.162 ms发布。
在当前计时粒度下，2秒时累计差额尚为零，5秒时已高于整场最终差额；
因此差额随导航执行及收尾阶段变化，不能视作一笔固定的首段准备税。
这没有证明首段准备零成本，也没有定位2～5秒内的具体函数；
后继段准备、实体运动、其他游戏工作均未被这张累计表分离。

## 排除的实现问题

1. **小余额下无限重排。** 常规drain在出队前及任务启动前仍检查500 μs启动门；
   阶段准备耗尽机会后保留游标，外层停止继续派发。
   idle仍按截止/haveTime运行，不能以恢复余额门替代定位。
   源码未发现没有截止约束的循环；已有控制覆盖余额、截止及同key完成后再提交。
   这不是对所有可能调度条件作不存在空转的证明。
2. **窗口暂停后从头重建。** `Preparation`在同一Stage中保留cursor、points和result；
   `planned`阻止重新创建。完成的result在后续advance直接返回。
   304格机制诊断19个准备对象各调用一次，游标均到limit，返回true。
3. **top8无故反复全扫。** 同一选择器只有actual或target坐标变化才重置；
   完成结果缓存，恢复时重扫全量候选是为保持实际位置变化后的精确性。
   304格19个选择器各调用一次且完成，没有命中这类重扫。
4. **同一次派发多搜或正常阶段反复空转。** 304格记录20次Stage执行、20次真实搜索，
   同一Stage最多执行一次、零无搜索阶段。
   最后一次是final目标搜索，只确认最终组件后直接搜索，不创建窗口或选择top8；
   其余19次才执行窗口准备及候选选择。
   八场控制中有9次Stage执行、2次无搜索、同Stage最多两次，
   属等待恢复/取消控制，不能把它们当普通并发性能样本。
   七次实际搜索中仅cross8的非final首段执行准备及top8，其他搜索直接使用final目标；
   因此该控制记录的“单次完成”只覆盖实际命中的一对准备/选择，
   不能外推至七次搜索均执行了窗口分支。
5. **集合冻结等同重复深拷贝。** `List.copyOf`与`Set.copyOf`存在多处调用，
   不能仅按源码调用次数认定每处都重新复制全部元素；
   本轮未以此宣称存在大规模重复分配。
   净测整场及主线程分配反而均较S9L下降，不能支持分配暴增假设。

这些结论限于源码边界和实际观察过的机制样本，不扩展为28格净测全部阶段的命中计数。

## 确认的调用放大

实际链路：

```text
Preparation / SegmentTargetSelection 每八单元
  -> StageTask.canPrepare()
     -> current -> identity -> live -> valid
        -> 配置、实体类型策略、物理属性和请求身份
     -> expired
     -> scheduler.canPrepare -> dispatchAllowed
        -> 调度身份、pending、haveTime、墙钟和当前余额
```

`physicalMatches`比较宽高、步高、落差、姿态及evaluator类，
没有重新capture能力或遍历整张malus表，不能把它描述为完整能力快照重建。
策略查询会访问配置及实体类型注册表；这里既有生命周期检查，
也有必须实时更新的墙钟、haveTime和预算检查。
不能为了降低调用数直接删掉全部检查或恢复idle余额限制。

普通本地窗口扫描4096个源cell，即使源组件稀疏，仍扫描4096项：
每八项一个门检查，再加完成前检查，单次完整准备为513次。
边界窗口256 bit单band为33次；候选选择也按八项检查。

从304格已有对象的最终cursor/limit、单次advance及精确循环结构推导，
19次窗口准备加19次top8选择内部合计9854次canPrepare调用。
**9854是从代码和完成游标推导的调用数，不是探针直接记录的计数或耗时。**
不包括阶段入口等其他检查，也不能套用于28格64实体的窗口分布。

单实体指一个Minecraft Mob，不是只有一个候选点。
逐阶段原值与推导对账：

|304格阶段|次数|准备limit|选择候选n|每次准备门|每次选择门|小计|
|---|---:|---:|---:|---:|---:|---:|
|1～10、12～18|17|4096|249～256|513|33|9282|
|11|1|4096|175|513|23|536|
|19|1|256|16|33|3|36|
|20（final目标）|1|无需准备|无需选择|0|0|0|
|合计|20|||||9854|

八场控制的cross8非final首段为limit256、n16，推导33+3=36次；
其余Stage没有执行准备/选择，不能以“36次”描述整个调度链的全部检查。
对象last字段来自关服时快照，逐阶段表按源码分支与调用命中解释，
不把关服字段冒充入口瞬时状态。

该304格深诊断记录的19次准备墙钟合计11.8149 ms，
19次选择合计4.1299 ms，已包含其内部准入检查。
这是带诊断的墙钟、包含冷启动与探针影响，没有独立CPU和有效对照；
不据它估算本轮28格额外CPU，亦不宣称检查开销可忽略。

因此定位结果是一个具体的后续可测点：
“每小批完整身份/策略检查的重复成本”，而非已确认的性能缺陷或收益。
如未来重新打开候选，应先获得该调用链的独立成本和实际命中次数，
再判断是否值得将不变身份检查与实时截止检查拆开。
本轮没有为这个待验证方案切换审查provider或直接实施。

## 定位的边界

当前资料缺少S1 28格净测的：

- 逐阶段续行、门拒绝及重排次数。
- 完整准入检查与枚举本体分别的耗时。
- 非主线程逐线程CPU及编译活动。

因此，不能从本轮结果断言93.75 ms主要是重复检查，
也不能断言218.75 ms是JIT、预热、拓扑工作或波动。
本轮已完成约定的现有证据定位，未发现足以据此继续修改的确定原因。
