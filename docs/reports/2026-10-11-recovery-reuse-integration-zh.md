## 优化筛查与具体取舍

| 检查方向 | 核对结果与取舍 |
|---|---|
| 原型的成功版本/代次字段 | 当前完成回调已经持有真实写入结果及加载/版本身份，并查询Runtime实际待写责任。这两个额外字段没有新增必要消费者，不移植重复状态。 |
| 恢复队列与通知 | 成功当前版本写入直接清除旧待办；原通知在poll找不到对象时退出。额外出队判断不能再省一次已经消除的扫描。 |
| 提前省掉尚在途的恢复 | 必须处理形成失败、已有需求和后续唤醒；旧“成功后复用”数据不支持这一新策略。没有实际收益证据和完整契约，不把它当作成熟简单优化。 |
| 复用扫描scratch | 需要保证碰撞getter重入时输入不被覆盖，尚无收益与完整重入证明。不是本轮已成熟的小改。 |
| 原来的减少RETURN采样方向 | 原型目标场景没有收益，边界编辑还退步；维持放弃，未接入。 |
| 形状缓存、增量扫描及压缩 | 各自涉及依赖、失效或存储策略，不扩大为本轮恢复复用的简单补丁。压缩仍有热点，后续按修复后的游戏数据另行判断。 |

源码事实与生产入口来自当前Service/Runtime、原型功能源和上一轮退出记录。Oracle Java17的CompletableFuture及ConcurrentLinkedQueue API用于核对异步完成线程和原队列交接边界；来源记录在本轮临时目录。外部文档不证明业务正确或性能。当前Service保留服务器邮箱/持久化回调交接，没有假定future回调自然运行在服务器线程。

## 性能结论边界

上一轮原型在受控重叠窗口的完整主线程采集工作中，两进程分别从0.600→0.329ms和0.525→0.381ms，减少45.2%/27.4%。该指标包含编辑观察、帧末和恢复调用，排除窗口外等待；不是整个游戏tick、纯搜索或整个模组开销。

本轮新增反馈没有计时，只确认当前生产同样消除第二次扫描。没有重新量化当前实现的性能比例，不能把旧原型百分比复制成当前生产的新增收益。两版在本轮重叠场景都只实际写入一次，因此不能据此声称压缩工作减半。

真实游戏中重复恢复的发生率及其在秒级尖峰中的占比尚未确定，不能据此承诺1.78秒尖峰减少27%–45%。采集/压缩其余热点和修复后整体正式性能仍待游戏确认。
