# 混合门基础与实体执行复测

日期：2026-10-14。状态：**用户将水域执行特性暂列为不处理边界，本轮其余 14 个场景通过；完整功能覆盖及生产接入尚未认证，未送审，压缩暂停。**

本轮按用户建议研究“其他能力低档、门允许打开基础；不能开门的局部处理”，并复测上一轮水域、不开门绕行、地形变化绕行三个失败。前轮原件保持，不将本轮结果写回旧版本。

## 1. 当前结论

“可开的门视作空气”在本轮宏观候选矩阵中可行：仅转换可开木门的临时事实，重新应用已有通用支撑规则，没有新增特殊落点算法。实际 PathFinder 和 OpenDoorGoal 仍面对真实门。

允许开门基础不能直接交付给不开门实体。原型在门依赖范围按实际状态生成替换行，空行也覆盖基础行；没有将不适用的门边并回去。普通区域和既有局部结果可共享。

最终主测试 `mixed-v3` 有 15 个实体场景：12 项实际到达、2 项负控制正确、水域 1 项 EXHAUSTED。**主测试运行结束与证据核对通过，不等于整体功能认证通过。**

用户随后明确：“这不是 bug，准确来说就是特性，暂时确实可以不做处理。”按此处理决定，水域演员在原生执行中停滞暂不作为需要修复的派生图问题，本轮其余 14 项均通过。原始水域终态、驱动失败检查和 `functionalPassed=false` 保持，不追改历史预期，也不把此决定当作水域实际到达或全部功能覆盖的证明。

## 2. 被测门与图

64 个真实门场景：木门/铁门 × 开/关 × 四朝向 × 两铰链 × 封闭门框/门顶布局。每个场景有两个权限的真实详细查询，共 128 次；这些是查询对照，不是 128 次实体执行。

驱动对照原版采集事实和门专用处理，与“木门空气视图＋通用支撑”得到的合法锚点及局部出边。合法锚点和出边没有差异。`mixed-v3` 导出每场景两份生产构图快照，独立读取器进一步对照标签、元数据、CSR 目标、能力掩码和距离下界，共 128 份图。

木门转为空气后，门顶没有生成仅由门板支撑的浮空锚点。铁门不因 canOpenDoors 而被转为空气。门框、低顶及其他真实几何保留。没有要求实体站上门顶，没有将查询 canReach 写成站稳或实际到达。

本矩阵也出现“关闭门的宏观几何候选存在，但不开门原版查询不能到达”的朝向组合。它与被对照的原有宏观规则相同，不能将候选的一致性理解为真实可达性的一致性；真实搜索继续决定详细结果。

`MixedDoorGraph` 是同一基础对象及按请求条件缓存的局部替换视图。门依赖范围覆盖现有 LocalKernel 的锚点、prism 与门移动读域，也考虑 halo 门。这个保守范围只为本内核验证，不能直接套用到其他构图算法。

本轮仍使用之前的锚点表达，没有测量新空间收益，没有把门策略当作压缩修复。

## 4. 上轮失败与本轮修订

### 中间段耗尽

上轮两条绕行的真实 Path 正常耗尽，但实体未进入精度 0 的阶段格。新原型在中间段可达且正常耗尽后，直接从实际实体位置查询下一候选目标。没有伪造中间位置，也没有扩大目标精度。两条绕行本轮均实际到达。

最终段规则保持严格：最后段真实 canReach 与实体实际目标 accuracy=0 必须同时成立。不能以中间段交接逻辑把最终 partial 或未到达改成成功。

### 输入版本与原生重算

前轮另建观察区域且只记录版本过期。新原型通过隔离同包桥接调用冻结 NativeNavigationSearch，取得实际搜索区域的 NativeQueryProof，检查 RAW scope 退出；生产类可见性未改。

输入过期先停止旧节点交付，再在 END 重搜。每次暂停记录旧节点游标，前后没有消费变化。临时宏观事实内容变化时使用最多一次刷新；没有人工支撑/方块资格复核，没有旧 Path 再批准。

`mixed-v1` 还暴露了门动作引起原导航 recomputePath 自行替换 Path，而原型仍引用旧 Path 的缺口。`mixed-v2/v3` 将该入口也排入暂停/真实重搜，并记录每次真实详细入口，最终没有未登记搜索或外来 Path 替换。正常查询的 timeout 重置及目标、精度安装单独与 moveTo 衔接，避免复用恢复前状态。

原参数保持 accuracy=0、visited multiplier=1，range 和节点上限来自实际原导航。最多两次 native-stop 恢复、一次宏观刷新、180 tick 阶段及 600 tick 场景上限保持。输入重搜属于当前性处理，不借此重置恢复计数。

## 5. 水域仍未通过

v1/v2 在流体连续更新时过早消费一次宏观刷新，下一次变化到来后返回 UNAVAILABLE_INPUT_REFRESH_LIMIT。这不是原版无路。

v3 暂停后合并宏观事实变化，在最后一次变化后连续十 tick 稳定才刷新。实际记录六次变化合并、一次宏观刷新；这个等待没有批准旧节点，也未增加刷新次数。十 tick 是研究参数，不能当作通用稳定性保证或生产调度方案。

刷新后的真实原版段查询可达，实体仍被推回 x≈1.3 的墙边。之后三次原生停滞停止，执行最多两次既有恢复，最终 EXHAUSTED。348 tick 结束时，额外终点诊断查询依旧 canReach=true，但没有执行该整条 Path。它只证明“搜索返回可达”与“该演员实际能逆流移动”不同，不能把水域改记为通过。

独立 `water-control-v2` 整段原版物理对照采用新演员、相同能力和精度，另建临时世界，不用于完成失败宏观请求。稳定水流控制从主测试失败位置启动，输入证明始终当前：一次真实终点查询 canReach=true，实际 x≈1.3 未能前进，101 tick 后原生停滞清空 Path。这个失败无需局部图或分段交接也能复现。

额外无流源水控制同样只查一次真实完整 Path，能前进到 x≈10.31、y≈81.53，但 404 tick 后仍原生停止且未到终点，输入证明一直当前。这说明普通 Husk 的浮水跟随还存在实际执行边界，不能把全部水域问题单独归因于水流，也不能宣称任何两栖实体无法到达。两个控制都保持 EXHAUSTED，不能用“原版也失败”删除主测试失败或宣告功能通过。

## 6. 版本和隔离

证据根：`.tmp/mixed-door-functional-20261014/`。最终主测试为 `mixed-v3`。

- `mixed-v1`：10 项到达、2 个正确负控制、3 项失败；门原生重算未完整纳入，查询记录不声称完整。
- `mixed-v2`：12 项到达、2 个正确负控制、水域 1 项失败；全部真实详细入口可计数，水域变化仍过早消费刷新。
- `mixed-v3`：12 项到达、2 个正确负控制、水域 1 项 EXHAUSTED；合并连续变化，补原版终点查询诊断和 128 份门图快照。

三个主 JVM 均完整停止、退出 0。`mixed-v3` 的 195 次真实查询为矩阵 128 次、实体场景 67 次；后者含 2 次负控制与 1 次仅查询的水域诊断，其余为实际段查询。735 条驱动检查中 734 成立、1 条功能预期失败，functionalPassed=false。

独立物理控制 JVM 完整停止、退出 0，2 次实际查询及两条完整移动轨迹另计，不混入上述 15 场景或 195 次查询。`water-control-v1` 因 Path 类型导入二义性编译失败，未启动 JVM，不计场景；原件保留，修正后使用新目录 `water-control-v2`。

独立读取器最终主测试 3,338 项证据核对通过；它重算真实位移及最终目标格，验证冻结身份、原参数、原生节点、候选目标、交接实际起点、暂停游标、旧代次拒绝和发行隔离。组件快照独立对照，完整 primitive 行相等仍是 Java 驱动断言，不夸大读取器覆盖。

独立物理控制读取器另有 551 项核对通过，确认主测试失败位置与同流控制起点一致、真实原版末节点、连续位置轨迹、原生停止、输入证明保持当前、两次实际搜索和完整关闭。它验证失败证据，不将两项实际未到达登记为功能通过。

五份生产构图/采集核心及原型依赖均来自此前冻结源，使用独立 javac/重映射/发行副本，没有运行共享 Gradle 构建。48 个原有导航、调度和 Mixin 类字节未变。新增同包 ResearchNativeBridge 只在隔离包内。没有修改生产源码、另一对话动态预算、用户存档或既有证据。
