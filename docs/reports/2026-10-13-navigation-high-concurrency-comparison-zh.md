# 128 / 256 / 512 并发、多路线寻路对照

日期：2026-10-13。设计依据仅为 [现行原版详细寻路契约](../designs/2026-10-13-native-detail-navigation-contract-zh.md)。测试没有修改生产寻路算法。

## 主要结论

两种模式各完成 18 个正式场景和 2 个预热场景。正式场景每种模式共 5,376 个请求，全部保留结果；所有场景都完成采集，没有服务端崩溃或测试截止超时，但部分导航以 `EXHAUSTED` 结束，不能把“测试采集完成”解释为“所有实体成功到达”。

512 并发的核心对照如下。A 为我们的寻路，V 为原版寻路；时间为 ms，括号为相对原版的变化率。

| 距离组 | 批量提交 A / V | 提交 tick 工作 A / V | 物理到达 P50 A / V | 成功率 A / V |
|---|---:|---:|---:|---:|
| <12 格 | 5.40 / 41.07（-86.85%） | 12.27 / 46.94（-73.85%） | 3253.97 / 1637.91（+98.67%） | 96.09% / 99.02% |
| 12–24 格 | 2.76 / 63.43（-95.65%） | 11.47 / 68.73（-83.32%） | 7180.52 / 3893.73（+84.41%） | 93.75% / 98.14% |
| 24–32 格 | 2.77 / 199.62（-98.61%） | 11.25 / 208.46（-94.61%） | 11656.55 / 6013.39（+93.84%） | 98.44% / 80.86% |

当前实现明显降低了同 tick 批量提交造成的主线程尖峰，但首次 Path 发布和实体到达更慢。不能把提交减少 98.61% 称为总体寻路加速 98.61%。

真实 `PathFinder` 的总搜索时间也有距离差异：512 并发下，8 格组增加 33.04%，18 格组增加 89.42%，28 格组减少 18.40%。28 格的成功率高出原版 17.58 个百分点，但其优势伴随更长的排队和移动时间。短程和中程的成功率反而低于原版。

## 场景与公平性

- 并发：128、256、512。每个批次在同一个服务端 tick 的 START 事件里逐个调用所有实体的 `moveTo`。原版同步搜索在调用内执行；加速版由共享调度器处理。不是 N 个原版搜索线程同时运行。
- 距离：主体水平距离为 8、18、28 格。斜线增加 3 格横向位移，坡道改变高度；分析程序逐个验证实际欧氏直线距离仍处在相应区间。绕障碍后的行走长度可以超过直线距离。
- 路线：64 个 40×40 地形单元，每单元 8 个不同起终点，轮换四个方向，并交换部分实体的起终点。512 并发时有 512 对不同起终点；不是所有实体共用同一路径。
- 8 类地形：平地、斜线、单墙绕行、错位双墙、两级坡道、柱阵、双格门洞、L 形拐角。各距离组均混合这 8 类；不是只改变同一路线的实体数量。
- 两种模式使用同一份地形生成代码、种子 `20261013`、相同 mod/probe jar、JVM 堆上限 3072 MB、成年尸壳、永久发光、速度 II。生成后落地 20 tick，再提交。
- 关闭自主目标和实体推挤，保留原版地形碰撞、寻路和运动规则。这隔离了请求调度与地形搜索；不模拟生产中的群体拥堵。
- 新建独立超平坦世界，不复制生产存档；测试区和寻路边缘区预加载。两边各一个 JVM，先后运行，避免同时争抢资源。
- 原版为同一 Forge + 导航 mod 运行时中的 Husk bypass 基线，后台拓扑服务仍存在。不是卸载 mod 的纯净原版服务器。
- 每个组合重复 2 次；第二轮反转距离和并发顺序。先用 64 实体的 8 格、28 格混合路线预热。未强制清理缓存或 GC，所以不是严格的冷缓存测试。

## 百分比与计时定义

变化率统一为：

```text
变化率 = (A - V) / V × 100%
```

耗时、分配量、节点占用的负值代表减少；TPS 和成功率的正值代表增加。基线为零或数据不存在时写 N/A。成功率另用“百分点”表达绝对差异；CSV 同时保留相对变化率。

每次试验先求相应统计量，再对两次重复取中位数；两个值的中位数等于它们的均值。因此某些“次数”汇总可以出现 .5。MB 为 1,000,000 字节。

物理到达要求实体的 `BlockPos` 到目标的 Manhattan 距离 ≤1，与本次原版 accuracy 一致。物理到达、Path 就绪、原版导航耗尽、加速任务终态分别计时。终态之后继续观察 10 tick，允许原版耗尽节点后的剩余速度进入目标范围。加速版成功必须为实际 `SUCCEEDED`；原版成功要求真实 Path 可达且物理到达。原生 partial、耗尽和失败均保留。

到达和成功完成的横向耗时只比较两边都成功的同一请求，并列出样本数。它回答“相同可完成路线的耗时差异”；不能代表未完成请求的到达时间。成功率、搜索总成本、资源和整个批次观察时间则包含所有提交。
