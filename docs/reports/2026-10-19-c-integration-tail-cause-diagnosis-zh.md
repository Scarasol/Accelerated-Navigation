# C 集成后 28 格并发尾延迟机制诊断

日期：2026-10-19。用户要求“寻找原因”。证据根：
`.tmp/c-integration-tail-cause-20261019-v1/`。

## 结论

**本轮确认了尾延迟的一个具体放大机制：后台结果完成后，还需主线程交付、
窗口准备和预算队列执行；准备好的原生搜索会因当前 tick 的时间余量或导航预算
不足而等到下一轮。同步原生调用不能中途抢占，一次较长调用可让剩余请求跨 tick。**

这不是新增的 C 专属调度规则。诊断 B 也发生预算不足后的等待。
本次有插桩的 C/B 中，28 格首 Path P95 反而是
107.6327/114.8982ms，C 低 6.32%，未复现旧两轮的 C/B 不利方向。
因此，当前已定位等待发生的阶段和实际停止条件，
**尚未证明这就是旧两轮 C 比 B 多出的全部 10.121/30.148ms 的原因，
也没有定位到 C 必须修改的具体代码缺陷。**

不使用本次诊断值冲销旧净测结果，不把旧差额全部归为波动、GC 或 JIT。
当前 C、预算和默认 JAR 均保持；没有新增候选或性能资格。

## C 的具体时间线

以 actor 24（tile 3、slot 0，交错墙）为例。
下表全部相对**场景提交时间**，不混用该实体晚 0.6022ms 的提交原点。
完整 64 请求的分解保存在 `cause-analysis-v1.json`，没有只保留该示例。

| 事件 | 时间 ms |
| --- | ---: |
| 宏观结果进入服务器队列 | 43.2796 |
| 主线程开始宏观结果回调 | 43.3569 |
| 主线程开始准备首窗口 | 54.4022 |
| worker 开始窗口计算 | 54.4732 |
| worker 窗口完成回调开始 | 54.5121 |
| 主线程窗口回调开始 / 结束 | 65.7141 / 65.7232 |
| 原生段搜索开始 | 109.1258 |
| 首 Path 安装 | 109.6796 |

窗口从请求到 worker 回调仅约 0.110ms；
随后主线程交付等待 11.202ms，窗口回调结束后又等 43.403ms 才开始搜索。
该请求首段搜索到发布约 0.554ms。

调度状态将等待进一步落实到两个不同条件：

| 场景提交后 ms | 实际事件 | 导航余额 ms | 当前截止余量 ms | pending | 条件 |
| --- | --- | ---: | ---: | ---: | --- |
| 42.2985 | 第一轮补发 drain 退出 | 2.3937 | 0.3971 | 5 | HEADROOM |
| 65.7261 | 后一轮补发获准，进入 drain 前的检查 | 6.4608 | 27.8811 | 22 | 可执行 |
| 73.5150 | 后一轮补发 drain 退出 | -1.3281 | 20.0922 | 7 | BALANCE |
| 99.9378 | 下一轮 beginTick 后 | 20.0000 | 旧 ready deadline，不适用于新 envelope | 7 | 新 tick |

第一轮停止时预算仍有 2.394ms，但剩余墙钟余量小于 0.5ms 启动门槛。
actor 24 的宏观结果稍后才交付，因此其 nextSegment 要等下一轮。
下一轮窗口很快完成，但主线程当时在执行同一批队列操作，
窗口回调直到本轮 envelope 结束后才被处理。

65.726ms 的补发开始时有约 6.461ms 余额。
其中 actor 26 的同步 findSegment 从 69.3943 持续到 73.5092ms，
耗时 4.1149ms。其后记录的余额已为 -1.3281ms，7 个待执行操作留下；
actor 24 就在这些尾部请求中。其搜索在下一轮 tick 才开始。

这是既有 `submitSoft` / `AtomicSearch` 的行为：
控制器用启动门槛决定是否调用，同步原生后端执行后再按实际时间记账，
不具备调用中的抢占能力。负余额不表示本轮加大预算或引入跨 tick 偿债。
代码入口为 NavigationScheduler 的 `drain`、`AtomicSearch.step`，
以及 SegmentedNavigationService 的 `queue` / `queueReady`。

B 也在提交后 70.1004ms 因 BALANCE 停止，
余额 -0.0321ms、pending 16，之后在下一轮处理。
因此该机制属于共同链路，不能据 C 示例称为 C 新增的调度错误。

## JFR 与未解决项

JFR 单调时钟锚点每版 4 个，无 DataLoss。
28 格首 Path 阶段，B/C 均无 GC，也没有记录到主线程 JavaMonitorEnter。
本机 profile.jfc 的该事件阈值为 10ms；
这个结果不排除更短的竞争、线程被调度出去或未采到的工作。

两版在相关阶段各记录到 4 个主线程 Deoptimization，
栈经过原生 WalkNodeEvaluator / LevelChunk；
C 的记录落在上述较长同步搜索中。事件自身没有提供可归属的耗时，
所以不把 4.115ms 全部记为反优化成本，更不外推解释旧两轮。
worker 的 JavaMonitorWait 包含任务队列空闲等待，不能当作 runtimeLock 竞争。

当前可以确认的关系是：**就绪/交付时点和执行次序改变，
在固定预算、截止时间和同步调用条件下，可以形成跨 tick 的延迟阶跃。**
C 的局部执行变化可能影响这些时点，但本轮没有单独操纵某一段时间来证明
旧 C/B 差额的因果归属。C/B 本次 P95 方向反转也保留。

冷路线最大相邻 tick 间隔和行走阶段 tick 中位数，本轮没有新场景插桩，
仍只有上一轮时间线定位，不能用本轮 28 格机制宣称这些指标已解释。
分配每秒的变化继续按原累计量与窗口长度解释，不以本轮 JFR 代替旧分配账目。

若继续优化，最明确的研究对象是宏观完成到首 Path 的主线程往返和
准备操作与同步搜索对同一预算的竞争；不能直接用扩大预算消去等待，
也不能凭本轮自动重开历史窗口候选。后续实现需要单独有界问题。
本轮停在诊断，不追加游戏、改法或外部送审。
