# 分段同步搜索的并发流畅性验证

日期：2026-10-12。

**当前证据支持采用“两连接分段、同步原版搜索、按段 FIFO 共享派发预算”，暂不增加分片。** 在本轮四条路线、最多128实体请求的隔离服务器中，共享预算下全部4531个搜索 tick 都低于50毫秒。这个结论覆盖本轮工作负载和服务器背景，不能扩大为任意地形、实体数量或繁忙生产服务器的保证。

用户补充的判断目标是大量实体同时请求寻路是否造成服务器尖峰，而不是分片能否减少累计寻路时间。本轮据此以实际服务器 tick、派发窗口和等待作为主要指标。生产源码、旧工程、原存档与历史原型未修改；没有生产接入、Git 操作或委派。

## 实际运行与输入

两个独立 JVM 顺序运行，分别使用全新世界副本。复用上一轮四条成功的两连接分段链：楼梯正向/反向各29次请求，城市正向/反向各33次，共124个不同请求。没有按耗时筛选请求，63240次调用是这组输入的重复测量，不代表63240种不同地形。

实际调用入口为 `ServerLevel → ProbeZombie → GroundPathNavigation.createPath → PathFinder → WalkNodeEvaluator`。原版搜索循环没有改写；原型只固定节点限额16384、搜索距离512、禁止水和开门，并记录评估器进入、清理与展开计数。

实体加入副本世界，禁用自主 AI 和重力，位置按照冻结请求回放。共享队列中的实体保持独立导航实例，每个实体每 tick 最多计算一段，下一段在 tick 结束后准备、下 tick 才能派发。**这验证真实服务器中的搜索和排队，不验证实体走路、落地、实际换段或完整 AI 负载。**

每个 JVM 包含首次、预热和三轮测量，每轮覆盖：

- 1实体分别运行四条路线；
- 8、32、128实体按四条路线分配，使用约4毫秒的共享派发预算；
- 32实体不设派发预算，在当前 tick 集中处理所有已就绪实体，作为对照。

每个批次之前采集8个空闲 tick，保留相同数量的静止实体。轮次和第二个 JVM 的批次顺序轮转；首次32实体对照在第二个 JVM 是第一个批次，因此包含首次调用成本，不能把这次峰值解释为与其他首次批次完全相同的冷热条件。

两个 JVM 均完成40批、31620次业务搜索，退出0、无超时，墙钟分别约157.24和156.47秒。总数为80批、63240次业务调用；首次12648、预热12648、测量37944。所有业务请求均返回可达路径，实际进入和结束一次评估器。两次障碍控制另列，不混入业务样本。

## 计时边界

派发放在 `ServerTickEvent.START`。实际 `MinecraftServer.tickTimes` 的计时开始于 START 事件之前、结束于 END 事件之前，因此包含本轮派发和世界 tick。读取器逐 tick 核对了实际 tick 时间不小于派发窗口、派发窗口不小于其中全部搜索调用时间。

原版搜索调用时间包括目标入口调整、`PathNavigationRegion` 获取、评估器准备、搜索、路径恢复和清理。候选目标已经冻结，宏观走廊计算、重新选择候选和位置准备在搜索计时外；位置状态检查、取队和少量结果保存计入派发窗口。分段候选排序的生产成本没有在本轮重新计入。

路径结果检查、下一段位置回放、报告构造和批次切换发生在 END 回调，不计入原版 tickTimes；START 到 START 的实际间隔另行完整记录，覆盖这些回调对运行节奏的影响。最终大文件写出、存档和停服在业务测量外。

4毫秒是本轮诊断配置，检查发生在两次不可抢占的原版调用之间，**不是严格上限**。50毫秒对应服务器正常20 Hz tick 间隔；低于它是本轮流畅性的参考判据，不是用户已批准的完整生产性能要求。

## 主要测量结果

以下合并两个独立 JVM 的三轮测量。所有数值单位为毫秒；p99 为全部对应 tick 的第99百分位，不是逐批最大值的中位数。

| 实体数与派发方式 | 搜索 tick 数 | tick 中位数 | tick p99 | tick 最大值 | 超过50毫秒 | 最晚首次获得路径 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1，共享预算 | 744 | 0.889 | 1.961 | 2.878 | 0 | 50.863 |
| 8，共享预算 | 202 | 2.454 | 5.420 | 5.490 | 0 | 52.758 |
| 32，共享预算 | 361 | 4.557 | 5.311 | 5.690 | 0 | 103.785 |
| 128，共享预算 | 1403 | 5.047 | 6.130 | 20.149 | 0 | 446.348 |
| 32，无预算集中派发 | 198 | 6.885 | 18.223 | 18.472 | 0 | 57.255 |

“首次获得路径”从入队到该请求返回计时，包含本轮 END 入队、下一 tick START 开始处理的正常等待；1实体约50毫秒不代表搜索本身耗费50毫秒。32实体共享预算的最晚首次服务为第2个 tick，128实体为第9个 tick。这里没有将实体搜索链结束轮次换算成走完全程的时间。

128实体匹配空闲基线的 tick 中位数1.393、p99与最大均2.063毫秒。其搜索期 START 间隔中位数49.993、p99为51.845、最大52.202毫秒，运行节奏未出现明显持续拖慢。空闲基线与搜索 tick 的差额不作为精确业务净耗时。

本轮直接观察到的取舍是：共享预算把请求分散到多个 tick，降低同 tick 派发的集中成本，同时增加首次等待。128实体一次涌入时等待可达约0.45秒，这个延迟是否适合最终 NPC 行为仍属于产品要求。

## 首次、尾部与预算超出

没有丢弃首次和预热：

- 共享预算首次 tick 的最大值按1/8/32/128实体分别为21.559、6.256、12.612、11.410毫秒，均未超过50毫秒。
- 共享预算预热最大值分别为2.827、5.091、5.809、12.910毫秒，也均未超过50毫秒。
- 32实体无预算首次对照出现一次51.602毫秒 tick；该批次含首次搜索初始化。预热和测量最大值分别21.565与18.472毫秒。仅此一个样本不能证明集中派发必然持续卡顿，但说明不能保证把所有已就绪请求塞进一个 tick 就足够安全。
- 全部4861个搜索 tick 中仅有上述一个超过50毫秒；共享预算下4531个为0次超出。

128实体测量期单次搜索中位数0.196、p99为1.028、最大14.912毫秒，23808次调用中7次超过4毫秒。派发窗口中位数4.102、p99为5.092、最大18.015毫秒，1397/1403个窗口超过名义4毫秒，通常来自完成最后一次调用后的正常超出。

这些尾部原值保留，没有扣掉 JVM 停顿、探针或调度时间。GC 日志包含运行中的停顿，但没有准确绑定每个长调用的停顿区间，不能把长调用全部归因于 GC，也不能据此承诺分片会消除它们。本轮长调用没有造成共享预算组超过50毫秒，因此没有触发追加可恢复分片对照。

## 核对、清理与异常

逐项核对实际请求输入、实体/路线/阶段/方法身份、候选目标、最终坐标调整、终点容差、加载路径区块、评估器 prepare/done、逐调用耗时分解、入队与派发关系、每 tick 调用数和计时包含关系。随后用独立读取程序重新计算所有报告中的分布与计数。

9类错误副本被拒绝：路线、请求序号、目标、成功状态、调用计时、缺调用、tick 未包含派发、等待和派发模式。两次运行的障碍拒绝、排队取消及实体/导航/队列清理成立；结束时调用解除全部168个强制加载区块，服务器正常保存副本并退出。

33个生产/构建文件保持原身份；153个冻结引用中149个未变化。另4个是两个副本的 `level.dat` 和 `server.properties` 正常运行写入。服务器扩写默认配置后，原设置逐项仍一致，原存档与输入区域文件未变。

异常保留：

- 第一次 JVM 启动的 GC 日志绝对路径参数在 Windows 下无效，退出1，未进入服务器或业务。仅修改新原型启动器，改用副本内相对路径；首次冻结记录保留，成功运行使用 `freeze-final.json`。
- 汇总首次把服务器自动扩写的 `server.properties` 当成不可变输入而拒绝。搜索数据与8类读取反例检查已通过；新增独立收尾读取器明确记录运行配置的预期变化、检查原设置，并增加派发模式拒绝。原冻结搜索源码与字节码没有修改。
- 仍有开发环境已有的8个 Forge coremod 字段转换错误，与此前实体诊断相同。它们未阻止本次服务器与导航调用，但本轮仍属于开发环境诊断，不是完整生产发行环境验收。

## 架构选择与后续

**在当前输入与背景负载下，分段同步加共享调度已经能保持基本流畅，暂不需要承担分片后端的实现和维护成本。** 原版搜索保留为不可抢占的局部调用，计算预算在段与段之间实施，实体请求共享 FIFO。

不能将这个结论简化为“分段后不需要任何调度限制”。128实体主要验证预算组，没有无预算128实体对照；32实体集中派发也已出现一次首次慢 tick。

真实实体接续仍需修正落地、实际到达和阶段目标衔接，这是后续实现验证。最终接入时应在真实 AI、宏观规划、区块活动及其他模组负载下复核服务器余量；当前隔离服务器的静止实体不能代替那些成本。如果出现局部搜索反复占用主线程并实际造成超时 tick，再针对其原因验证分片。当前生产没有接入本轮队列或详细导航。
