## 本轮结果

实际实现并验证了一个最小候选：
在旧连续空气段第二版上，省去ACTIVE到ACTIVE时字节桶的净零扣加。
正确性核查通过，但第一组完整API对照不支持采用：

| 新候选相对旧空气段版 | 进程CPU变化 | 实际耗时变化 | 分配变化 |
| --- | ---: | ---: | ---: |
| 空气重复 | -8.11% | -5.34% | 约0 |
| 无重复 | +24.87% | +27.99% | 约0 |
| 混合 | +12.33% | +9.50% | 约0 |

空气确有本次观察到的增益，但无重复和混合没有取得整体改善。
按测前范围在第一组停止，第二组及真实worker侦察均未运行。
不追加参数、候选或相同测试来争取通过；不重新开启波动归因。

这些是各形状一个独立fork的有界观察，不证明该写法在所有环境普遍退化。
本轮结论是“不支持采用这一候选”，不是所有同类别优化都无价值。
生产、旧版、默认JAR及旧封存保持；停止的图级引用聚合继续停止。

## 实现及语义

`B`为原生产基线快照，`R2`为旧连续空气段第二版，
`C`为本轮隔离候选，均不在生产目录修改。
C复制R2的62份源码/资源，只有`TopologyWorkerRuntime.changeFactReferences`
增加以下七行：

```java
int nextIdle = refs.idle + idle;
int nextActive = refs.active + active;
if (refs.active > 0 && nextActive > 0 && nextIdle >= 0) {
    refs.idle = nextIdle;
    refs.active = nextActive;
    return;
}
```

插入点位于原`computeIfAbsent`和`retainedBytes()`读取之后。
这两步各执行一次、顺序保持；剩余原标量主体保持。
只处理ACTIVE到ACTIVE，真实引用数仍逐次更新。
加权`applyFactReferences`、连续段遍历、单元素处理、锁、预算和生命周期均未改。

原先处于ACTIVE且最终仍处于ACTIVE时，字节桶先减后加同一个值，
按Java long模运算净效果为零；新旧int计数按原Java溢出语义计算。
条件不满足则继续原主体，保留归零、类别变化及负计数异常的写入前缀。
这里`nextIdle >= 0`表示原int运算后的结果非负，
不等于额外引入数学范围检查或修复旧溢出行为。

优化依据是确定的源级重复和既有引用维护热点，而不是假定旧波动根因。
JIT可能已省略部分原写入，新增条件也可能带来成本；
本轮没有用源码操作次数推算CPU收益。

## 正确性证据

- 实际B/C标量各核对351,384个状态，含268,956个错误结果、
  22,320个满足新守卫的模型状态；错误及完整状态摘要一致。
  独立oracle执行原始有序算法，不用C的快路径作预期。
- 覆盖int最小/最大值、极值delta、负数、内容相同但身份不同、
  map缺失、long桶溢出、归零与类别转换。
  22,320不是实际寻路命中率。
- 另注入`retainedBytes()`内部NPE：两版均先在map插入零计数对象，
  再抛相同异常，字节桶保持，核对了原读取与插入的失败顺序。
- 原9,073引用、6,048摘要、11,115失效构型的摘要与B一致，
  原实际断言91,668项通过，77项所有者账目与B一致。
- Core、Boundary、Door、Worker、Shared Stage、Shared Runtime六组受影响契约通过；
  其中Shared Stage为99,951检查、41路线构型、643组件证明，
  Shared Runtime为1,296检查。不是本轮实际游戏路线到达数。

`verify-checks.mjs`核对插入以外的源码一致性，
并将B/C独立模型输出、原B摘要、所有者账目和契约结果作二次核对。
有限状态和受控账目证据不替代全部并发执行证明。

## 成本协议与执行

协议在测量前固定，DeepSeek方案包4564B/118.261秒认可。
完整操作是`requestBaseGraph().join()`、读取组件数、关闭视图，
仍保留一个anchor；不是独立计数微基准。

每个fixture发布27个真实section，实际图有15个事实槽。
空气/无重复/混合分别有14/0/9个空气单例槽。
三个实现使用相同新JMH壳及profiler；
初始raw账目、槽数和单例数逐形状一致，关闭全部归零。
不同JVM的对象身份及哈希布局没有作同键配对。

Java17、JMH1.37、512MiB、单线程；
3次各1秒预热、4次各1秒测量，每形状独立fork。
记录进程CPU、负载线程CPU、wall、分配、GC、编译和操作数。
负载线程是运行JMH操作的线程，不是JMH驱动的main线程。
性能运行无JFR、插桩、强制GC、编译或hash调整。

最多两组`B/R2/C`及`C/R2/B`，每组完成三个实现后检查。
实际只完成第一组，3个master、9个负载fork，
测量操作83,119,234次；全部四次测量值保留。

预定有限筛选：

- 每组C对B：空气的CPU和wall至少改善10%；
  无重复/混合的CPU和wall增加不超过10%。
- 每组C对R2：无重复CPU和wall至少改善5%；
  空气/混合增加不超过5%。
- 每形状分配相对B和R2均增加不超过5%。
- 任一未过，停止进入下一组及游戏侦察。
  这些是有限投入门，不是统计显著性或生产资格。

无重复多项未过，混合相对R2也超过5%门，
因此`group2=null`、`gameScout=null`；未测值没有填成零或通过。
第一组3个实现均完成，没有只留下有利的空气结果。

## 下一项更具体的机会

源码复核找到一个比改等待/取消链更小的后继研究点：
**共享Base图导出时复用内部已经不可变的版本戳列表。**

`captureBaseStamps`返回`stream().sorted(...).toList()`，
`ViewEntry.topologyStamps`已见赋值入口为该结果及`List.of()`。
`BaseGraphView`私有构造器只有一处调用，传入该列表，
但内部仍执行`List.copyOf(stamps)`。
列表元素原本已浅共享；旧图快照需要保持的是原列表及原戳序列。

本机JDK17.0.18的`src.zip`核对：

- `ReferencePipeline.toList()`使用`listFromTrustedArrayNullsAllowed`。
- `ImmutableCollections.listCopy()`直接复用`List12`或不允许null的`ListN`，
  对上述允许null表示的`ListN`则执行`List.of(coll.toArray())`。

因此这里不能仅凭“二者都是不可变列表”假定导出时没有复制。
这提供了明确的分配消除方向，但本轮没有实施或测量它，
不承诺每次省多少B或整条寻路快多少。

后继应先核全私有构造及赋值入口、列表无后续修改及成员无null，
在受控交接处研究直接复用，保留参数异常、完整版本验证、
旧快照寿命和逐次pin/unpin/关闭。
不全局删除`List.copyOf`，不改变引用所有权。

该导出API由`RuntimeSharedTopology`和`TopologyService`调用；
宏观worker内部并非全部经过这里。
即使热API分配减少，也须另核真实请求频次及整路线收益，
不能把微基准改善直接视为解决冷依赖或Boundary热点。
Future/Waiter/取消回调链精简保留为更后继，
其关闭、取消、锁外完成、TTL/优先级及命中副作用更复杂。
