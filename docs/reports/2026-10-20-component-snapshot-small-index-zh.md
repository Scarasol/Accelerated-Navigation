# S9L：降低快照去重索引成本

日期：2026-10-20。用户授权在已保留的 S9 基础上尝试降低去重索引成本。

**本轮取得局部净分配下降的直接证据，建议优先保留 S9L 隔离候选。** 同输入局部操作的净分配
分别减少约 472 B 和 344 B；完整直接影响窗口的三个负载均值、中位数及 P95 下降。
不能把窗口约 20%–33% 的全部均值改善归给这个索引改动，也不认定稳定性能。
原 S9、生产代码、默认 JAR 及既有数据保持。

证据根：`.tmp/component-snapshot-small-index-20261020-v1/`。
协议 `protocol.md`，隔离源码 `candidate/TopologyWorkerRuntime.java`，
完整数据 `summary.json`，原始窗口 `runs/S9L/`，局部重放 `replay/`。
候选版本身份来自源码/class 哈希和加载来源，不由显示标签单独决定。

## 改动

S9 为每个新 component endpoint 构造 `ComponentSnapshotKey`，即使命中也要查
HashMap。S9L 将查询私有索引改为 `ComponentSnapshotIndex`：

- 最多 8 个唯一组件时，用固定 `Object[16]` 交替保存已有 endpoint 和 snapshot 引用，
  不另建查询 key 或 HashMap 节点。
- 匹配完整的 section、revision、channel 和 componentId；不按 anchor/id 匹配，
  不以哈希值代替完整身份。
- 第 9 个唯一组件成功构造快照后，一次迁移到原 HashMap key 规则，
  复用已有 8 份快照，并释放小数组。
- 大表模式仍由同一个临时 key 完成 get 和缺失插入，不重复构造第二个 key。

MacroQuery 仍只持一根索引引用，索引按查询惰性创建；普通非 refining 路线保持原路径。
不增加 Base 图字段或跨查询共享。原 16384 完整 endpoint 上限、每 endpoint 映射、
逐格成员快照、命中身份校验、保守收费和终态置空保持。
这是一次有界小表尝试，没有根据性能结果再调整容量。

## 正确性

旧真实路线 AuditChecks 字节码复用，普通 4 endpoint / 4 snapshot、
分层 9 endpoint / 5 snapshot，成员摘要、cost、witness 均与 S9 相同。
原 macro-commit 4 项、boundary-recovery 9 项通过。

SnapshotChecks 仅适配私有容器 size 的反射并增加新表示控制，共 **73,829 条断言**通过：
保留原身份/成员/别名/容量/计费/重物化/清理逻辑，新增 8/9 唯一组件边界、
重复不升级、错误第 9 项不污染、升级后原快照对象不变、释放数组、
大表模式拒绝错误拓扑，以及 small/map 的成功、取消、失败清理和导出寿命。
测试没有改变公开查询接口或扩大性能场景。
其中原 16384 endpoint 容量控制确实执行，含重复接受、第 16385 个新 endpoint 拒绝；
出处为 `correctness/snapshot-controls.json` 的 `capacity` 及原控制源码。

5 个实际被 agent 变换的候选类剥离 13 个已知探针后，
全部原方法规范化指令、分支目标、异常表及字段/方法结构保持。
该静态核对没有新增性能样本；未被变换的新 helper 使用冻结的候选 class，
加载来源核对通过。

## 历史复用与口径

复用上一轮 [S9 扩窗验证](2026-10-20-component-snapshot-direct-window-zh.md)
的有效 S9 及 C 背景数据，没有重跑 S9、C 或 B。
先核对版本、工具、接口、场景和计量身份，旧 528 行原始窗口记录直接读取。

只新增一个 S9L 窗口 JVM，沿原 ComponentColdProbe 和原窄 agent 的字节码、
原生 requestMacroQuery、63 section、air/distinct/mixed 顺序、
每负载 24 次预热和 64 次测量、512 MiB 堆。三个负载在同一 JVM 内顺序执行，
与旧工具一致，每次查询建立独立冷 runtime；不是擅自改成每负载新 JVM。
新 264 行（72 预热、192 计量）的输入/结果 hash、cost、endpoint/connection、
状态/witness、关闭和锚点全部通过。

W 仍从 NEW MacroQuery 前至对应最终结果 complete 调用返回后，
包含构造、capture、清理、结果缓存写入、走廊重物化及结果创建/完成，
也包含异步间隔；不是 CPU。queryEnd 是原工具 get 返回后的时钟，
wholeEnd 是原工具关闭后的第三个时钟。get 可以先于 complete 返回苏醒，
不裁掉这段，以 wholeEnd 包住 W。
起止和四锚点每查询各一次；complete 的 boolean 未另采，
唯一完成者是固定成功 fixture 的路径前提，不外推竞争终态。

只分析 W。窗外按用户口径视为波动，间接影响不处理；这是分析取舍，不是因果排除。
不分析旧工具附带的全进程 CPU、分配、GC 或 JIT 差额。

## 局部索引成本

为检验“降低索引成本”的目标，复用已有无 agent 的 SnapshotCaptureBench 字节及
历史 S9 数据，只补两个 S9L fork。actual 是真实走廊的 9 endpoint / 5 组件；
unique 是同走廊取每组件一个 endpoint，共 5/5，**仍强制 refining=true**，
不是普通路线成本。每操作含 MacroQuery 构造、共同反射接线和一次 capture，
三段合一少两个迭代器，不冒充完整窗口。

每输入 1 fork，3×1 秒预热、3×1 秒测量、单线程、512 MiB，
GC profiler 仅取直接分配 B/op；保留原 LogCompilation 设置但不调查 JIT/GC 间接效应。
参数、JVM/工具版本、成员摘要、输入计数和实际 overlay 来源均与历史对齐。
旧工具的 `snapshot.variant=S9` 是 dedup 语义开关；execution.role 和冻结的类来源
明确标记真实候选 S9L，未以该开关冒充版本身份。

W 包含异步间隔。本轮按用户范围不追溯间接原因、不追加对照矩阵。

本次性能输入都只有 5 个唯一组件，没有触发第 9 项升级。
升级分支有功能证据，但没有大量唯一组件的性能资格，不从小表输入外推。

## 审查与结论

代码/方案 7236 B 自包含包经既有 WSL 无头接口送 DeepSeek，
实际 `deepseek/deepseek-v4.1-flash`，407.959 秒正常返回
`ACCEPT_WITH_GATES`、本轮必须修改项无。
实际源码核对：revision 为 long、componentId 为 int、channel 为 enum；
ComponentEndpoint 是 record，anchor 构造时 immutable，Key 无自定义 equals/hashCode。
小表比较与原 key 四字段语义一致，索引每查询串行使用、原终态置空保持。
这些是有限前提核查，不把字段相等说成数学唯一或全面并发证明。

审查提及的普通索引 null、small 拒绝、升级保留前 8 对象、错误第 9 项后合法升级、
small/map 终态等已有控制覆盖。未将非阻断的建议扩成新性能矩阵。
窗口未开 GC profiler，两版局部 JMH 均开 allocation profiler，两个口径分开；
没有将两者混为一个 profiler 下的配对。三个负载顺序共用一个窗口 JVM 与旧工具一致。

结果 7368 B 自包含包在 250.122 秒正常返回
**`ACCEPT_SCOPED`、本轮必须修改项无**，仅认可小表路径的局部净分配证据、
历史非配对观察和保留隔离候选的取舍。
结果审查再次指出窗口差额主要在含异步间隔的主体段，
不能作为索引改动的因果收益；本报告保留该限制，也不反向断言与索引无关。
旧窗口 528 行是 C/S9 各 264 行，不照搬审查中将其全部称为 S9 的笔误。

两次审查均退出 0、未超时，配置前后 SHA256 均为
`071db56517e8f97ccde780095f71e5b264a1c7bc41694499cf81af7c2aca1858`，
实际 prompt/transmitted/answer/exit 原件全部保留。
`final-seal.json` 核对 1021 份旧保护输入、原 S9/生产/默认 JAR、实际候选和工具身份、
264 行新窗口及复用的 528 行旧窗口、两个局部 fork、5 类指令审计和两次审查；
三份状态文档旧原文另有备份。无 Java 进程残留。

本轮“降低小规模去重索引自身成本”的目标取得局部净分配下降的直接证据；
S9L 作为后续优先保留的隔离候选，原 S9 继续保留为有效参照。
不为达到更漂亮数据继续调阈值或复跑；未接入生产、替换默认 JAR、提交、push 或部署。
