## 实现与测量控制

`TopologyTaskExecutor` 在真实 Task 上记录既有入队时钟、实际选择时刻、序列及同 WorkKind 的排队深度。深度不表示所有类型的全局任务总数；入队时钟来自锁内 Task 创建，选择时钟在实际移出队列之后，区间包含很小的入队/选择记账时间。worker 从自己的 currentTask 读取身份，没有用 latency 减 queryWork 冒充排队，也没有在 executor 锁内调用观察回调。

`TopologyWorkerRuntime` 与 `RuntimeSharedTopology` 提供诊断开关、实际 worker 入口、query 前后、发布和交付入口的可选时钟。关闭诊断时不创建 Timing/JobTiming/TaskTiming，不读取新增分相时钟；Task 中保留诊断字段和分支，不能宣称关闭后的程序与旧版本逐字节相同或完全零成本。诊断开关只在完成 drain 的窗口之间切换，本轮不认证在途动态切换。

五个独立控制 JVM：对象+捕获、分块+捕获、对象+复用、分块+复用，以及开启诊断的分块+复用。各复跑原有 30 场景，驱动检查数分别为 1,254、1,254、1,255、1,255、1,255；不是新增 150 种场景或游戏成功率。保留同键订阅、leader 取消、两个真实 worker 的同层/异层发布、8 caller/512 请求、TTL 交付、Error、输入/halo/loadIdentity、资源拒绝、关停和输入引用归零控制。

另一个控制 JVM 共 2,066 项驱动记录：两 worker 卡在 before-query，第三个不同查询实际排队。第三 Task 的入队到选择约 35.36ms，选择发生在释放门控之后，三个真实序列互异，两 worker 身份不同。该控制证明测量取到了真实排队区间；不把门控人为等待计入正常性能收益。

生成器另在第 512 个请求人为停顿 20ms，该请求实际迟到约 32.23ms，2048 个计划请求全部保留，计划时钟没有重设，计划到完成观察的延迟确实包含迟到。控制 JVM 退出 0、无超时，关闭状态及 pin 归零。

本轮没有新增实体移动测试。诊断与候选接口回归不继承或重新证明原版实体执行、全部消费者、Boundary/Super 发布或真实 tick 资格。

## 性能协议与统计口径

四模式对象/分块 × 每次捕获/有效 Slot 复用；每模式三个独立 JVM，共十二实际进程。启动顺序、场景顺序、到达率和诊断顺序轮转，不同表示不在同一 JVM 中交错。每 JVM 三场景：平地复用、水域升级后、五种请求条件混合。混合含正/负候选，范围仍为 GROUND、width<=1、heightCells>=2。

每场景预热 8192 个请求，再预热诊断入口；正式每窗口 2048 个唯一完整查询键，每条件两个窗口，诊断启停成对。速率为 2000、8000、32000 请求/秒，另设无节奏的 2048 请求突发。窗口间完全 drain；正式热态均无新增局部行、无同键 joined。水域场景测量已升级后的读取，不能当作首次升级性能。

生成器按单调计划 deadline 主动等待，不等待前一请求结果，不丢迟到请求，不重新设定计划时钟。原始行分别保存计划时刻、API 调用/返回、完成观察、实际入队/选择等。terminalNs 是消费者 whenComplete 回调观察时刻，若 Future 在注册回调前已经完成，观察会稍晚；它不是 Future 内部精确结算时钟。所有模式采用同一观察方式。

P95/P99 使用最近秩 `ceil(n*p)`。六窗口配对变化先逐对计算，再按通常中位数汇总：偶数个值取中央两个的平均；两个聚合分位数之比是另一口径。初版读取器使用上中位数，原脚本和原输出另存为 `analyze-before-review.mjs` 与 `independent-analysis-before-review.json`。最终只重新分析原始记录，不重新制造实验样本，计数保持。

实际负载可比较门槛事先写入 plan：生成器迟到 P95 不超过一个间隔、P99 不超过两个间隔，首末实际发出跨度与计划相差不超过 5%，无资源拒绝，且未观察到其他 Java 重叠。门槛用于解释，所有不合格窗口和请求仍保留。达到门槛只支持本协议内近似负载对照，不能消除系统噪声或证明因果。

读取器的所有配对记录显式携带 `observedInterpretation` 与 `comparisonStatus`：全部计划负载观测始终不是匹配负载因果结论，双方满足门槛的对数另列；零对满足门槛时状态为 `NO_PAIRS_PACING_QUALIFIED`。保留全部观测值的用途是记录反例，不能只凭一个非空百分比登记实现优劣。

十二次启动前清单为空，运行期间 219 次周期抽查未观察到其他 Java；共 231 个检查点。这不是没有其他系统负载的证明。正式窗口仍有 GC 和后台编译，预热不能保证 JIT 已稳定。每模式三个 JVM、六窗不提供统计显著性或置信区间结论。

主动等待本身持续消耗生成器线程的 CPU 时间，可能与两个 worker 争用资源。本轮没有测量独占核占用或隔离核对照，不能断言它是迟到的确定原因；全部速率均保持同协议，并保留负载不匹配边界。

32000/s 关闭诊断时，四模式达到门槛的窗口数，平地为 3/3/4/1，水域为 3/0/4/1，混合为 2/1/2/1，各自总数 6。大量生成器迟到使该速率的聚合尾延迟不能解释为相同实际到达负载下的实现差异。只剩一对达到门槛的合并对照也不提供稳定结论。

明确保留混合 packed-fast、重复 2/窗口 1 的高负载反例：计划 P99=16.54575ms，实际调用到观察 P99=4.6416ms，生成器迟到 P99=16.15695ms；编译时间增量 605ms、GC 时间 1ms。首末发出跨度几乎等于计划仍不能掩盖中途迟到和追赶。分位数不能直接相减分解成本；后台编译/GC 只是同窗观察，不能断言其确定因果。

## 真实队列与诊断扰动

诊断开启的数据用于区间观察，主性能判定使用关闭诊断的窗口。8000/s 分块+复用开启诊断相对关闭的配对 P99 中位变化约为平地 +9.6%、水域 +16.7%、混合 +12.0%；这是含运行波动的成对观测，不是纯诊断指令开销。不能忽略这项扰动，把开启诊断的队列数值原样当作关闭诊断的成本。

以下为已接纳请求的入队到选择 P99，单位微秒；括号中为 query P95。固定速率下排队通常较短，突发则明显累积，仍不以分位数相减归因：

## 用户质疑后的性能解释更正

2026-10-14 用户指出：只报告六对窗口的中位变化，遗漏整体结果；独立重复不足且配对选择未解释，因此不能称为性能退化。接受该批评，撤回“混合场景退化 13.7%”的实现性能判断。上述百分比保留为描述性计算，不作为稳定提升、退化或根因证据。

六对来源为预先安排的三个独立 JVM 重复、每次两个批次，全部纳入，没有事后抽选。每个模式的独立进程重复只有三个；同进程内两批相关，不能视为六个完全独立样本，更不能把 12288 请求视为 12288 次独立实现比较。同重复号/批次号对应不保证相同系统状态，分批比较不具备强匹配实验的证明力度。

同一混合 8000/s 条件下，对象+捕获/分块+复用各 12288 请求、无拒绝。整体计划时刻起算 P95 为 40.9/34.9 微秒，P99 为 151.6/76.8 微秒；整体实际调用起算 P99 为 85.6/58.2 微秒。整体观测指标降低与分批统计波动均须一起报告。本轮性能推论统一为“独立重复不足，无法确认稳定提升或退化”。

每个批次有 2048 个唯一完整查询键，并非单个请求。一个 caller 以 8000/s、125 微秒间隔提交，不等待上一 Future 完成，两个 worker 异步处理，任务可以同时在途。等待须区分计划到实际发出的迟到、真实入队到选择，以及选择后的执行/发布/完成观察。单提交线程不等于一次只有一个未完成请求；唯一键也不等于没有资源竞争。
