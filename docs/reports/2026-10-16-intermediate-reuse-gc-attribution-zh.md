# 行复用 GC 差异归因

日期：2026-10-16。方案：`docs/designs/2026-10-16-intermediate-reuse-gc-attribution-plan-zh.md`。新证据：`.tmp/intermediate-reuse-gc-attribution-20261016/`。

## 判断

**已经缩小问题范围，但没有找到足以宣布原GC门通过的唯一根因。** 新的对称诊断没有复现候选GC暂停增加。固定复杂输入中，候选实际多分配约17.48KiB／256次完整构建。GC时相和自适应堆状态是目前最需要区分的因素，不能断言候选毫无影响。停服期观察到的短引用处理时间，尚不能估计旧请求窗口内缓存弱引用的真实成本。

行复用的局部收益仍有研究价值。原复杂输入JMH完整构建下降53.725%属于已验证的局部结果；目标冷首次Path为何没有改善，尚缺精确的阶段及关键路径证据。此次没有修改缓存算法或生产源码，也没有转向优化其他生产成本。

## 旧结果的时间线

原封存complex数据每侧4独立JVM，GC均值差5.092ms，门为允许增加≤5ms，超门0.092ms。该验收结果保持不变；没有通过扩窗、删样本或改门将失败变为通过。

原窗口内baseline合计1次、packed合计4次年轻代GC。这是事件次数、发生时相和各次暂停时长共同作用的结果，不是“候选每次GC都慢5.092ms”。总暂停和最大暂停两门来自同一批事件，不构成两个独立证据。

| 候选运行 | GC开始距提交 ms | 暂停 ms | 所有实体首Path最晚观测 ms |
| --- | ---: | ---: | ---: |
| packed-r1 | 463.959 | 5.041 | 495.38 |
| packed-r2 | 30937.734 | 9.266 | 515.69 |
| packed-r3 | 15257.189 | 2.811 | 543.40 |
| packed-r4 | 28782.205 | 8.795 | 470.17 |

其中三次GC发生在首次Path之后很久，不能直接解释首次Path未改善。原GC门覆盖约31秒的完整自然旅程，并非只覆盖首次构图。

packed-r1在0.464秒附近的GC仍需优先关联：它与首次Path阶段相邻，现有旧info级日志不能恢复其引用处理或疏散子阶段，不能用其他晚GC代替解释。

baseline-r1/r3/r4窗口内无GC，但在请求窗口末端后约88.69/113.72/96.77ms开始GC。这不是“基线全过程无GC”。不过旧探针在终态后立即停止实体并halt，随后停服保存本身可能触发GC；旧stdout只有秒级时间戳，不能将这些停服期GC重新记入请求窗口，也不能因此认定原窗口错误。初步时间线保留在`original-timeline.json`；精确沿用原窗口公式的复核以`boundary-qc-v1.json`为准。

边界规则与原验收一致：窗口起点为`probe.submitUptimeMs`，末端为该起点加`(max(rows.terminalNanos)-probe.submittedNanos)/1e6`；GC区间为`[打印结束uptime-打印暂停时长, 打印结束uptime]`，先判断相交，再截取交集、求区间并集。对窗口端点与GC端点分别保守扩为±1ms不确定带，最坏相对不确定度2ms，重新要求“之前／完整在内／之后”的归属稳定。8个complex JVM全部根暂停通过，最近任意暂停端点距任意窗口边界仍为88.6929ms；计入次数保持baseline1次、packed4次。因此此次并非暂停被边界裁切造成的差值。

## 新的对称诊断

固定复杂混合场景，AB/BA顺序，4个独立服务器JVM。使用原收尾冻结runtime.jar/probe.jar，SHA一致；真实派发均在场景就绪30秒以后，目标图冷态通过。capture/count/trace均关闭，捕获源数量和逐构建捕获记录均为0。64实体全部自然成功，无whole回退、清理通过；每次请求期任务构建完成数均408。

双方同JDK17、`-Xms256m -Xmx2048m`、JFR配置和详细GC日志。执行采样10ms、分配采样300/s、线程累计分配1秒，另启用GC堆/引用/子阶段事件。实际JFR设置已核对，DataLoss均为0。根据Young GC的相同gcId对齐JFR和统一GC日志，时间残差范围0.81–0.98ms；不直接混用JFR墙钟与uptime的起点。

| 顺序 | 请求窗口GC ms | 派发前最近GC后提交堆 MiB | 同次GC后Eden容量 MiB |
| --- | ---: | ---: | ---: |
| baseline-r1 | 12.250 | 851 | 187.80 |
| packed-r1 | 0 | 1157 | 387.01 |
| packed-r2 | 0 | 1049 | 354 |
| baseline-r2 | 0 | 949 | 275 |

此轮第一对的差异方向反过来了。两次候选均未在请求窗口触发GC，**不能据此宣称GC更快或长期无成本**。这4次是带JFR的归因诊断，不与封存净对照混池，也不替代原16JVM验收。

在相同堆上下限下，派发前的提交堆和Eden容量仍有明显差异。最近一次GC后的容量不等于提交瞬间剩余空间，但表明各JVM不是在相同年轻代状态下开始请求。启动波动可能影响它，候选也可能通过启动工作影响GC时相；这里不能将其一概归为外部噪声。

## 弱引用与额外分配

候选终态后的5次年轻代GC，**整个Reference Processing阶段为0.13–0.23ms**；其中第一次分别0.19/0.19ms，相应整次暂停6.368/5.131ms。两个候选的疏散集合阶段为数毫秒。JFR的引用通知子阶段存在层级嵌套，未重复相加。

这些停服期事件无法重建上一轮窗口内GC的子阶段。若缓存引用对象已晋升，年轻代GC也未必处理相同引用集合；本轮没有逐条证明缓存条目是否被这些GC处理。因此只能报告观察到的引用处理时间，不能把它当作缓存特有成本上限，或据此排除旧窗口内弱引用及候选存活对象的成本。

为避免分配采样漏掉小缓存，另用冻结complex的256次真实构建输入进行精确线程分配计数。baseline/packed/packed/baseline，4独立JVM；每次30轮热身、5批×10轮，完整路径包含清缓存、完整构图、再清缓存，TRACE/COUNT关闭。

一个“256构建回放”指捕获complex轨迹中256次BaseClusterTopology完整构建的整个序列，按捕获worker身份使用各自cache/scratch；每轮前后清空所有worker缓存。每JVM测50轮，即12800次构建，表中除以50后按整个256构建序列计。每侧仅2个独立JVM，批次不是额外独立JVM，不能把5批当成n=5。

| 独立JVM | 每256次完整构建平均分配 B |
| --- | ---: |
| baseline-1 | 744332.00 |
| packed-1 | 762126.56 |
| packed-2 | 762239.84 |
| baseline-2 | 744241.76 |
| baseline均值 | 744286.88 |
| packed均值 | 762183.20 |
| 差值 | +17896.32（17.4769KiB，+2.4045%） |

这是分配累计量，不是实时存活或缓存保留量。输入固定强持，只适合判断局部操作的分配代价，不能代表真实服务器的弱键释放。相较此前强键最坏强持约213.5MB／worker的问题，当前没有发现相同量级的问题；弱键缓存强可达142640B／worker的结论仍引用原独立所有权实验，没有用此次分配数字替换。

约17.48KiB额外分配很小，仍可能在临界堆状态下提前触发一次GC。因此不能用“小”直接豁免原门，也不能由原窗口多一次GC推出额外分配很大。

## 首次Path收益仍待定位

JFR请求窗口分配sample weight约195–209MiB，主线程约144–145MiB；栈包括实体移动、GroundSegmentWindow、任务及导航工作等。它们提示整段旅程的分配来源远大于原始行缓存，但sample weight不是精确字节，更不是CPU时间或首Path关键路径占比。这些生产成本由其他会话研究，此处不修改。

10ms执行采样在本次约0.5秒首次Path窗口中的相关样本很稀疏。不能仅凭出现BoundaryGeometry、Base边生成或GroundSegmentWindow的栈，就声称已证实它们吞掉了行复用收益。

原复杂净对照各JVM首Path中位数的均值为baseline486.899ms、packed489.240ms，候选方向为+0.481%；4对差值为+5.842/+50.378/+51.053/-97.908ms，离散明显。“未证明改善”不等于已排除恶化。原单侧90%筛选上界59.745ms低于原允许上界97.380ms，只是4对且有分布假设的工程筛选，不是无回退证明。

下一步先用双方相同轻量计数确认submit至首Path内确有缓存命中，并关联源、体型及构建；此前整个捕获轨迹的55040次命中不能替代这个时间窗的命中证据。然后成对记录原始行、侵蚀、分量、边/输出阶段，以及完成构图、发布、首Path之间的对应时间。这能回答节省了多少实际冷构图时间、是否落在请求关键路径上。不要为减少几毫秒GC指标盲改弱键容器，也不要继续盲加整个旅程矩阵以争取过门。

## 证据与审核

机器可读结果`results-v1.json`包含4次诊断、4次精确分配、GC时间线、分配栈和身份核对。各运行以`attribution-v3.json`为有效归因输出；开发期早期读取输出不用于结论。封存收尾目录558项、此前targeted目录478项重新逐项SHA核对，均无漂移。

DeepSeek首包4463 UTF-8 bytes，WSL原生dsh headless，provider=deepseek、model=deepseek-v4.1-flash，禁止读文件/工具，900秒本地期限；99.017秒返回ACCEPT_WITH_GATES并列出7项必须先纠正的表述/定义，尚不是最终无修改共识。报告已补充事件次数、近首Path的旧GC、年轻代引用处理局限、首Path方向及离散度、精确分配单位与独立JVM数量，以及下一步首Path窗内命中前提。

首包另将新诊断0.81–0.98ms的JFR/GC对齐残差与旧门超出0.092ms混比。旧门依据GC日志中的暂停时长字段（0.001ms打印分辨率）；旧事件完整落在请求窗口内，没有边界截取。新对齐残差不等于旧暂停时长测量误差，不能据此撤销旧门失败；但这也不消除旧4对样本的统计不确定性。后续复核已接受该纠正。本报告不表示生产接入批准。

第二包3668B，64.705秒返回ACCEPT_WITH_GATES，接受跨时钟误差纠正及其他边界，只要求补窗口归属规则和±1ms不确定带。上述`boundary-qc-v1.json`完成该补充，并复算8次暂停总量与原封存读数一致。

最终自足包3488B，31.837秒返回**ACCEPT_WITH_GATES，本轮必须修改项：无**。双方就本轮事实和推断边界达成共识：没有证明稳定GC回退，GC唯一因果尚未解决；继续当前原型的首Path前命中及阶段关联验证；不盲改缓存、不盲加矩阵、不宣布生产可用。3个包均正常结束，无超时，实际provider/model及配置SHA前后一致。该共识仅批准本轮归因报告及后续研究范围，不豁免原门，也不是生产接入批准。
