## 当前结论

优先保留旧版的连续段合并和原引用账目，先诊断无重复场景和单元素路径成本，
有成本依据后才实施“单元素在原辅助函数入口提前返回”这一最小候选。
不以重新实现遍历器、替换哈希表或扩大生命周期改动作为第一步。
无重复额外成本若不能解释和控制，不靠扩大空气场景收益宣告整体改善。

本轮找到了具体可研究的成本，而没有确定旧版波动的唯一根因，
也没有证明新候选能够稳定提高整次寻路收益。
“固定收益”在这里应落实为：真实工作量减量可解释、
无重复场景的额外成本得到控制、整查询结果在预定验证范围内可复现。
不能承诺每次独立JVM测量都更快。

本轮只有源码和历史数据复核、网络资料、顺序/算术模型及DeepSeek讨论。
没有新的Java实现、Minecraft或JMH测量；旧性能门和封存保持。

## 选定的第一项改法

旧版启用连续段路径后，非空气和孤立空气都以`count=1`进入
`changeFactReferenceRun`。该方法先初始化`supported`，
再检查`count > 1 && supported`；单元素最终进入一次循环的原标量fallback。

最小候选只在原方法入口增加：

```java
if (count == 1) {
    changeFactReferences(facts, idle, active);
    return;
}
```

原遍历器、调用点、标量方法、加权预检和fallback其余部分保持。
不新增字段、元数据、回调类型或长期缓存，不重排任何事实，不改变生命周期。
原方法在fallback循环之后没有其它逻辑；候选仍需真实Java差分验证。
多元素路径会增加一次`count == 1`比较和分支，不能称整个执行路径原样。
单元素进入频率、实际内联后的成本，以及新分支代价，均应先诊断；
如果原主体已被JIT消除，或新增分支吞掉节省，不实施这一候选，也不靠追样争取通过。

该修改仍会调用辅助函数，不能称“删除了16,280次函数调用”。
它绕过单元素情况下的其余函数主体。
`supported`在源码中先初始化，后面的`&&`短路不会倒过来取消该初始化；
但JIT可能已将它重排或消除，因此源级省略不能直接折算CPU。

历史冷首Path的3364次遍历包含50,460槽，合法成功路径合并为：

| 机会 | 历史次数 |
| --- | ---: |
| 多元素空气段应用 | 7750 |
| 单元素应用 | 16280 |
| 合并后应用合计 | 24030 |
| 相比逐槽可少的应用 | 26430 |

最小候选针对16,280次单元素主体，不改变原来的合并省槽数量。
它不能解决完全无重复路径的已观测额外成本：
该路径原本就绕过辅助函数。必须在诊断结论中单独交代这一点。

## 怎样减小波动

第一项诊断针对未修改的基线和旧版，不先增加候选组合。

1. 检查实际调用的内联、编译层级和分配形态，特别是外层分支与捕获lambda。
   诊断日志单独运行，不用带日志的时间判定收益；不预称helper未内联是根因。
2. 观察引用表。独立诊断JVM通过反射读取`IdentityHashMap.table`；
   在runtime原锁内，仅于提交前、结清后两个约定点浅复制表。
   锁外按实际JDK17哈希/步进计算容量、键数、成功探测总数/最大值及空气单例探测长度。
   不重排、不resize、不固定hash种子，不将两张快照冒充精确resize次数。
   空气单例指`PackedFacts.allAir()`返回的唯一对象，以`==`识别；表内没有该键则记录缺失。
   每个JVM单独描述，不把不同JVM中的对象当同键配对，不按探测差额扣CPU或据此认定因果。
3. 反射需诊断用`--add-opens java.base/java.util=ALL-UNNAMED`，
   复制、额外遍历及锁占用都有扰动；所得形状不当作CPU证据或净性能样本。
   诊断与性能轮应核对源码、事实/版本和初态摘要，分别记录诊断flags。
4. 记录电源设置、背景负载及运行顺序；预算和技术无效条件测前固定。
   不修改生产JVM参数来制造收益，不事后删掉有效不利样本，也不将所有变化统称噪声。

IdentityHashMap键的identityHashCode分布在独立JVM间可能不同，
线性探测成本是新的具体检查对象，但现有记录没有表分布证据。
不能据源码事实就认定它造成了无重复场景+7.09%至+15.59%的观测。
如果未取得具体成本依据，不通过随机换布局或增加fork来猜原因。

## 放大收益的备选

### 暂不推进的遍历级支持类型判断

`supported`只读取本次不变的`idle/active`，可在遍历级判断一次；
引用表、旧计数、`delta * count`、long范围/非负检查和更新仍须逐段执行，
fallback后下一段重新查当前值。
两者不能一起提升，也不能缓存前一段的预检结果。

这一较大构想的历史源级判断机会可从24,030次到3364次，
但需要改变签名、捕获或调用形态，当前没有成本依据，不列入待实施方案。
该数值仅保留为模型机会，不能用来为首候选承诺收益。

### 同类别字节桶维护

旧标量即使活动事实仍为活动，也先扣字节、改计数、再加回字节。
可研究仅在标量`changeFactReferences`中保留
`computeIfAbsent → retainedBytes()`各一次的原始顺序，
随后在任何计数/桶写入前以long确认旧/新计数合法且类别同为ACTIVE或同为IDLE时，
只更新真实引用数，字节桶不变。
例如活动引用10到11，引用delta为+1，活动字节桶净delta仍为0。

归零、类别变化、未知或非法状态、溢出全部执行剩余原标量主体；
错误时原本已发生的扣字节和计数变化也须保留。
不引入图级租约、延迟账目或新的所有者含义。
不跳过或重复`retainedBytes()`读取，不吞其潜在异常；
前面的map插入与原标量保持，不将“无写入预检”误称整个方法之前没有map操作。
源方法没有版本/脏标记写入，但实际锁、预算发布和生命周期仍需验证。
首轮不修改`applyFactReferences`批量路径，不将单次同类别条件外推为整段等价。
旧trace没有delta和当时计数，命中率未知；只有profile证明其有实质成本才实现。

### 二元段的成本门槛

历史数据重新按304张图各自遍历次数加权：

| 最小合并段长 | 批处理段数 | 可少的逐槽应用 |
| --- | ---: | ---: |
| 2，现有规则 | 7750 | 26430 |
| 3 | 6372 | 25052 |
| 4 | 4950 | 22208 |

二元段有1378次；提高到3会减少1378次批处理预检，
同时失去1378次逐槽更新减量。两种操作成本不相同，不能仅凭此表选3。
只有二元段被实际诊断为不划算时才单独验证阈值，不做多参数扫样。

## 本轮模型和实现边界

`analyze.mjs`复核原输入哈希及基线/旧版标量源码相等，提取六组完整历史指标。
另做两个独立模型：

- 顺序模型：1至16槽全部bitmask，17至27槽边界及固定随机，
  共241,598构型，逐槽身份和顺序展开一致。
- 同类别算术模型：11,907状态，含7800错误状态，与逐次扣加模型的计数、
  字节、map存在性及异常前缀一致；其中2304例命中守卫。

顺序模型验证的是一个后继专用mask遍历构想：
已有事实序列mask中，`starts = mask & (mask >>> 1) & ~(mask << 1)`标识至少二元段起点；
每次先执行当前段前的普通槽，再该段，循环。
它不是空间halo掩码，不跨非空气重排，也不合并内容相同但对象不同的事实。
考虑实施范围，最终不把它作为首项候选。

两模型都不是实际Java实现、并发证明、命中率或性能测试。
不把241,598或11,907的模型数量写成生产断言通过数。
`histogram.mjs`只复算历史段长，不新增路线或CPU数据。

## 后继验证顺序

先作上述成本诊断，有成本依据后才实现最小候选，再验证真实方法的完整失败前缀、计数、
对象身份、异常传播及生命周期；有意义时复用受影响的原有契约。
通过后以完整API的空气、无重复和混合场景作成本筛选。
旧API不包含冷宏观请求，不能据它直接接入。

最终必须观察实际worker宏观查询的CPU与首Path，并列分配、GC、tick、
构建/扩展工作量和正确性。初态核对缓存键与版本摘要，不能只比条目数。
如果工作量不同，应先说明差异而非将全部差额计作引用优化效果。
采样、实际收益目标、控制场景代价和停止预算在测量前定义；
不修改历史10%门、不事后用A/A抵扣、不仅报最有利指标。
当前没有执行这些后继诊断或性能测试。

## DeepSeek讨论

首包6678B，40.399秒`REQUEST_CHANGES`：
采纳其将首项收窄为单元素提前返回的建议，专用遍历器改为研究备选。
其把纯delta类型判断与逐段状态预检混淆、把顺序执行误读成全局重排，
已提供源码和步骤澄清，没有将这些判断直接当作技术结论。

第二包4665B，33.688秒，首行为`ACCEPT_SCOPED`但仍列必须修改项，
因此不算最终共识。继续以完整方法澄清Java布尔初始化与后续短路的区别、
辅助函数调用仍存在、引用delta非零但同类别字节净delta为零，
并固定反射表形状诊断的采样方式和扰动限定。

第三包5251B，145.161秒`REQUEST_CHANGES`：
已澄清纯类型判断、Java初始化和同类别桶的数学关系；
同时采纳新增分支须计成本、支持类型提升不列待实施、
字节桶保留原读取且仅限scalar、固定表诊断定义等收窄意见。
其“探测只能同JVM描述”在本轮按保守范围执行，不将不同对象的形状差异作因果配对。

最终3541B收窄包25.043秒正常返回`ACCEPT_SCOPED`，
本轮必须修改项无。已完整阅读回答，认可范围仅为本轮研究取舍：
诊断先行、按成本决定最小候选，字节桶仅限有证据后的独立标量备选，
不宣称固定收益、不接入生产、新图级聚合继续停止。
