## 原型边界

新增源码与证据位于 `.tmp/derived-topology-async-20261013/`。`async-v4/sources/` 是本轮正式编译输入的冻结副本，`source-identities.json` 绑定源码。此前 v1/v2/v3 和种子运行均保留，不能混入正式计数。

v4 是服务器对照的冻结版本；v5 是审核后修订的安全性版本，源码另冻结在 `async-v5/sources/`。不得把 v4 的性能数字改称 v5 的完整性能验证。

复用第一阶段完整 Base 编码器，保留标签、组件元数据、CSR、能力位、float 原始位、halo 与 boundary offsets。恢复时重绑当前事实，当前进程重新计算 signature，不复用跨进程内存身份。新增显式 world namespace，仍绑定精确 GeometryKey、维度、section、算法/格式版本，以及全部 27 槽事实存在性、版本、指纹与内容摘要。

本轮 Runtime 仍为独立副本。它在事实准备好后捕获不可变输入与 stamps，将读取交给独立 I/O 执行器；等待读取不占构建 permit。命中后经既有 publish 检查，未命中回到原有单 permit Base 构建。回调检查 demand 身份、当前 stamps 和停止状态。读尝试代次使已取消、卸载或替换的迟到结果不能再次发布。

optional halo 的非 AVAILABLE/UNLOADED 状态保守跳过缓存，保持原来的正常构建或基础事实失败语义；不能把 PENDING 或 RECOVERY_FAILED 编码成已卸载。恢复不是详细可行性证明，宏观候选仍交给真实原版搜索。

## 资源与所有权

- 2 个独立 I/O worker；总接纳请求数包括执行和排队，最多 8。资源不足返回缓存未命中或跳过写入，不拒绝正常 Base 图。
- 原型 reservation 总额最多 16MiB，包含输入引用、图引用及读取/解码/编码的保守暂存份额；v5 增加事实摘要临时序列化的份额，覆盖解码/编码中再次算 key 的暂存。文件头检查先于载荷分配。此处是软件 reservation 口径，不是 JVM 实测堆硬上限，也没有声称涵盖目录索引或所有对象头。
- 单条原始、压缩载荷各最多 8MiB；每 root 成品 `.bin` 留存最多 128MiB，写入前淘汰旧条目。临时文件不属于成品额度。
- 同完整输入 key 的在途读取共享磁盘字节；各订阅分别解码并重绑自己当前的 boundaryFacts。Runtime 本身继续合并同一图需求。
- 同 key 写入去重，文件名是完整输入摘要。旧输入写与新输入写落到不同文件，不覆盖当前输入记录。
- 读取的 Runtime pin 由读尝试或正常发布/取消负责释放；写快照另持 Runtime pin，缓存 future 完成后释放。执行中超时的 Java 输入引用与 reservation 继续计入 I/O，直到 worker 实际退出；不会把仍执行的工作提前扣成零。
- `owner.lock` 用文件锁拒绝第二所有者。只清理专用 root 内符合缓存命名格式的临时文件，保留外来文件。世界 namespace 由实验启动配置提供，生产世界生命周期的自动分配尚未接入。

写入采用同目录独立临时文件、文件 force 和 ATOMIC_MOVE。缓存明确可丢弃：没有目录 fsync 的跨平台持久承诺，不宣称掉电后一定存在；失败、坏文件、丢失或原子提交不可用时必须正常未命中。进程崩溃测试不能替代机器掉电测试。

## 正确性验证

v4 运行在 `async-v4/`；v5 安全修订运行在 `async-v5/`。各为一个种子 JVM、一个主动 `halt(73)` 的崩溃 JVM、一个恢复 JVM；正常进程退出 0，崩溃进程按预期退出 73。

v4 种子 49、恢复 84 项断言通过。最终 v4 二进制与服务器读取器完成 636 项核对，包含 196 份冻结世界派生记录的文件名/输入摘要、载荷摘要、组件、元数据、CSR、能力位、float 和 halo/boundary 结构。初期 core 读取器曾报告 311 项；进入 v5 后按版本分开身份核对，修订说明保存在 `reader-version-binding.md`，原始样本没有修改。

v5 种子 49、恢复 93 项断言通过，原独立读取器 117 项核对通过；补同 key 提交挂点与超时订阅控制后，聚焦读取器 141 项核对通过。恢复测试 I/O 在途峰值为 8，reservation 峰值 767,796B。新增 leader/共享订阅超时后迟到读取的额度释放，以及已有文件和磁盘容量不足的写入跳过计数。

审核提出 leader 读取尚未登记额度时，最后一个 follower 超时可能把 users 扣到零。代码中 producer 自身在整个 read 期间也占一份 users；订阅超时不等于 Job 已退出。`v4-owner-control/` 直接运行冻结 v4：两个订阅超时、follower 退出后，producer 仍有 1 个在途请求、12,360B 输入额度；迟到物理读结束后全部归零。因此没有复现该描述的永久泄漏，不能把它登记为已确认的运行错误。

v5 将 flight 额度登记与 users 释放放在同一 monitor 内，清零已释放的额度，减少维护时的归属歧义；增加 `existingWriteSkips`/`oversizedWriteSkips`，并补事实散列暂存额度。原 v4 与新 v5 的反例及源码均保留。

补充控制直接加载冻结 v5，不改其源码或发行包：

- `v5-write-control-r2/`：J1 在已 force 的 `write-temporary` 挂点持有 `diskLock`；J2 同 key 写入的线程栈为 BLOCKED，位于 `initialize`，锁 owner 为 J1，此时 requests=2、writes=0。释放后只有一次提交，J2 计入已有文件跳过；随后重写再次跳过，文件字节不变，关闭归零。此路径证明提交被串行化，不能把它称为 `joinedWrites` 命中；后者另由完整 Probe 的 `write-encoded` 挂点断言验证。
- `v5-late-control/`：两个订阅都超时后，producer 仍有 1 个在途请求、119,144B 总 reservation，其中输入引用为 12,360B；迟到实际读取后归零。另一路径先让 leader 订阅超时，再加入仍有效 follower；一次物理读取交付 follower，并直接断言其 center 事实身份，最终全部归零。
- 完整 `AsyncPersistenceProbe.resources` 原本就直接比较两个恢复图的 center 事实分别等于各自输入，且一次物理读取供两个订阅。上轮送审摘录漏了这些断言，本轮补送完整程序。

初次 `v5-write-control/` 控制错误预期 J2 应立即合并返回，实际先阻塞在 `initialize` 的同一 `diskLock`，控制程序 get 超时退出 1。原件保留并排除；修正的是控制预期，没有修改冻结实现。

正确性测试没有启动原版详细搜索；不能将这些断言或宏观成功当成实体到达证据。

## 真实服务器对照方法

使用标准 Forge 1.20.1-47.3.0 发行启动、Java 17.0.18，清空 MOD_CLASSES 与 MCP_MAPPINGS。原发行包冻结后只替换独立 Runtime、加入缓存和驱动类及实验 mod 元数据；发行包核对确认 Scheduler 字节码和所有其他原有条目未变。两组使用完全相同的原型发行包。

固定场景是种子 20261013 的平地世界，16 块区域、一半有固定墙体；成年尸壳无自主 Goal、禁止实体推挤，原移动速度与原寻路参数。每条目标直线距离 32 格，最多 512 个不同起点。该场景不是城市路线资格测试。

初次世界形成、事实和派生记录落盘的种子运行，以及一次重启准备运行，独立保留。正式矩阵每个 JVM 从 `server-prepare-v4/world` 的同一个冻结副本复制：

1. facts 组删除自身隔离副本的派生目录并禁用缓存，仅保留事实存储。
2. derived 组保留事实与派生目录，并启用缓存。
3. 每个新 JVM 只执行一个首次导航 burst，分别取 1/128/256/512 请求。
4. 每组五个 JVM；反转重复中的并发顺序，并交换 facts/derived 的先后。
5. 两组均保持 4ms/tick 固定共享软预算，第 21 tick 提交，显式检查预算 refill/cap 常量。

这是新 JVM 重启后固定准备窗口的对照。没有清空 OS 文件缓存，不能称物理磁盘冷读；现有后台预热仍运行，不能称 RAM 派生图在提交瞬间为空。提交前的图、I/O、事实恢复和阶段计数也保存，避免把提前准备的成本隐藏在计时外。

记录真实首次 Path、实际最终到达与终态、完整服务器 tickTimes、进程耗时、事实恢复、Base 排队/构建/缓存等待与发布累计/最大耗时、逻辑 I/O 字节、输入/解码 reservation、堆和可观测线程分配。阶段诊断目前是 count/total/max，不能冒充每次阶段的 P50/P95；分配是线程计数差值，不是严格全进程分配剖析。
