## 已确认的生产缺陷

当前存在“同版本重复恢复被跳过，但持久化等待标志已经置位”的状态缺口：

1. 帧末扫描已经完成当前版本的发布和持久化；旧恢复任务仍在队列中。
2. 旧恢复任务再次扫描，调用 [TopologyService.writeFull](D:/Workspace/AcceleratedNavigation-forge-1.20.1/src/main/java/com/scarasol/acceleratednavigation/topology/TopologyService.java:869)，先设置 `persistencePending=true`。
3. [TopologyWorkerRuntime.publishSection](D:/Workspace/AcceleratedNavigation-forge-1.20.1/src/main/java/com/scarasol/acceleratednavigation/topology/TopologyWorkerRuntime.java:446) 发现没有待处理事件，加载身份、版本、状态及完整事实相同，在 `sectionEventAlreadyApplied` 分支直接返回。这个判断不考虑新调用的持久化责任。
4. 没有新持久化decision，也没有相应完成回调，Service标志留为true，尽管实际没有写入任务。
5. 基础事实被缓存淘汰后，Runtime将其置为PENDING。前台需要它时通知Service恢复，但 [readPersisted](D:/Workspace/AcceleratedNavigation-forge-1.20.1/src/main/java/com/scarasol/acceleratednavigation/topology/TopologyService.java:472) 被这个标志挡住。
6. Service在正需求变化时尝试读取一次；没有持续轮询或能清理这个残留标志的后续动作。构图和搜索任务不提交，工作线程进入队列等待。
7. 区块卸载移除旧LoadedSection；重新加载创建新状态对象，标志默认false，能够重新读取。这解释了为什么重载可能恢复。

这条缺陷已经有前一轮受控运行证据，**本轮没有为它重跑原型**：

- 两个基线进程各96个受控重叠操作，Runtime/Store已经收尾后，96个全部仍留下该标志；合计192个。
- 减少采样候选同样192个残留；复用完成恢复候选192个均无残留。
- 本轮逐差异核对：旧受控Service相对当前生产只有观察计数/计时和临时宿主适配，相关状态逻辑未变；受控Runtime源与当前生产逐字相同。
- 该旧证据只证明标志残留。旧测试没有做“随后淘汰并再次磁盘读取”的完整请求，因此不能把192个写成192次真实寻路挂起。

来源为 [复用恢复原型报告](D:/Workspace/AcceleratedNavigation-forge-1.20.1/docs/reports/2026-10-11-scan-reuse-prototype-validation-zh.md:216) 及其原始jsonl。本轮差异保存在 `previous-controlled-service.diff`。

**确定性分层：生产状态缺陷已经确认；它是这次现场异常的最强候选，但还没有某个等待区段的现场状态快照，不能声称两个请求都被唯一证明由它导致。**

## 同一等待链的其他核对结果

| 核对关系 | 结果及支持边界 |
|---|---|
| 合法写入期间的读取需求 | `readPersisted`同样会因真正的持久化在途而提前返回；`persistenceApplied`清标志后没有根据现有前台等待需求重新尝试读取。若Runtime完成写入后先淘汰事实，恢复需求在Service清标志前到达，就存在失去重试触发的时序风险。本轮源码确认缺少恢复动作，未做该完整交错的运行复现，不将其冒称现场确定原因 |
| 淘汰后的当前性 | `ClusterEntry.current()`比较加载身份、版本及不可用终态，不要求Runtime本地factState等于LatestFacts状态。正常缓存淘汰不会单凭AVAILABLE→PENDING使前台通知被这一判断挡住；先前关于这里可能存在另一个挂点的疑问已排除 |
| 依赖范围 | 默认地面图仍会在构图前等待已加载的所需邻区事实，包括边界几何输入。任何一个事实阻塞都会阻止构图提交。这里的额外邻区不是本轮新增；本轮没有再次扩大依赖或关闭碰撞检查 |
| 预热与前台 | 前台接管已有预热需求会释放预热名额、提高优先级，并重新准备事实。已有宏观请求会阻止继续准入新的预热。不能把长窗口的空队列等待归为“预热任务占满两个线程” |
| 真正开始构图 | `beginBuild`再次检查事实，输入未齐就返回等待；输入齐全才持有事实并构图。因此日志的端到端时间会很长，而采样没有构图热点 |
| 正常读写完成 | Store读入与写入有明确完成future和Service/Runtime消费者；全会话读/写失败均0，没有未处理工作线程异常日志。没有证据支持I/O线程死亡或持续写盘阻塞了整个异常窗口 |
| 世界陈旧失败 | 本轮worker陈旧结果4、自动重试2、耗尽2；Service最终校验拒绝0。两次陈旧失败来自worker依赖身份链，不能说是最终发布校验误报。卸载本身能使身份变化，另一条请求涉及哪个具体身份变化没有逐请求记录 |
| 区块不可用失败 | `UNAVAILABLE_CHUNK`不同于事实恢复失败、持久化不可用。它可能来自端点缺失，也可能来自搜索探索的不可用边界；不能从这一文案推断两端所在区块一定未加载。日志未输出已有的blockedSection，四次失败尚不能逐次绑定到具体区段 |
| 取消、卸载与关闭 | 取消释放端点/搜索消费者和事实需求；卸载清Service加载状态，Runtime发布UNLOADED并使相关等待终止；最终请求、队列、写回执和活动引用归零。这证明关闭收尾有效，不证明此前请求及时完成 |
