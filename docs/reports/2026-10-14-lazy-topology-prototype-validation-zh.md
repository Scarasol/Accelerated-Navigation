# 派生拓扑懒惰升级三个问题的原型验证

日期：2026-10-14。状态：**取得有限范围的原型证据，整体方案未通过认证；未送审，未接入生产。**

用户授权验证三个问题：能力逐项增强能否复用连接，基础图断开时能否局部升级，共享能否减少工作和内存。本轮使用 [研究草案](../designs/2026-10-14-derived-topology-lazy-upgrade-research-plan-zh.md) 界定问题；[原版详细寻路现行契约](../designs/2026-10-13-native-detail-navigation-contract-zh.md) 保持。没有修改生产代码、动态预算、原版搜索参数、游戏世界或共享构建输出，没有调用 DeepSeek，没有提交或推送。

## 1. 判定

| 问题 | 本轮判定 | 证据与边界 |
| --- | --- | --- |
| 能力逐项增强能否直接继承原图 | **通用关系不成立** | 当前构图启用开门能力会移除部分门上方的支撑位置。42 个事实样本、24 个 GeometryKey、6,930 个比较对中，72 对丢失旧可用锚点；反例保留。 |

## 3. 问题一：能力复用关系

### 3.1 比较内容

24 个 GeometryKey 来自六组宽高与门/流体标志的组合，包含精确小体型、整数尺寸、偶数尺寸、较大体型及 1×1 的离散尺寸情况。以宽高要求不增加、权限不减少确定比较方向，始终保持 GROUND 类型和相同事实输入。

比较分三层：

1. 旧可用锚点在增强后的图中是否仍有组件标签。
2. 未丢失锚点的比较对，旧组件内部和有向边连接在增强后的图中是否仍可达。
3. 同一 GeometryKey 的边能力掩码，对台阶/跳跃/落差的逐项增强是否仍支持；独立读取器另外检查跨 GeometryKey 下所有 30 个 MovementKey。

生产图导出为 1,008 份二进制记录，包含逐格组件标签、CSR 和能力掩码。Node 读取器自行解析、检查结构并重算比较关系与候选可达性，不只读取 Java 的 passed 字段。

| 计数 | 正式结果 |
| --- | ---: |
| 事实样本 / GeometryKey | 42 / 24 |
| 逐项可比较的图对 | 6,930 |
| 丢失旧锚点的比较对 | 72 |
| 在各比较对中累加的丢失锚点 | 96 |
| 未丢锚点比较对的旧有向边检查，最大移动组合 | 47,192，失败 0 |
| 同图移动能力增强检查 | 1,159,860，失败 0 |
| 未丢锚点比较对的跨 GeometryKey / MovementKey 有向边检查 | 737,863，失败 0 |

96 是跨比较对的累计计数，不是 96 个独立位置。72 个失败对均来自门相关样本；在其余所测样本中没有发现锚点或连接丢失。这是有限样本结果，不是对任意世界、体型或 NodeEvaluator 的证明。

### 3.2 保留的反例

`standing-above-openable-door` 的 `(8,1,7)`，精确体型宽 0.6、高 1.95，其他条件不变：

- `canOpenDoors=false`：生产图该位置的组件为 0。
- `canOpenDoors=true`：生产图该位置没有组件，标签为 -1。

源码原因在 `BuildInput.groundOpen`：启用开门处理后，下方为门的情况返回 false。当前算法会把可打开的门作为失去支撑的情形处理，因此“能力权限增加”没有在当前图中纯粹表现为增加候选连接。

这个反例说明**当前表达不能直接采用通用继承假设**，不否定实体具有更多可选动作时可以保留原动作的概念。是否通过状态条件、替代连接或其他表示保留门上的原连接，需要后续研究；不能直接合并门打开/关闭条件，批准一条没有一致状态的路线。本轮没有修改此生产行为。

后续局部原型采用保守范围：有门事实且 GeometryKey 改变时，不直接继承基础图；按目标条件局部生成。这条限制由原型检查输入事实以选择研究算法，未接入真实寻路的前置资格过滤。

## 4. 问题二：没有基础路线时的升级

### 4.1 实际实现

初始基准为宽 2.4、高 2.7、陆地、不开门的 GROUND 图；研究视图采用固定格内锚点身份，保存基础出边及目标条件下的增量。

`LocalKernel` 按需计算单个锚点及所需空间检查，复用冻结的 `BuildInput.volumeOpen/groundOpen/doorMoveOpen`、边能力函数及原 `movementEnvelopeOpen`。不先生成完整目标图再把它当作“局部升级”。

局部实现支持 GROUND 且 `heightCells>=2`。在 42 个样本、5 个条件下，局部可用位置与 prism 位逐项对比完整生产生成的位图：共 1,774,080 项位置/条件核对一致。1×1 的特殊移除分支只在问题一中检查，未纳入局部内核。

搜索先用已有且可复用的连接；没有候选时，从起点及搜索前沿逐步生成目标出边。单次最多评估 4,096 个源锚点；零升级额度时返回 `UPGRADE_BUDGET_EXHAUSTED`，不能当作实际原版无路。基础图本身已经完整的失败请求无需再次局部烘焙。

`newlyEvaluatedRows` 是生成出边的源锚点数，不是全部碰撞检查数。生成一行还可能检查目标锚点、中间 prism、邻区事实及多个移动候选，这些另有计数，不能把“100 行”说成只检查 100 格。

### 4.2 主要场景

| 场景 | 已有候选 | 第一次局部评估出边的源锚点 | 结果 |
| --- | --- | ---: | --- |
| 窄缺口连接两侧区域 | 无 | 100 | 小体型取得候选 |
| 水域是唯一连接 | 无 | 100 | 允许走水的条件取得候选 |
| 低顶连接 | 无 | 109 | 较低体型取得候选 |
| 宽缺口 | 有 | 0 | 直接复用 |
| 台阶 | 有 | 0 | 使用已有能力掩码 |
| 三格落差 | 无 | 106 | 相应落差条件取得候选 |
| 两格缺口跳跃 | 无 | 89 | 相应跳跃条件取得候选 |
| 全跨度可开门 | 无，不采用通用继承 | 100 | 目标条件局部生成候选 |
| 全跨度不可开门 | 无，不采用通用继承 | 128 | 没有宏观候选，与生产图一致 |

另有细门板样本：当前生产宏观图在测试条件下有候选，局部图给出相同结果。不能把这个结果称为实际穿过锁门；原型没有真实 NodeEvaluator 或实体执行。

初始没有基础路线的三个主要样本都跑通了前沿升级。窄缺口中起点本身落在基础图没有表示的位置，也能够按实际小体型发现；不是等待一条已有路线出现才升级。

完成升级后，重复请求没有新增出边生成。在无门、可比较的条件下，小体型已有增量还能被具有额外流体权限的请求复用，未再次创建该体型的局部层。8 个成本场景的平地请求中，48 次查询、4 个目标条件全部使用已有陆地候选，没有触发水域或小体型烘焙。

### 4.3 方向、未知与边界

较弱 MovementKey 的查询与完整生产图对照，失败不删除已存在的较强能力候选；宽矮与窄高条件不能拼接成未经生成的宽高组合。

两个相邻 section 的示例分别升级局部端点，再调用实际 `BoundaryGeometry` 检查桥接：大体型边界不通，小体型边界可形成候选；西侧和东侧分别评估 170、103 行。移除所需 halo 后桥接不能交付。

这个边界示例是两个局部搜索加真实边界几何检查，没有替换或验证现有 Super、跨 section 连接发布和 Runtime 流程。12 类局部样本另有 768 次固定随机的端点/MovementKey 比较，与完整生产图结果一致。

本轮所有“候选成功”只表示宏观结构连接。真实 Path、partial、最终 accuracy 到达、Goal/Brain/POI 生命周期与并发输入失效均不在本轮认证范围内。

## 5. 问题三：工作量与空间

### 5.1 对照

成本场景为平地、窄/宽缺口、水域连接、低顶及三个固定随机布局。每个场景 48 次请求，对应 4 个精确 GeometryKey，各重复 12 次。已有生产控制对每个唯一条件只构图一次，后续请求复用，**没有使用逐请求重复构图的人为劣化控制**。

三种表示分别测量：

1. 当前生产的紧凑组件图，按精确 GeometryKey 缓存。
2. 全量锚点出边图，每个条件都完整生成。
3. 锚点基础图加局部增量。本原型同时保留一份基准组件图用于候选位置查询，其成本计入留存。

内存由 JVM Instrumentation 的实际对象大小与身份去重遍历得到；排除共同的不可变事实/原始 BuildInput 及一个公共 BuildScratch，公共 scratch 单独测量为 886,224B。各图自行创建的边界输入引用、索引、能力层、数组和缓存计入其对象遍历。没有用几个数组长度的估算来替代所有对象留存。

这是受控拥有对象的留存大小，不是全进程峰值堆。8 个场景数值相加是比较口径，不表示测试进程同时保有它们。也未测磁盘格式或压缩后的共享记录大小。

### 5.2 留存结果

单位为 B；三个正式 JVM 的确定性大小相同。

| 场景 | 当前紧凑组件图 | 全量锚点图 | 懒惰基础＋增量 |
| --- | ---: | ---: | ---: |
| 平地 | 4,120 | 243,696 | 53,440 |
| 窄缺口 | 5,176 | 218,480 | 90,800 |
| 宽缺口 | 4,120 | 222,656 | 44,592 |
| 水域连接 | 5,704 | 218,224 | 115,952 |
| 低顶 | 4,648 | 228,368 | 64,480 |
| 固定布局 0 | 6,528 | 156,904 | 88,472 |
| 固定布局 1 | 5,288 | 152,216 | 46,744 |
| 固定布局 2 | 6,344 | 157,408 | 76,704 |
| 合计 | **41,928** | **1,597,952** | **581,184** |

懒惰表示小于完整锚点表示，但远大于当前生产压缩组件图。格内节点、出边数组、各能力的检查缓存和增量索引，使它失去当前组件压缩的主要空间优势。不能只与全量锚点图比较后宣称项目节省内存。

### 5.3 工作与时间

| 工作计数，8 个场景合计 | 全量锚点控制 | 懒惰表示 |
| --- | ---: | ---: |
| 生成的出边行 | 131,072 | 基础 32,768＋局部 1,278＝34,046 |

在相同锚点内核下，源出边生成减少约 74.02%，可用陆地路线及已完成升级被复用。这个计数不能直接换算为生产构图次数或 CPU 减少 74.02%：生产组件图的算法和压缩过程不同，原型还需要基础图构建、前沿搜索、索引、临时合并与查询缓冲区。

三种控制均记录实际构图和候选查询耗时，以及可观测主线程分配。所测场景中懒惰表示的诊断总时间没有优于紧凑生产控制；完整原始数字在各 `lazy-results.json`，不将减少行数登记为提速。

只有三个 JVM 的诊断，每个内部的控制顺序未平衡，JIT/GC 影响未严格控制；没有 Forge 服务器、固定 tick 首次 Path 或物理冷读实验。因此没有生产性能认证。

## 7. 当前检查点

三个问题已有首轮原型结果，**整体方向尚未通过认证**。局部升级值得继续研究，但需要先解决两个阻断点：
