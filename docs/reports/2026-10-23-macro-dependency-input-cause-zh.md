# 宏观通道变化的依赖交付输入定位

日期：2026-10-23。承接用户“算法未改，输入固定就不应改变输出”的质疑，
以及“那你继续找呀”的定位要求。本轮没有修改选路规则。
证据目录：`.tmp/macro-input-cause-20261023-v1/`。

## 1. 结论及边界

已定位并通过单变量回放证明：
**依赖在哪一批续行前交付，是当前宏观搜索的有效输入。
静态图、节点身份、起终点、启发值与算法固定，
只改变一条边界连接的交付批次，就足以改变等结构代价的组件通道。**

因此“没有随机调用”和“显式起终点及地图相同”不足以保证当前运行方式输出相同。
固定完整记录后，未修改的原NT宏观算法36次回放均复现对应结果；
没有证据表明算法在完整输入固定后自行随机改变输出。

这证明了具体机制，不等于旧版全部性能差异已经归因：

- 尚未恢复旧十条秒级延后请求的完整依赖交付记录。
- 尚未证明NT节点计时修复就是旧依赖批次变化的原因。
- 不把本轮诊断计时当性能收益，不宣称旧1.50～1.81秒全部由该机制造成。
- 不据此宣布宏观质量回退，或立即更换宏观算法。

本报告补充[输入与因果边界修正](2026-10-23-route-choice-input-boundary-correction-zh.md)。
旧报告、历史性能及原封存证据保持。

## 2. “南北绕行”属于哪一层

用户指出，如果只是在同一通道中绕一个台阶，应该由详细寻路处理。
这个层级划分成立；前文“台阶南北侧”的说法容易把两层混在一起。

本项目宏观层不是只返回“连通/不连通”，而是返回一串组件及其连接。
同一个section也可以有多个连通组件；宏观结果会指定经过哪一个组件、
跨哪一条section边界，详细层再按该通道构造目标集合及逐格路径。

本次台阶路线的两条组件链如下，省略精确首尾端点：

| 路线 | 宏观组件链，格式为section/组件号 |
| --- | --- |
| 南侧 | `(2,5,-9)/0 → (1,5,-9)/1 → (1,5,-10)/0 → (1,5,-9)/0 → (0,5,-9)/0` |
| 北侧 | `(2,5,-9)/0 → (1,5,-9)/1 → (1,5,-8)/0 → (1,5,-9)/0 → (0,5,-9)/0` |

差别是经过`(1,5,-10)`还是`(1,5,-8)`，不是在固定组件通道里选某个台阶方块。
两条链在宏观结构度量下均为4，实际交接坐标和行走距离仍可能不同。
这里的4不等于四个方块，也不证明实际行走成本相同。

## 3. 最小补证范围

历史性能矩阵、NS/NT结果继续复用；没有重跑基线或原六场性能矩阵。
仅因旧记录缺完整输入，复制冻结NT为只读观测副本ND，
增加三个文件范围内的诊断记录：

- `MacroSearch`：构造参数、启发值、每次step/pop/展开、依赖通知和结果。
- `TopologyWorkerRuntime`：请求/共享/缓存来源、查询关联、拓扑及边界交付。
- 新`MacroInputTrace`：保存完整已捕获拓扑内容及事件，退出时输出JSON。

观测不写图、队列、成本、路径或计时器；但新增锁、分配和保留对象，
会影响执行时序，所以这两场不作性能比较。
生产、默认包、原NS/NT源码和生产区既有脏改保持。

沿用原工具、接口、模板、路线、30秒门及负载参数：
`pressure28-n128`，35ms均值、5ms标准差、seed20261021，
原TRACE日志开关、NoTrace，不启JFR。

第一场台阶通道均走南侧，缺少完整输入对照，
因此仅再补一次同场景；未扩展实体数、距离或压力矩阵。
两场均128/128到达、正常退出和清理，原analyzer通过，无外部Java干扰。
输入观测均无error/overflow；每场焦点范围6次物理搜索、
16个请求、10个共享跟随者、0次已完成缓存命中。

## 4. 实际运行中的输入分叉

两场查询30对应同一个代表请求：
实际起点`(19,81,-85)`，终点`(19,81,-113)`。
生产普通宏观搜索使用反向图，所以搜索记录的首尾顺序与实际请求相反。
两场能力参数、起终组件、weight1.25、slack1及节点上限相同，
均未进入层级或精炼分支。

两场查询捕获的共同18份Base和24份边界内容逐项相同。
Base比较包含revision、source fingerprint、geometry、4096格组件标签、
组件metadata、局部边/能力/成本及halo；仅排除跨JVM不稳定的signatureHex。
边界比较包含组件边、成本、band、descriptor、capability及全部位图。

第二场还探索了额外区域；这里没有声称捕获整张世界图或全部未访问邻接。

明确不同的一项输入为：
`BASE_BOUNDARY (1,5,-7) → (1,5,-8), NORTH`。
第一场在第7批available交付，第二场在第4批交付，
两场随后选出的等代价通道不同。
批次指该查询实际收到的available调用，不是全局tick编号。

第4批以后，第一场先经西侧组件建立到`(0,5,-7)/0`的前驱，
第二场已经能够经`(1,5,-7)/0`建立前驱。
后续同代价路径不会替换既有前驱，最终保留了不同通道。
这里没有把边界列表排列差异或跨进程签名数值当作地形变化。

## 5. 原算法回放与单变量核验

回放使用冻结`build-NT-final/build/classes/java/main`中的原始MacroSearch class，
不是ND诊断版算法。两份输入各6次搜索，每份重复3次，共36次，
均复现原路径端点序列、结构成本、展开次序和展开part状态。

随后从同一份已观测数据构造按part提供邻接的只读回放图。
原始调度下逐次核对所有边的ID/目标/成本/次序、依赖/part/次序、
completed/skipped mask及最终通道，全部匹配实际记录。
未观测到完整响应的part一旦被要求完成，回放直接报错，
不将已观察边并集冒充完整世界图，不补造邻接。

在这个固定图上做两项单变量核验：

| 查询 | 唯一变化 | 结果 |
| --- | --- | --- |
| 30 | 上述北向边界从第7批提前至第4批 | 中间通道由`(1,5,-8)→(0,5,-8)→(0,5,-7)`变为`(1,5,-8)→(1,5,-7)→(0,5,-7)` |
| 8，台阶 | `BASE_BOUNDARY (1,5,-10)→(1,5,-9), SOUTH`从第4批延至第5批 | 上表南侧通道改为北侧通道 |

两项各重复3对，全部稳定改变通道，成本均保持4。
节点ID、静态已知邻接/成本、启发值、起终点、搜索预算与原算法保持，
没有使用墙钟延时、随机数或新评分。
查询8直接复现了用户关心的南北宏观通道选择机制。

回放范围是搜索通道几何与状态机。
边界transition payload在搜索中只用于最终物化，不参与g/h/f或前驱更新；
回放以局部描述替代该payload，不验证最终BoundaryTransition位图、
详细寻路结果、碰撞和实际到达时间。
实际游戏的边界完整内容另由JSON快照保存和比较。

## 6. 源码如何产生这个结果

1. `runWorkerSlice`只消费本次续行前已经解析好的依赖，
   attach之后通知`dependenciesAvailable`，再调用`stepSearch`。
2. 缺部分边界的节点仍可以先展开其他已就绪部分。
   `shouldWaitForTopology`按待定/就绪f和slack决定是否继续，
   不要求所有可竞争通道的边同时就绪后才搜索。
3. 原生BinaryHeap按f处理待搜索节点；`MacroSearch.expand`中，
   `nextCost >= next.g`直接跳过，同g路径不替换已有前驱。
4. 因而某条边早一批可用，可能改变哪一条同g路径先登记前驱。
   后续另一条边补齐，并不使同代价通道重新择优。

不是“算法输入完全固定却无故改变结果”，
而是当前可消费邻接和依赖通知批次尚未固定。
对本轮两个受控核验，这一项已足以产生结果差异。
至于两次实际JVM中worker为何恰在不同批次完成，
本轮没有进一步把它唯一拆成JIT、线程调度或某项业务操作的占比。

## 7. 后续判断

当前先保留因果边界：能够继续研究等代价结果对交付时序的敏感性，
但不能直接恢复“宏观选路质量是NT回退根因”的结论。
如果后续处理，应先区分“让同代价结果可复现”与“让实际行走更短”，
固定坐标平局规则本身不保证行走质量，等待所有依赖也会增加等待。
本轮未选择或实现这些改法，不改详细寻路或目标算法。

本地构建、原负载控制、原分析、36次固定记录回放、
6对已核对展开输入的单变量回放完成。
分析脚本初版将第7批手工数成第6批，断言失败后按原JSON修正；
没有修改日志、业务代码或数据来迁就断言。
