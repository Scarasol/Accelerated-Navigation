## 一、结论

**历史数据可以继续用，而且足以调整研究方向，无须为了做这次判断再跑同一套矩阵。**
它支持优先研究“图的活动类别不变时，免去整次事实遍历”，而非继续修改R2后扩样。
这仍是机制机会判断，尚未测出新的CPU收益。

1. 冷路线首Path前，3364次图事实遍历中，保守模型识别2348次可省的消费者固定、
   释放维护，占69.80%；涉及35,220个事实槽位，占全部标量事实调用的42.28%。
   这两个分母不同，均不代表worker或整次寻路能提速相同比例。
2. R2无重复路径不进入加权预检；热API也不每次构造摘要。
   这两项不能直接解释旧distinct控制的回退。
3. 同B跨场次绝对CPU成本明显漂移，旧单fork内也存在波动。
   旧编译日志不足以确定R2/distinct根因；不能把所有回退都归为噪声或JIT。
4. 下一研究优先项是B1的图级持有账目及状态转换设计，B0作为较小备选；
   R2保留既有证据并维持停止扩样。快照化和旧闭包矩阵暂不优先。
   本轮没有批准B1实现、生产接入或宣告步骤8完成。

## 二、数据能够回答什么

| 历史资料 | 本轮用途 | 不能回答 |
| --- | --- | --- |
| B/R/R2源码及class | 还原实际分支、核对标量方法 | 相同字节码的机器码或耗时必然相同 |
| 冷暖深trace及不可变对象身份 | 统计图、事实槽位和调用祖先 | 无插桩CPU、未记录的primitive delta |
| 旧局部和完整API JMH | 还原负载、各场迭代和控制 | 游戏净收益、跨场候选因果效应 |
| 旧B/R1空气编译XML | 核对已有内联记录 | R2、distinct或A/A的编译状态 |
| 生命周期检查原件 | 确认旧候选覆盖范围 | 尚未实现的图级聚合正确性 |

40个既有测量fork、160个迭代的CPU总量/实际操作数归一化重新核对通过，
没有新增测量。各版本、场次、fixture分开保留，没有混池算一个“总改善”，
没有减去A/A噪声、剔除不利样本或放宽旧门。

trace原件按旧`closure-analysis-v5.json`的五个输入哈希核对，无丢失/错误。
`objects.tsv`是运行结束后的反射dump：本轮只用不可变图/事实身份和
`PackedFacts.uniformFlags`，不把最终pin数字或cache字段当作历史状态。
代理只记录前两个对象参数，没有记录idle/active等primitive参数；
调用角色依祖先与已核对源码推断，无法确定的转换保持未知。

## 三、哪些旧解释需要纠正

### 3.1 R2的distinct路径没有加权预检

R2的实际分支是：

```text
boundaryFacts.hasFactRuns() == false
  -> visitFacts
  -> 原changeFactReferences
```

R2标量方法源码与B逐字相同；静态反汇编也完全相同，包括符号引用。
但外层增加了摘要读取和分支，调用及编译形态也改变，因此不能反推distinct一定零成本。
图遍历方法的末条指令偏移由15变为43，`hasFactRuns`末条偏移12；
这些只是静态形状，不用字节码长度估CPU。

完整API基准在`@Setup(Level.Trial)`发布中心与halo、构图并保留anchor。
测量方法只是请求就绪视图、读取组件数并关闭，所以摘要构造不在每操作内。
旧构造控制的+11.51%不能直接解释这个热API的每操作回退；冷构建成本仍独立存在。

### 3.2 局部微基准测的不是完整生命周期

引用微基准预置每份事实active=100，每次依次执行四种delta。
整个循环active始终为正，主要测稳态重复账目，没有测归零、淘汰或冷图发布。
其全空气fixture是15槽合为1段；完整API的空气fixture是中心flat加14个空气halo，
理想情况下15槽变2次应用。局部-88.46%不能外推成完整API或游戏改善。

实际冷trace的全部3364次图walk都有可合并空气段，50,460槽理论变24,030次应用，
少26,430槽，即52.38%。这仍保留7750个多元素段和16,280个单元素回调；
启用run路径后，单元素回调也会经过run helper，再执行原标量逻辑。
加权段还需要查表、条件判断和预检，不是把所有余下开销同时删除。
这些计数说明工作减量的边界，不能据此断言某项新增成本导致回退。
由于trace未记录delta和当时计数，这里是合法成功路径的段机会，不是假装执行过R2。

### 3.3 已有内联记录不支持helper根因定论

旧XML仅来自B/R1的空气诊断。结构解析找到R1
`changeFactReferences -> applyFactReferences`的5条C2 `inline_success (hot)`，
所以“helper始终不内联”不是成立的通用解释。
这不代表所有调用站点都内联，更不能据此确定R2/distinct行为。

B/R1在`visitFacts/visitFactRuns`上均有大方法内联失败记录；
记录条数是编译站点和编译轮次，不是动态执行次数，不拿它们比较CPU。
相关allocation-elimination记录为零，也不能推导不存在逃逸消除。

## 四、同代码为什么仍不能跨场直接比较

下面只列相同B代码在各自场次的描述性数据，不是算法效应：

| 场次 | 场景 | B的CPU范围 ns/操作 | 均值 | 最大单fork内CPU变异系数 |
| --- | --- | ---: | ---: | ---: |
| R1比较 | air | 854.79～969.34 | 905.83 | 20.77% |
| R2比较 | air | 612.69～627.99 | 618.40 | 15.96% |
| A/A | air | 409.36～452.82 | 422.84 | 10.47% |
| R1比较 | distinct | 625.55～890.07 | 762.50 | 18.32% |
| R2比较 | distinct | 612.81～729.53 | 675.01 | 19.36% |
| A/A | distinct | 424.82～446.84 | 436.10 | 8.07% |

变异系数来自每fork的四个原始迭代，仅作波动描述，不将迭代当独立JVM样本。
R2第一对air的B耗时四迭代为546.33/759.20/632.26/579.43ns；
R2为472.65/451.94/630.17/694.44ns，存在明显的fork内变化。

A/A的wall单fork最大变异系数约0.50%/1.06%，旧R1/R2可达18.14%/19.25%。
因此后一次A/A较稳定，不能证明前面的环境或执行形态同样稳定。
测量期编译计数较低，也不足以将全部波动解释为编译，或证明已进入相同稳态。
现有记录不能在后台负载、调度、频率、编译形态等解释之间确定唯一根因。

结论是：保留旧R2未过门的判断，同时不把它升级为“算法确定无效”。
再跑相同矩阵可能增加描述性样本，但不会自动解释上述原因，
目前已有更具体的工作减量问题值得先研究。

## 五、图级持有的机会比空气段合并更靠上层

### 5.1 当前重复了什么

`pinBase`已有按具体图的真实消费者计数，但每次增加消费者后，
仍遍历该图的中心与halo事实，并逐份增加active。
`releaseBasePin`也逐份减active。
如果缓存自己已经活动持有这张图，消费者再加一减一通常不改变事实的活动类别，
仍发生整次遍历、身份哈希查询与字节桶减加。

例如图有15个事实槽位、缓存保持活动：新增并释放一个消费者就产生30个槽位更新，
而图的事实始终需要保持活动。图级持有研究的是保留消费者计数，
但只在图的ACTIVE/IDLE/NONE类别真正变化时，再向底层事实传递一次变化。
这与允许寻路使用过期图无关，不需要改变当前性或快照语义。

### 5.2 保守模型与计数

模型为每具体图维护“已确认缓存活动”和观察到的消费者数下界：

- 初始缓存活动未知，按false；消费者下界从0起，不假定初始读者。
- 只有观察到publish的缓存持有，或pin前的缓存重激活walk，才确认缓存活动。
- 任何未分类图walk都清除“已确认缓存活动”前提，不把未知维护算成可省。
- 消费者增减未改变图类别时，才计作一次可省遍历；事实访问顺序按实际trace计数。

核对后，冷暖所有可省项均有已确认的活动缓存持有作为前提；
没有任何一项仅依赖消费者下界来推断可省。
补充逐图核对表保存在`audit-details-v3.json`，冷首Path窗口得到：

| 状态检查 | 观察次数 |
| --- | ---: |
| 首次观察到publish之前的消费者walk | 0 |
| unknown之后首次出现的消费者walk | 146 |
| 上述walk之前重新取得活动缓存依据 | 146 |
| 释放后已观察消费者数下界归零 | 1134 |
| 消费者walk没有当前有效的活动缓存依据 | 0 |

每次unknown都会使先前缓存依据作废，断言禁止跨unknown复用依据。
暖场没有窗口内publish，但4次消费者walk都有重激活依据。
原始trace也逐次确认每个图walk完成15次标量调用，walk及其标量子调用均无失败，
不是用图的最终长度代替实际完成的访问数。这些核对仍不构成新实现的生命周期证明。

| 首Path前记录 | 冷路线 | 暖路线 |
| --- | ---: | ---: |
| 具体Base图 | 304 | 2 |
| 图事实遍历 | 3364 | 12 |
| 图内事实槽位 | 50,460 | 180 |
| 全部标量事实调用 | 83,292 | 180 |
| consumer pin / release | 1174 / 1174 | 2 / 2 |
| publish缓存持有 | 304 | 0 |

| 模型可省事实槽位 | 35,220 | 60 |

冷场其余1016次图walk全部保留，另有32,832个不属于图walk的事实调用。
不能拿2348/3364去宣称所有引用维护少70%，更不能乘插桩wall估无插桩CPU收益。
冷整场仅比首Path窗口多4次未知walk，可省计数仍2348。
每具体图遍历次数范围1～38，不能假设每图都有同样复用程度。

2348次已识别机会按来源分为：

| 消费者来源 | pin与release合计walk |
| --- | ---: |

这说明大量重复来自构建与依赖的输入持有，不代表这些Base图或Boundary计算本身无用。

未知566次按可见祖先粗分：事件处理300、Super Boundary释放链92、
宏观依赖捕获72、图关闭释放链54、宏观完成链48。
这些祖先不足以恢复精确delta，故不继续猜测或把它们都称为真实类别转换。

### 5.3 与连续空气段合并重叠

冷首Path前，以原50,460槽为共同分母：

| 机会模型 | 可省槽位 | 保留槽位 |
| --- | ---: | ---: |
| 仅连续空气段 | 26,430 | 24,030 |
| 仅图级类别维护 | 35,220 | 15,240 |
| 图级类别维护后再合并余下空气段 | 43,484 | 6976 |

后者只比图级方案额外省8264槽，两个比例不能直接相加。
组合等式为`35,220 + 8264 = 43,484`；26,430是空气段单独口径，不再加入组合。
这是静态叠加机会，不是组合实现、CPU上界或实测结果；
当前优先独立研究图级方案，避免同时改变两个机制。
暖路线的图级机会仅33.33%，也说明冷场约70%不能泛化全部请求。

## 六、实现难度与研究顺序

B1并非只在pin/release外面加一个if。发布时缓存自己贡献活动持有；
`touchBase/removeIdleBase`转换缓存类别；退役撤销缓存持有；
旧图可能仍有读者，替换图不能继承它的租约。
cache是否活动还涉及demand、handoff和构建中的link，不能仅由pin是否为0推断。

一个保守的首版定义可保留原序列槽位重数，不顺手按事实身份去重。
设`m(g,f)`为图g中事实f的槽位数，则底层目标账目是：

```text
active(f) = directActive(f) + Σ m(g,f) × [图g类别为ACTIVE]
idle(f)   = directIdle(f)   + Σ m(g,f) × [图g类别为IDLE]
```

消费者自身的真实pin计数及全局活动引用仍逐次维护。
每份事实仍需累计多张图及直接所有者，不能用一个布尔值代替计数；
直接事实持有变化应立即更新，不等待图类别转换。

**B1改变FactReferences原始数字的含义，实施难度中高。**
旧“raw计数与B逐项相同”的oracle不适用于它。
需要按独立所有者账目验证每个可观察状态的活动/空闲类别、字节预算与峰值、
外部pin、旧图寿命及最终回收；并覆盖发布、idle、旧图替换、多geometry、
Boundary/Super构建、持久化直接持有、取消、淘汰、卸载和关闭。
新的租约元数据及旧图记录也须计入留存成本。
设计阶段还须明确：图租约及多图共享事实的存储表示、每次类别转换的完整成本、
在既有runtime锁下的原子性和回调重入次序。不能通过跨事件延迟账目结算来省成本，
也不能暗中改变预算、TTL或旧读者退出规则。
可复用旧oracle的可观察层，比较活动事实集合、每事实类别、删除集合和字节指标；
新的内部整数用独立所有者账目检验，另验证每次所有权取得与释放恰好配对。

| 方向 | 当前判断 | 下一步应回答的问题 |
| --- | --- | --- |
| B1图级类别维护 | 优先做设计与正确性可行性研究，不能直接接入 | 能否利用现有pin账目，完整维护cache/旧图/直接所有者，避免新增昂贵生命周期 |
| B0同类别免字节减加 | 较小备选，仍保留事实遍历和哈希 | 在保留异常前缀与预算语义下，是否有足够实际减量 |
| R2连续空气段 | 保留证据，停止当前版扩样 | 只有新的明确机制或诊断问题才重开，不能仅换布局试运气 |
| A父区查询缓存 | 保留分配减量，当前版不扩测 | 有新目标负载证据时再评估，不事后改旧10%门 |
| 宏观快照、闭包新算法 | 暂不升级为下一候选 | 先证明其可避免成本足以支付版本相容、失效和留存复杂度 |

这里优先B1指先研究状态机和新oracle，不预判它一定比B0有更好净收益。
选择标准是：B1有机会删除整次遍历，B0改动较小但保留遍历和哈希；
当前缺少字节桶减加自身的成本占比，不能仅因B0简单就认定它收益更好。
若完整生命周期无法在局部改动内表达，或新增账目成本明显吞掉机会，再退回B0。
后继测试应针对新的候选或未回答的问题；本轮不重新启动24JVM矩阵。

## 七、复审与封存

通过既有`tools/review/deepseek-review.mjs`及WSL dsh固定
`deepseek/deepseek-v4.1-flash`复审，实际发送6528字节自足摘要，
176.153秒返回`ACCEPT_SCOPED`、本轮必须修改项无。
退出0、未超时、settings前后哈希相同。已完整阅读回答，
其只读取自足摘要，不构成独立源码审查或实验复现。

有限共识是：继续R2盲目扩样的优先级下降，B1设计研究优先级上升，
B0为较小备选；不改变旧候选判定，不批准实现、性能或生产。
采纳其建议，补入逐图依据核对、完整15槽实际访问断言、组合等式、
B0选择标准及可观察层oracle。补核没有改变2348次机会的结果。

对部分措辞作了收窄：42.28%是模型已识别的调用机会，不称全项目可省调用的严格上限，
因为未知转换仍未分类；更不是CPU收益上限。原标量相同不代表回退“没有机制”，
外层分支与调用编译形态仍可能有成本。CPU迭代波动也不能单独归因于计量器本身；
实际进程线程工作与计量扰动尚未分离。未照搬这些更强表述。

`analyze.mjs`提供原始归因，`audit-details.mjs`补核完整标量反汇编、
空气单例身份、分段计数及模型前提；v1/v2/v3结构化输出保留，最终补核以v3为准。
首次TSV读取曾误删最后空列的tab，修正为只去末尾换行后执行通过，
错误记录见`analysis-notes.md`。这不是候选或性能测量失败。

本轮只新增分析脚本、输出和本报告；生产代码、旧候选、默认Jar、旧封存文档不变。
`final-seal-v1.json`绑定71项已消费历史输入、69项生产/Jar/旧文档保护对象、
附加来源身份、本轮分析输出、实际复审及正式报告。静态脚本检查与差异检查通过，
未运行生产测试、Minecraft或JMH。
本报告的结论限于历史离线归因和下一研究方向，不是步骤8优化完成或性能批准。
