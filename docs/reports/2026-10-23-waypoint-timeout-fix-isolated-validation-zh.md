## 2. 最终实现及开销

最终代码位于
[隔离Mixin](../../.tmp/waypoint-timeout-fix-20261023-v1/NT/main/java/com/scarasol/acceleratednavigation/mixin/AutomaticNavigationMixin.java)。
采用`ModifyArg`匹配原`doStuckDetection`中唯一的
`Vec3.atBottomCenterOf(Vec3i)`调用。
该调用只存在于next变化的else内：
cached已更新，limit和超时判断尚未执行。

```java
private Vec3i nextNodeTimeout(Vec3i next) {
    if(path instanceof NavigationRequestPath)timeoutTimer=0L;
    return next;
}
```

不修改传入坐标，不新建逐tick表、缓存、代次或身份检查链。
同节点分支没有新增调用；每次节点变化仅类型判断、赋值及原参返回。
shadow映射到原字段，不新增导航实例状态。
非项目路径保持原有计时行为。

初版非取消Inject虽然语义正确，但真实变换字节码显示每次切换创建CallbackInfo。
正式性能测试前已换为上述无回调对象的参数钩子；初版无正式性能结果。
最终导出字节码确认只一次调用，位于cached写后、limit写前，
`doStuckDetection`没有新增new或CallbackInfo。
这证明实现未引入该对象，不是JIT分配消除或CPU节省比例的测量。

## 3. 正确性与测试对齐

新增控制是计时分支修复必需的补缺，不扩常规性能矩阵。

独立Forge/Mixin正确性JVM最终25项通过，覆盖：

- 原节点变化分支清timer，cached、limit及lastTimeoutCheck保持原更新。
- 同节点精确累计和原严格超时比较。
- 非项目Path不应用修正。

- 公有移动API同intent复用、不同intent替换及外部取消。
- 真实石墙碰撞与实体物理，原60tick阈值在第61tick停止，
  实体未穿墙或抵达目标，100tick分支未抢先。

物理控制使用未加入实体表的Husk，每个server tick显式tick一次，
由真实世界方块碰撞阻挡；不是64实体性能场。
控制mod及Mixin导出均未进入正式性能包，正式mods仅生产JAR和原计量探针。

另一次控制启动在Java空闲门前因Gradle进程尚未退出被拒，无新游戏JVM，

## 6. 恢复、分配及秒级不利的已有数据定位

DEBUG覆盖全部1686次搜索，实际无>2连接跨度。
对NS，28格三场各少2/6/6次台阶reachable后执行恢复，
对应14条请求每条少一次恢复/搜索。
其中10条到达更早，4条晚约1.50至1.55秒。
另4条256/8 corner从首次正常中段partial后恢复变为无partial，
缺完整查询输入，不能将这4次初始搜索变化全部归给计时修正。

搜索分配按已有请求分组：

| 分组 | 请求数 | 搜索NS→NT | 搜索分配差MiB |
| --- | ---: | ---: | ---: |
| 搜索/partial/恢复计数不变 | 878 | 1642→1642 | +5.497978 |
| 台阶执行恢复变化 | 14 | 50→36 | -0.066986 |
| corner首次partial变化 | 4 | 12→8 | -0.389389 |

净+5.041603MiB全部被计数不变组的增长覆盖。
计数相同不证明输入、展开或完整路径相同；
无JIT及完整查询采样，不唯一归JIT、宿主、timer或恢复变化。

逐实体秒级延后共10条，全部在28格台阶：

- 64/128/256的tile4 slot0/4六条，搜索均3→3、恢复均0→0，
  到达晚1542.15至1810.84ms。
  首段节点7→12，末段8/9→10；首次查询range也已不同。
- 128/256的tile12 slot3/7四条，搜索4→3、恢复1→0，
  到达晚1502.73至1552.83ms。
  首段8→11、末段5→9节点，中段均23节点；
  首次range约22.04→25.03，已不只是同输入计时差。

128/tile12/slot3为例，首段搜索到中段搜索的DEBUG窗1742→2323ms；
中段搜索到最终搜索（旧窗含恢复）6752→6447ms，反而缩短305ms。
其余三条对应中段窗也约缩短0.29至0.31秒。
这些窗含执行、落地和接续，不是A*或独占CPU分账。

因此秒级增量伴随实际路径和交接位置差异，
不能说是多了常数级timer检查把主线程算慢1.5秒，
也不能把反复出现的节点数变化简单记为计时波动。
旧数据缺完整候选集合、当前位置和路径坐标，
尚不能唯一确定首次range/节点变化的上游原因，亦不保证全部独立于本轮间接影响。
未为此自动再跑对照或叠新选点算法。
`result-diagnosis-v2.json`覆盖全部10条；初版仅分析4条计数变化路线，原件保留。
