# 动态寻路预算原型验证

日期：2026-10-13。状态：原型验证与候选方案，未接入生产实现。唯一现行架构依据为 [原版详细寻路接入契约](../designs/2026-10-13-native-detail-navigation-contract-zh.md)。固定约 4ms 条款仍是现行条款；本文动态额度是待定的明确修订，不能以本文代替现行契约。废弃方案和旧审查不作为依据。

用户本轮要求以原型验证为主，验证后交由 DeepSeek 审核。派生拓扑持久化由另一对话独立研究；本轮不修改其实现、缓存、预热或构建并发。

## 当前结论

2026-10-14 后续：[新增失败交接根因研究](2026-10-14-dynamic-budget-handoff-root-cause-zh.md)已取得分支记录和有界等待的独立原型对照。下文第一版、第二版数据和审核结论保持其原有版本范围，不以新试验改写它们。

扩大额度能明显减少本次高并发排队，但未降低算法总工作量。512 并发下，动态对固定4的首 Path P95 下降 78.05%–89.48%，共同成功实体的实际到达 P50 下降 36.17%–40.51%。低负载时与固定12接近，目前不能证明历史预测器比固定12更优。

扩大额度也暴露了原有分段执行对等待时序的依赖：第一版正式比较新增 8 个配对失败，固定8/12同样有回退。第二版逐次轨迹确认额外的中间搜索与最终 partial，尚未确认触发这个中间阶段的具体分支。额外40ms负载下首次等待还有反向增加。建议继续隔离原型，不直接接入生产，也不直接改用固定8/12。

## 已确认的控制问题

1. 当前 `NavigationScheduler` 每 tick 补充 4ms，正余额上限也是 4ms；已经有从 START 计起的 45ms 实时截止检查。动态方案需要调整补充额度，不能把已有实时余量检查当成新实现。
2. 当前 `beginTick` 通过普通优先级 START 监听器调用。高优先级 START 订阅者可以先提交并产生计费；从该普通监听器才计时会遗漏它之前的工作。
3. 固定版本 Minecraft 1.20.1 / Forge 47.3.0 的 `MinecraftServer.tickServer` 在 `onPostServerTick` 之前写入 `tickTimes` 和 `averageTickTime`。本项目在 END 事件派发真实详细搜索；直接读取原生平均 tick 时间，会漏掉我们的 END 派发及其他 END 订阅者。不能据此得出“导航执行后上一 tick 仍很空闲”。
4. `runServer` 调用 `tickServer` 后才进入 `waitUntilNextTick`。等待阶段还可能执行任务，不全是睡眠。tickServer 封套与 tick 间任务需分开测量；不能把两个 START 之间约 50ms 的间隔当工作 MSPT。
5. 单机 `IntegratedServer` 在调用 `super.tickServer` 后还有视距等工作。只在基类 `tickServer` 的 HEAD/RETURN 计时也有覆盖边界。候选封套包围 `runServer` 的实际虚调用，计入子类尾部，暂停时无正常 START/END 的样本不进入控制历史。

固定版本源归因见 [源码位置与 jar 哈希](../../.tmp/navigation-dynamic-budget-20261013/tick-source.json)，可用 [提取脚本](../../tools/benchmark/capture-budget-tick-source.ps1) 重现。原型在专用服务器实际验证了封套；单机暂停及子类尾部尚未运行验证。

试跑的 8 格 / 128 并发提交 tick：tickServer封套 5.6591ms，原生 `tickTimes` 3.3720ms，差额 2.2871ms。差额涵盖原生统计截止之后的全部工作和计量入口差异，不能全部归为 PathFinder。

## 原型实现

生产 jar 和既有路线探针冻结复制后，另外装载一个仅用于研究的测试 mod。原型通过 Mixin 调整调度入口；不修改 `src/main`、生产配置、原生搜索参数或详细寻路语义。

- [原型源码](../../tools/benchmark/budget-prototype/java/an/budget/BudgetPrototype.java)保存tickServer封套、非导航历史、尾部历史、额度、余额和停止原因。
- [预算接入](../../tools/benchmark/budget-prototype/java/an/budget/mixin/BudgetSchedulerMixin.java)替换补充与 END 截止选择，继续调用生产 `drain`。原队列、优先级、老化、维度轮转、每次启动阈值、原子调用、嵌套计费和同步回调保持原实现；在取下一任务时重新读取 `haveTime`。
- [封套接入](../../tools/benchmark/budget-prototype/java/an/budget/mixin/BudgetTickMixin.java)包围实际 `tickServer` 调用，包括正常 START/END。按映射文件固定发行态方法名，不依赖开发态反混淆启动。
- [运行器](../../tools/benchmark/run-budget-prototype.ps1)生成独立超平坦世界，依次启动 JVM，保存原始输出、退出状态与 jar 哈希。

测试 mod 不能安装到生产服务器。第一版用于四额度正式对照，源码已保存在 [首版源码快照](../../.tmp/navigation-dynamic-budget-20261013/prototype-v1-source/java/an/budget/BudgetPrototype.java)。检查发现替换 START 入口后应显式保留原线程断言，第二版已补回 START/END/补充入口的所有权检查，并增加实际跨线程拒绝检查及可选逐次 PathFinder 轨迹。高负载和轨迹验证使用第二版，独立冻结在 `navigation-dynamic-budget-20261013-guards`。两个版本的性能表不混合；不能声称首版数据是第二版最终发行包验收。

## 控制规则

单位统一为纳秒。初始参数为实验值：

```text
目标工作窗口                 45ms
额度范围                     0..12ms
冷控制器额度                 4ms，前 8 个有效样本最多 4ms
历史长度                     32 个有效 tick
EWMA                         alpha = 0.2
扩张                         每 tick 最多 +1ms
收缩                         预测额度下降时立即收缩
上一个tickServer封套 >45ms  本 tick 额度额外限制为上一额度的一半

baseEstimate = max(EWMA(nonNavigation), P95(nonNavigation))
desired = clamp(45ms - baseEstimate, 0ms, 12ms)
grant = min(desired, previousGrant + 1ms)

tailReserve = max(2ms, EWMA(nonNavigationTail), P95(nonNavigationTail))
dispatchDeadline = fullTickStart + 45ms - tailReserve
balance = min(grant, previousBalance - outsideTickNavigation + grant)
```

`nonNavigation = tickServer封套工作 - 该封套内导航计费的并集`。它是墙钟归因，不能解释为纯 CPU 时间；GC 停顿发生在哪个区间就包含在哪个区间。不用包含导航工作的平均 MSPT直接反馈额度。

尾部留量用于覆盖本调度器 END 派发之后的其他工作。完整历史中的非导航工作已经包含尾部，额度公式不再扣一次尾部；当前 tick 的实时截止另减尾部，因为这部分尚未发生。这两处控制不同约束。

每次启动仍需余额、实时余量与 `haveTime` 同时允许。原生搜索不抢占，实际执行、发布与同步回调全部消耗余额；发生超支后停后续派发并保留负债。额度为 0 时不清除负债，不给无条件最低执行量。持续过载可造成现行 TTL 失败，应保留真实结果。

tickServer 之外的导航回调继续计费并形成负债，但不减入该封套的非导航样本。本轮测试记录 `outsideNavigationNanos`；整个等待阶段的非导航任务、主线程连续忙碌时间和落后于原生计划的程度尚需另外测量，不能宣称已覆盖完整事件循环负载。

P95 32 项使用固定数组和复用 scratch；每 tick 至多两次 32 项排序，为固定 O(32 log 32) 时间、O(32) 状态。每次派发前检查仍为 O(1)，生产队列复杂度不变。没有把整个寻路算法变成 O(1)。

上述空间界限只指控制器历史，不包括原型仪表。测试 mod 把逐 tick 样本和诊断轨迹保存在列表中，保留成本随样本数增长；它用于有限批次，生产计量需要有界采样和独立输出。

[模型脚本](../../tools/benchmark/research-dynamic-budget.mjs)完成 9 项边界检查、20 场景 × 4 模式，共 80 次确定性模拟。[证据](../../.tmp/navigation-dynamic-budget-20261013/evidence.json)保存全部逐 tick 数据、任务启动和源哈希。

覆盖正余额不积攒、0 额度保留负债、原子操作及回调计费、当前高负载停发、冷控制器缓慢增长、逐任务重新读取 `haveTime`、tick 间导航计费、长原子操作超 50ms、未知尾部突发超 50ms。它验证控制规则的逻辑，不是 Minecraft 性能。

各模式统一使用新封套、同一尾部留量和同一截止规则。固定 4ms 是模型额度参考，不是当前生产实现的逐行复制。合成任务成本包含一次完整原子操作及回调；它不是从旧 PathFinder 内部计时拟合的生产成本。未模拟实体运动、优先级/维度公平、TTL、GC、线程竞争或控制器自身成本。

四额度模式各完成18个正式场景和两个预热场景，合计72个正式场景；每模式正式提交5,376个请求，共21,504个正式请求。相同jar的输入身份、路线逐actor对齐和逐tick计费核对均通过；原始失败完整保留。[全部36组指标和百分比](../../.tmp/navigation-dynamic-budget-20261013/runtime-analysis.json)、[比较表](../../.tmp/navigation-dynamic-budget-20261013/runtime-table.md)和[新增失败原始对照](../../.tmp/navigation-dynamic-budget-20261013/failure-evidence.json)由[分析程序](../../tools/benchmark/analyze-budget-prototype.mjs)生成。

共同输入：Minecraft 1.20.1、Forge 47.3.0、Java 17.0.18、3GB 堆、相同冻结生产 jar 和探针、成年尸壳、速度 II、关闭自主目标和推挤、64 地形单元、8 类混合地形、不同起终点。三个距离代表值 8/18/28 格，对应 <12、12–24、24–32 格；并发 128/256/512。每种额度模式两轮正式测试，第二轮反转距离和并发顺序，另有两个 64 实体预热批次。

四模式全部使用同一个原型测试 mod，共享新计时封套、2ms 起步尾部留量、每次取任务读取 `haveTime` 等保护。横向只改变固定 4/8/12ms 和动态 0..12ms 的额度控制；因此固定 4ms 组也不是完全未加仪表的原生产包。真实原版同步基线保留在既有报告，本轮比较的是预算模式，不借它宣称相对原版寻路的提升。

本轮实际 test world 有路线预热，不能称为严格冷启动测试；模型的“冷控制器”只表示缺少预算历史，不表示拓扑冷缓存。

统计口径：从提交到首个非空可执行 Path、从提交到实际到达、批量 API 提交和任务终态分别报告。到达只比较双方都成功的同一 actor；首次 Path 比较双方实际有 Path 的同一 actor，另列未产生 Path 和失败。成功率涵盖所有提交并列出新增配对失败。变化率 `(候选 - 固定4) / 固定4 ×100%`，不把末段 partial 耗尽改成到达成功。

本文表格统一称“tickServer封套工作”，不称完整服务端MSPT。封套从本次前置控制入口起到真实tickServer虚调用返回，包含前置控制/人工附加负载、START/END、END派发及其后的探针；不包含tick间等待/任务，也不包含封套采样后的控制历史更新与序列化元数据开销。`controllerEntryNanos`仅测入场/选额成本，不代表原型全部仪表成本。不把旧START到探针END的工作时间冒充该封套。

候选解释是更快补段改变真实搜索起点与实体运动状态，固定4的排队等待可能掩盖了交接时序问题。这是待验证假设，不能仅据地形或汇总 partial 次数确认根因。

### 第二版逐次搜索证据

第二版恢复显式线程所有权，实际 START/END 跨线程调用均被原有 `requireServerThread` 拒绝。另用相同第二版 jar、相同生产与路线探针重跑固定4/动态12的18/28格、512并发、两次重复，各四个正式场景。可选轨迹会增加计量开销，故这两轮诊断不拼入第一版性能百分比。

[轨迹对照](../../.tmp/navigation-dynamic-budget-20261013-guards/trace-analysis.json)由[分析脚本](../../tools/benchmark/analyze-budget-traces.mjs)验证请求身份、提交区间、初始位置、最终目标和真实调用数。此次诊断中新增6个配对失败；与首版8个不是同一次试验，不能相加或当作消失了2个失败。

以18格 actor29（第0轮）为例：

- 两边第一段都是同一候选集合、range18.630146、accuracy0、multiplier1，起点 `(-16.5,81,-136.5)`，真实末节点 `(-17,81,-145)`，可达。
- 固定4第二次直接搜索最终目标 `(-17,81,-155)`，range18、accuracy1，起点约 `(-16.5013,81,-144.0879)`，水平速度0，真实末节点 `(-17,81,-154)`，可达。
- 动态第二次先搜索额外中间目标 `(-18,81,-146)`，range16、accuracy0，起点约 `(-16.5013,81,-144.0108)`，水平速度约0.03643，可达。第三次才搜索最终目标，range18.049875、accuracy1，起点约 `(-17.0969,81,-144.9457)`，水平速度约0.03509，真实结果为partial，末节点 `(-17,81,-153)`。

这确认了阶段与真实搜索输入不同；range等差异是既有按当前位置/阶段选参逻辑的结果，不是测试改变常量。还不能仅靠这组轨迹判定是水平惯性、原生stop、目的组件经过记录、恢复分支或宏观阶段选择造成。

下一轮应在原型记录 `settle/intermediateArrival/recover`、真实 native-stop、经过记录身份/发布代次、窗口组件及当前性、游标/stride/attempt和触发原因，再做单一变量的交接时机对照。不能通过地形资格过滤、放宽原参数/accuracy或整条回退掩盖这一失败。

### 资源与 TPS

512 并发的动态相对固定4：

| 距离 | 主线程累计分配变化 | 堆采样峰值变化 | 原生累计搜索时间变化 | 原生调用数变化 | 累计导航计费变化 |
|---:|---:|---:|---:|---:|---:|
| 8 | -5.90% | +21.45% | +12.97% | +5.35% | +21.11% |
| 18 | +1.90% | +6.84% | +11.35% | +9.84% | +8.11% |
| 28 | -16.76% | +6.59% | +11.70% | +8.87% | +8.38% |

缩短观察期可能降低累计分配，它不是等时长的算法独占分配；堆峰值受 GC 和 JVM 生命周期影响，也不是导航驻留内存。原生总搜索和调用数上升，动态预算没有降低算法总工作量；它主要改变工作发生的时机，实体运动与恢复也随之改变。

动态三组观测 TPS 为 19.983/19.993/19.996，相对固定4约 -0.040%/-0.013%/-0.002%，不能认为平均 TPS 改善。tickServer封套工作与>50ms尖峰须同时查看。

512 三组选择额度入口的 P95 为约 0.0145/0.0086/0.0092ms；它只说明该入口在此机的开销较小，不覆盖 END 计量、历史更新、探针实体遍历或 JSON 元数据开销。

## 下一阶段通过条件

研究原型是否值得继续，与是否可以进入生产是两个判定：

1. 首 Path 与途中等待有实测改善，并且新增失败需逐 actor 解释。原版查询目标集合、accuracy、range、节点限额、visited multiplier、region offset、partial/EXHAUSTED 和真实到达规则保持。
2. 至少五次独立重复、交换额度模式顺序，冷控制器/暖控制器及冷热拓扑分开；补持续请求、真实玩家与速度 IV。本轮两次重复不给置信区间，不足以定最终 12ms 参数。
3. 在额外主线程负载 10/30/40/48ms 下验证缩额与零额度，另测真实生产负载。人工忙等只用于调度压力，不代表真实生产 CPU 结构。
4. 补独立的可运行队列、parked、宏观依赖等待、段间等待、单次完整任务成本与 stop 原因计时。不能把 `pendingRequests` 等同“只等预算”；原型首版的 `DEPENDENCY_OR_THRESHOLD` 仍需拆分。
5. 明确处理 tick 间主线程工作、原生落后/追赶、未知 END 尾部和一次不可抢占长搜索。>50ms 尖峰、成功率与等待联合判定，不能只看平均 TPS。
6. 完整线程所有权、替换/取消、目标漂移、同 tick 输入变化、原版 prepare/done、迟到回调、TTL、关闭归零与单机暂停回归通过。

第一阶段只改计时和额度，保留优先级、公平、参数和恢复上限。补段优先、任务成本 P95 作为启动门槛、请求索引和预取另做独立变量；尤其不能因估计任务成本高于最高额度而使任务永久无法启动。
