# 旧连续空气段：波动来源定向诊断

日期：2026-10-18。
依据用户“回到项目，先尝试定位波动来源”的要求，承接
[稳定性研究](2026-10-18-air-run-stability-and-amplification-research-zh.md)。

## 结论

本轮定位到两类具体机制，但没有把历史跨JVM波动全部确定归因：

1. **进程CPU的部分尖峰与GC期间的量化增量对应，而实际耗时没有同步尖峰。**
   本轮48个测量阶段的进程及主线程CPU增量都为15.625ms整倍数。
   这是实际观察到的计量粒度，不是该API的精度保证。
   一个显著尖峰与GC事件读取的CPU计数对应，详见下文；
   两者可能来自同类底层计数，不能作为两份独立CPU证据。
2. **空气合并路径确实改变了编译和分配形态。**
   旧版空气路径中的`pinBase`因`NodeCountInliningCutoff`被拒绝内联，
   对应请求回调的编译代码变大；此JVM每次分配800B，其余三个为768B。
   这些是本次的实测差异，尚未证明额外32B属于哪个对象，
   或历史收益从约10%到约36%的变化均由这种编译差异造成。
3. **无重复路径的额外耗时仍未闭合。**
   本次旧版的实际图槽位哈希探测反而更少，且没有特有的关键内联失败；
   不支持用“更多哈希冲突”或“多做空气段预检”解释它较慢。
   不据此宣称无重复成本已经解决，也不把未知原因一概归入噪声。

因此，原先拟议的单元素提前返回仍不直接实现：
run helper在空气遍历中已经内联，源码上的判断和循环不等于独立运行成本；
该修改又不能解决完全无重复路径。
后继应优先针对热调用图大小、调用边界和分配做可证伪的最小验证，
而不是先假定单元素分支能稳定收益。
本轮没有实施任何算法候选，也没有追加性能矩阵。

## 固定范围与输入

测前协议为材料目录中的`protocol.md`。
只运行四个工作负载JVM，串行顺序：
基线空气、旧版无重复、旧版空气、基线无重复。
`B`为原基线，`R2`为旧连续空气段第二版，均复用既有`compiled-v3`字节码。
仅新编译诊断观察器，不重新编译或修改旧算法。
离线`jfr print`是对既有录制文件的解码，没有新增工作负载。

使用Java 17.0.18+8、512MiB堆、原默认编译/哈希策略，
诊断额外开启`LogCompilation`、JFR profile和`java.util`反射访问。
宿主为平衡电源模式、32逻辑CPU，没有修改电源或频率设置。
记录了后台进程CPU，未记录每核频率、温度或调度事件。
OneDrive、System等在四段运行期间有背景活动，但不能据此直接解释某个差额。

fixture保持原27个section和同一中心anchor。
热操作是取得已就绪图、读取连通分量数、关闭视图；
实际图保留15个事实槽位。
预热以16384次为一批执行至少3秒，随后12段各100万次。
没有强制GC、强制编译、固定对象哈希、适应性追加预热或删除不利阶段。

每段同步记录wall、进程/主线程CPU、主线程分配、GC和编译。
调用图和原始引用账目、字节桶、一个anchor、当前性及checksum全部核对；
各段无未结构建需求，关闭后引用/字节/缓存和引用表归零。
926份生产输入、默认JAR、旧源码与字节码前后哈希一致，
并核对16项实际加载类的SHA256和来源。

**这些诊断时间不作净收益资格判定。**
日志、JFR和观察器存在扰动，直接循环壳也不同于历史JMH壳；
不能把下表相对差额作为对旧性能门的改判，更不是冷构图或真实寻路性能。

## CPU尖峰的具体对应

旧版无重复第10段：

| 项目 | 观测 |
| --- | ---: |
| 操作数 | 1,000,000 |
| 实际耗时 | 486.3396ms |
| 进程CPU | 640.625ms |
| 主线程CPU | 453.125ms |
| 进程减主线程 | 187.5ms |
| GC | 2次，MXBean累计2ms |
| 总编译时间增量 | 3ms |
| 同段`GCCPUTime.userTime`累计 | 187.5ms |
| 同段`GCCPUTime.systemTime`累计 | 0 |
| 同段`GCCPUTime.realTime`累计 | 约2ms |

前后实际耗时仍处于该JVM的474.68～488.66ms范围。
这支持将这个CPU尖峰定位为**GC关联的进程CPU量化增量**；
不支持把它写成“主线程引用维护突然多做187.5ms”。

`GCCPUTime`和进程CPU可能读取同类底层进程计数，并非独立测量。
它们也不是整个阶段的独占CPU分账。
不能把187.5ms简单作为真实GC执行成本、从样本中扣除后重算收益，
或据此宣称旧版所有历史不利数据都只是GC/计量噪声。
既不认定它是纯记账伪影，也不认定它是更多真实并发GC工作；
没有线程级证据作这两种区分。
本轮其余CPU波动没有全部逐项确定归因。

## 编译及分配形态

四JVM的目标C2安装均在uptime约4.04～4.44秒前完成，
测量阶段从约6.62～7.09秒开始。
十二段内没有目标重新安装，JFR也未记录反优化事件。
因此，**本诊断没有观察到测量阶段的目标C1/C2切换造成耗时台阶**。
总编译计数仍有134～160ms，包含其它后台或观察器代码，
不能据此称整个进程已经停止编译。
uptime与日志对齐为毫秒精度，编译任务wall重叠也不是编译CPU。

关键C2日志：

| 调用/编译实例 | 基线空气 | 旧版空气 | 无重复两边 |
| --- | --- | --- | --- |
| 请求回调中的`pinBase` | 内联成功 | `NodeCountInliningCutoff` | 均内联成功 |
| `changeTopologyFactReferences` | 在热调用中内联 | 在相关热调用中内联/独立编译 | 均有成功内联 |
| 实际遍历器 | `visitFacts` | `visitFactRuns` | `visitFacts` |
| run helper在遍历中 | 不存在 | 已内联 | 不调用 |
| 外层对遍历器的内联 | 已编译为大方法而拒绝 | 已编译为大方法而拒绝 | 两边均因此拒绝 |

基线空气的`visitFacts`对应C2代码总大小13,256B，
旧版空气的`visitFactRuns`为17,352B；
对应请求回调分别12,712B与31,616B。
这些是日志中具体`nmethod.size`，包含编译代码相关内容，
不是执行指令次数或方法CPU占比。
不能只凭体积差断言它导致了历史收益幅度变化。

旧版空气的十二段分配均为800B/次；
其它三JVM均为768B/次，主线程分配精确计数差32B/次。
历史R2 JMH约768B/次，因此本轮不能外推为R2必然增加32B。
诊断观察器、调用壳、类型profile及编译取舍都可能改变分配形态。

JFR分配样本覆盖请求/关闭回调、`afterRuntimeLock`、`ArrayList`、
`CompletableFuture`和事实引用Consumer等路径；
各类采样权重明显偏斜，**不能把额外32B直接归属到某种lambda或容器**。
例如旧版空气的主线程分配样本很少落在`BaseGraphView`，
较多集中于`Object[]`、回调、`UniWhenComplete`和`ArrayList`；
其它JVM则有较多`BaseGraphView`、`ClusterKey`等样本。
这种采样差异不能解释成相应对象在某条正确调用路径中消失了。
没有精确对象分配清单，也没有强制编译/关闭逃逸分析来制造差异。

测量期JFR执行采样总数仅为：
基线空气12、旧版无重复15、旧版空气6、基线无重复2。
这个密度不足以估计方法CPU占比，不用分配权重代替CPU。

## 引用表核查

按测前约定，在预热前和全部阶段结清后两个点，
仅于runtime原锁内浅复制`IdentityHashMap.table`，
锁外计算探测次数；没有改表、resize、重排或固定identity hash。
哈希和步进公式核对本机JDK17的`src.zip`。
各表容量均32个key槽，真实图均15个事实槽。

| 实现/场景 | 表中身份数 | 所有键探测和 | 最大探测 | 实际15槽加权探测和 | 空气单例 |

空气图实际序列为一个中心事实和十四个连续空气单例。
无重复图的各槽身份不同；不是将内容相同误当作同一对象。
四个JVM各自的前后完整表形状相同。
两端观测相同不是连续resize/探测事件监控，
不同JVM的对象也不能当作同一组键做因果配对。

当前较慢的旧版无重复，其实际图槽位探测更少；
本次证据不支持“它因更多引用表冲突而慢”。
哈希分布仍可能影响别的独立JVM，只是旧历史没有这些形状记录。

## 未闭合项与后继取舍

无重复路径没有调用run helper，标量方法与B相同，
并且本次关键内联形态大体一致、分配相同、探测未更差。
额外的`hasFactRuns`判断及其代码布局影响仍存在，
但目前没有指令级成本证据将约5.64%的诊断wall差额全部归给它。
也没有每核时钟或调度证据将差额全部归给宿主。
这个问题仍需保留，不能作已修复登记。

本轮优先级调整为：

1. 保留旧段合并语义，先研究如何限制其对热调用图及分配形态的影响。
   若后继实施，应只有一个最小结构改动，并能用日志和精确分配反证。
2. 单元素提前返回继续停留在候选层；helper已内联，
   不能按源级分支数量宣告省时，更不能用它解释无重复成本。
3. 不替换引用表，不固定hash或编译参数，不恢复新版图级聚合，
   不追加本轮四JVM之外的工作负载来追求有利结论。

这次完成的是波动诊断和证据范围收窄，
不是稳定提速、真实worker成本改善或生产接入批准。
步骤8仍未完成；历史门和封存均保持。
