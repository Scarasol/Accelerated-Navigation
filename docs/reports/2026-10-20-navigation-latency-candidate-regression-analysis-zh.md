# A2 不利数据的离线分解

日期：2026-10-20。回应用户关于 A2 相对 S9L 的增量原因。
仅复用已有封存记录进行离线分析，没有新游戏、构建、基线复跑、外部调用或生产修改。
原验证报告、原 1653 项证据清单及原始数据不改写。

## 结论

此前完成的是机制/生命周期验证及性能观察，没有完成增量的代码根因定位。
本补充将现有记录进一步拆分，仍未定位到解释全部增量的明确代码缺陷：

- 8 格适用组唯一不利路线的到达增加 52.0324 ms，发生在首次移动前；
  真实搜索本体反而更短，首次移动至到达的观察 tick 跨度不变。
- 28 格最差路线到达增加 248.9239 ms，只有 23.2562 ms 来自首次移动更晚；
  另外 225.6677 ms 出现在首次移动至到达期间，观察 tick 跨度增加四。
  不能将全部 249 ms 解释成首段就绪晚了一次。
- 28 格进程 CPU 增加 328.125 ms，其中主线程增加 187.500 ms，
  进程减主线程的计数差额增加 140.625 ms。真实搜索次数、结果汇总没增加，
  搜索合计 wall 反而下降，尚无证据把这些 CPU 增量归给真实搜索本体变重。
- 两场的所有逐路线搜索次数、partial/null/reachable 次数及最大返回节点数均一致。
  这些汇总相同不证明实际完整路径、探索节点数、实际路程或段间等待完全相同。

按用户既定规则，未明确定位的变化暂按波动处理；
这是处理约定，不是证明与改动没有因果关系，也不能据此认定 A2 有稳定净收益。

## 方法与边界

比较对象为 2026-10-20 当前生产 S9L 历史净测与同日 A2 隔离净测，
原 8/28 格各 64 实体并发、同一 NoTrace 工具。历史基线没有复跑。
按 tile/slot/kind 匹配，直接使用原 `timeline.json` 与 `full-ticks.json`。
所有实际用于数值结论的历史数据均与原封存哈希一致。
未进入原封存的历史逐段 DEBUG 日志不作为本补充的依据。

四阶段定义为自身提交至首 Path、首 Path 至首次移动、
首次移动至实际到达、到达至请求终态；逐路线先相减。
前三阶段的差额相加核对为总到达差额，不将不同路线的分位相加。
firstMove/arrival 是原 END 观察时刻，不是精确物理运动开始/结束时刻；
“首次移动至到达”包含实体移动、段间等待和观察节拍，不能叫纯移动耗时。

事件 tick 取实际包含该时间戳的完整 server tick。
首 Path 可在 tick 主体后的 idle 期间发布，因而有些时间戳不属于任何完整 tick；
不强行将其塞进前后某个 tick，也不按墙钟除以 50 ms 反推 tick 数。

## 8 格适用组的不利路线

`tile3/slot6`，交错墙，原诊断识别为初始零组件边适用路线。
单位毫秒；“差”均为 A2 减 S9L。

| 指标 | S9L | A2 | 差 |
| --- | ---: | ---: | ---: |
| 自身提交至首 Path | 102.9353 | 124.4339 | +21.4986 |
| 首 Path 至首次移动 | 7.1418 | 44.5427 | +37.4009 |
| 首次移动至到达 | 1980.3363 | 1973.4692 | -6.8671 |
| 自身提交至首次移动 | 110.0771 | 168.9766 | +58.8995 |
| 自身提交至到达 | 2090.4134 | 2142.4458 | +52.0324 |
| 唯一真实搜索 wall | 14.2352 | 0.6353 | -13.5999 |
| 首次移动至到达的观察 tick 跨度 | 40 | 40 | 0 |

因此能定位到“开始移动前更晚”，并排除本样本到达增加来自搜索本体 wall 增长的解释。
但 NoTrace 没有逐请求宏观完成、排队准入和真实搜索开始时间，
尚不能把首 Path 的 +21.4986 ms 进一步唯一分配给宏观等待、队列等待或结果交付。
首 Path 后至首次移动的 +37.4009 ms 也不能据 END 观察直接认作新代码阻塞 37 ms。

8 格另一条非适用门洞路线 `tile6/slot0`：
首次移动提前 46.2133 ms，首次移动至到达增加 50.8748 ms、tick 跨度 61→62，
最后到达增加 4.6615 ms。这是“开始早了但后来多一个观察 tick”的数据，
不能据此推断纯移动速度下降或实际路程增加。
8 格其余 62 条路线的该 tick 跨度相同；另有一条减少，合计 64 条。

场景 CPU 包含整个测量窗内的工作，不是导航改动专属；

搜索次数为 8 格 99→99、28 格 142→142；
partial 为 0→0、4→4，null 均为零。

两场测量窗内 GC 次数与时间都为零，不能将窗内 CPU 上升直接归因 GC。

## 代码层面的解释与尚缺的证据

[原 queue/followup](D:/Workspace/AcceleratedNavigation-forge-1.20.1/src/main/java/com/scarasol/acceleratednavigation/navigation/SegmentedNavigationService.java:316)
在准备任务运行时设置 `running=true`；准备内再次 queue 真实搜索时先挂 followup，
外层完成才再次提交。A2 则在宏观交付内完成准备，直接向原调度器提交真实搜索。
因此它改变真实搜索提交的时机与队列相对次序，即使最终每个请求都少排一次任务，
也不能保证 64 并发里每个请求都得到更早的 Path。

[调度准入与选取](D:/Workspace/AcceleratedNavigation-forge-1.20.1/src/main/java/com/scarasol/acceleratednavigation/scheduler/NavigationScheduler.java:368)
仍受墙钟窗口、常规余额、优先级/维度及同队列次序影响。
更早入队可能改变哪个任务落在本次或下次实体更新前；
这是代码允许的影响机制，不是本轮不利样本已经验证的精确因果链。
没有发现候选增加全走廊扫描、预取、真实搜索调用或新的后台任务。

所以当前应保留“可能的排队/发布相位变化”和“未定位波动”的区别：
8 格不利样本已有阶段定位，但仍缺直接队列链；
28 格的大尾部主要落在后续执行/等待，而 CPU 尚缺方法级归属。
不以一份接受范围受限的 DeepSeek 文本审查代替根因证据。
若将来要确认这些具体原因，需要另行约定最窄补充诊断；
本补充未据此启动新测试、重跑有效基线或修改候选。
