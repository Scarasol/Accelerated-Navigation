# 独立冷首批与压缩接线验证

日期：2026-10-11。**诊断参考，不是正式生产验收。**

本轮已经完成18个独立Java进程的预定对照。每个进程只执行一个变体的首个Store和8次全量新区块写入，三变体每个各6个进程。原23.2%的首批平均回退在新口径下没有复现：默认31.80ms/批、原代理32.71ms/批（+2.8%）、直接封装31.89ms/批（+0.3%）。

**首批平均接近并不等于第一笔没有损失。** 真正第一笔写入的中位为默认19.10ms、原代理22.88ms（+19.8%）、直接封装20.98ms（+9.9%）。直接封装在数值上落于10%线内，但余量只有0.02ms，明显小于这些样本的波动，不能据此声称首笔已稳定不回退。

建议保留级别5技术和直接封装作为接线候选，不再照搬代理原型；当前数据不支持给第一笔的稳定性作保证。生产接线仍未实现，未改变新工程生产代码或旧工程，没有Git、委派、DeepSeek或游戏/UI操作。本轮仅承接用户“好的，继续进行验证”。

沿用一个真实导出的城市区块：11个16×16×16区段，Y−4至6，45,056格，38,525B原始载荷。每笔写入是一个新水平区块的这11段事实；8个不同新块共用一个RegionFile。几何只替换cell0，其余格和门/碰撞形状保留，输入生成及断言在计时外。不是整个城市、构图或寻路耗时。

三变体的内容、版本和按Y排序后的原始字节完全相同。独立JVM的Map遍历可能不同，因此三方在流式写内同样排序，成本均计入。使用同一Java17、512MiB堆和实际Forge依赖，六组使用三变体六种顺序各一次；每行来自全新进程，无变体之间的JVM预热。

可以由证据确认的结论：第一笔负担主要集中在首次读/region准备、首个流式写/关流和其余首次执行工作，而非后续每笔都多几毫秒；新直接封装消除了动态Proxy和inputWrapper字段字符串反射，正文开销下降，但没有消除全部首次准备。18个宿主GC关联均为0，本次差值没有证据归因于GC。JIT、调度和计时正文之外的类加载贡献没有分别量得，不能声明唯一原因。

上一轮口径已知有两个限制：同JVM先后执行变体，后者可能享用公共类/方法初始化；原worker计时窗口内包含取得线程CPU计数器。该计数器在本机只有粗刻度又不支撑原结论，本轮三方均删除其调用/字段，未用估计值从旧时间中减去。新增独立进程、去探针和同序列化顺序共同改变了口径，**只能说旧23%回退在新对照中未复现，不能定量断言其中多少就是探针或先后顺序造成的**。旧失败和原始数据保留。

网络对照使用OpenJDK JMH关于fork的原始样例：独立进程用于避免不同测试共享优化profile。本轮借用这一原则，没有安装JMH或假称由JMH认证；原文及来源记录保存在证据目录。
