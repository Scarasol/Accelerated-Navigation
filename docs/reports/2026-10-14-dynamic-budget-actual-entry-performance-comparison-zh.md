# 动态预算实际接入性能对比

日期：2026-10-14。测试对象是本轮实际交接候选包，候选 SHA-256 为 `53F48B1551414115B15EE086F8F7EE79DF75787CDC99BA76B45AF2B256C34636`。

本报告只使用当前候选和当前唯一现行契约，不引用废弃设计或旧三 tick 包作为通过依据。固定 4ms 是同一候选源码替换预算控制器后的研究消融包，原版是同一候选包关闭加速后端的运行时基线。

## 测试矩阵

正式矩阵在三个独立 Java 进程中顺序运行：

- 动态预算：最大额度 20ms，生产候选控制器。
- 固定 4ms：相同导航、拓扑、Mixin 和探针，只替换预算控制器；除控制器两个 class 和重新生成的 Manifest 外，其余 jar 条目与候选逐字节一致。
- 原版运行时：相同候选包和相同调度器，Husk 加速后端 bypass，使用真实原版 `PathFinder`。

每种模式包含 8、18、28 格三组直线距离，128、256、512 并发，八类不同路线，正式请求共 2,688 个；每个模式另有两个预热场景。实体是成年尸壳，永久发光、速度 II、无自主目标、关闭实体推挤。起点、终点、地形、种子、堆上限和探针完全相同。

完整 tick 计时包含实际 tick 虚调用、同步发布、回调、GC 和测试清理。Path 就绪时间从提交开始计；实体到达时间只比较双方都成功的同一实体。原生搜索时间由相同 `PathFinder` 入口探针记录。内存数据含测试探针保留和 GC 时机，不能直接当作生产净内存。

## 正式结果

下面的百分比定义为“动态预算 - 对照”除以对照。到达时间仅包含两边都成功的配对实体。

| 直线距离 | 并发 | 动态成功率 | 固定4ms成功率 | 动态相对固定4ms的 Path 就绪 P95 | 动态相对固定4ms的完整 tick P95 | 动态相对固定4ms的实体到达 P50 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 512 | 96.09% | 96.09% | -87.8% | +93.4% | -44.3% |
| 18 | 512 | 93.75% | 93.75% | -89.4% | +51.7% | -37.4% |
| 28 | 512 | 98.44% | 97.66% | -93.1% | +70.9% | -42.3% |

对应的绝对值为：

- Path 就绪 P95：动态约 `270 / 265 / 465ms`，固定 4ms 约 `2208 / 2508 / 6708ms`。
- 完整 tick P95：动态约 `18.7 / 15.3 / 16.1ms`，固定 4ms 约 `9.6 / 10.1 / 9.4ms`。
- 动态三组均没有超过 100ms 的 tick；28 格组出现一个 `70.27ms` tick。固定 4ms 在 28 格组出现一个 `58.35ms` tick。
- 两种加速模式的 TPS 都约为 `20`，所以这里的收益主要是提交后更早发布首段 Path，不是把单 tick 反算成高于 20 TPS。

动态预算相对固定 4ms 的原生搜索总墙钟分别为 `+4.0% / +8.1% / +2.6%`（8/18/28 格）；原生搜索调用数基本相同。主线程分配量分别为 `-39.9% / -11.9% / -25.6%`。这说明动态预算降低了排队和积压带来的测试分配峰值，但没有减少真实 `PathFinder` 的算法工作。

与同包原版运行时相比，动态预算在 512 并发下的成功率差异为：

- 8 格：`-3.125` 个百分点；
- 18 格：`-4.492` 个百分点；
- 28 格：`+17.578` 个百分点。

动态相对原版的提交批次耗时下降 `80.2% / 95.6% / 98.6%`，但 Path 就绪 P95 增加 `515.4% / 305.0% / 157.7%`。原版同步提交会在提交调用内直接支付搜索时间，因此两者的“提交时间”和“Path 就绪时间”必须分开解读。动态相对原版的共同成功实体到达 P50 增加约 `19.4% / 8.2% / 8.3%`。

## 冷启动结果

冷启动使用新 JVM、新世界和第一批导航请求，不做路线预热。512 并发下，动态相对固定 4ms 的首段 Path 就绪 P95 为 `-51.6% / -86.7% / -92.0%`；实体到达 P50 为 `-33.6% / -37.1% / -39.7%`。动态相对固定 4ms 的完整 tick P95 却增加 `+140.0% / +49.9% / +54.1%`，8 格冷启动出现一个超过 50ms 的 tick。

这表示动态额度确实缩短了冷启动排队，但会在首次拓扑和搜索工作集中时把更多工作放进当前 tick。它不能被描述成所有指标都变快。

## 动态控制和负载探针

真实事件循环负载探针通过 106 项预算断言，覆盖 0、10、30、40、48ms 基础负载、未知 END 尾部、60ms 原子调用、负债、tick 外任务和队列排空：

- `48ms` 基础负载选择零导航额度；
- 观测到并保留负余额；
- 学习到至少 `12ms` 的 END 尾部；
- tick 外任务保持在封套外归因；
- 负载结束后待办清零；
- 观测期间动态额度范围为 `0..20ms`，最大完整 tick 约 `65.18ms`。

该探针明确记录 `actualIntegratedPauseTested=false`，因此没有把合成调度控制冒充 IntegratedServer 暂停验证。

## 无效测试和限制

持续跨 tick 提交矩阵的动态运行完成，但固定 4ms 对照启动前发现另一会话已有 Java 服务器运行。按照隔离规则，该轮不进入任何百分比或结论。正式矩阵和冷启动矩阵均在启动前没有其他 Java 进程，并通过了候选、探针、属性和世界配置身份检查。

本轮是一轮正式矩阵和一轮冷启动矩阵，不足以证明所有机器负载、所有实体能力和长期生产流量下的稳定性。真实 IntegratedServer 暂停、连续多小时负载和所有第三方导航消费者仍是发布前的独立门槛。

## 结论

动态预算值得继续接入验证，主要收益是高并发提交后的首个 Path 发布时间和较低的主线程分配峰值；它没有降低原生搜索总成本，并使完整 tick 的尾部和冷启动尖峰变大。当前证据支持“候选机制有效”，不支持“整体性能无条件优于固定 4ms”或“已经完成生产发布验收”。
