# GPU宏观查询直接输出与逐请求提交隔离优化

日期：2026-10-26。承接[上一轮GPU常驻宏观验证](2026-10-26-gpu-resident-macro-isolated-validation-zh.md)，
响应用户“宏观寻路没法整批提交，再进行一轮优化”。
设备仍只使用RTX 5060 Laptop，源码与结果在
`.tmp/gpu-macro-direct-query-isolated-20261026-v1/`。

## 1. 结论

本轮优化有效，但没有改变零散热查询仍由CPU更快的判断。

逐请求立即提交、上一请求完成才提交下一请求，不设置凑批或tick等待：
单体型GPU单请求中位0.1164→0.0725ms（-37.71%），
混合0.1022→0.0692ms（-32.29%）。
同轮CPU双worker池逐请求交付/收集中位为0.0240/0.0179ms，
候选仍分别约为其3.02/3.87倍。

沿用旧批量接口时，候选GPU热查询中位从1.7529/2.1871ms降至0.7680/0.8502ms，
已低于有效历史CPU双worker的1.2822/1.8455ms。
但用户明确指出请求不能为批量而等待，这个吞吐结果不能替代逐请求延迟结论。

结果支持保留优化源码和GPU批量构图方向，不支持把实时零散宏观搜索统一迁到GPU。
仍为隔离程序，未修改生产源码、默认包或依赖，未提交、推送或部署。
本轮没有调用1017，不称外审通过。

## 2. 实际改动

保持原图、能力过滤、边顺序、堆同分规则、路径代价与搜索结果。
没有更换启发式，没有让实体等待凑批，也没有恢复主线程时间预算。

1. 搜索直接写入结果槽，删除独立的单线程整批路径打包内核。
   槽上界来自GPU图完成后已发布的节点数，搜索输出最多包含该图全部节点。
   这是图规模上界，不是按本次路线猜测长度，不截短路径。
2. 原来每组“先读长度、再读载荷”的两次阻塞回读改成一次有界回读。
   返回少量未用满的槽空间，换取更少的提交与同步。
   每个即时请求由一次查询上传、一个搜索内核和一次结果回读完成。
3. 基础组件图构建时，额外生成每组件两个64位邻居掩码。
   搜索按低位到高位枚举实际存在的目标，再做原能力过滤；
   不再逐个扫描所有没有连接的组件，目标迭代顺序保持。
4. 批量查询的工作区与结果槽按实际节点数组织，减少每查询按128/1024上限预留。
   逐请求槽仍预留其类别最大容量并反复复用，提交时不重新分配设备buffer或kernel。
5. 在途槽禁止重绑；图节点数与槽上界不符时拒绝结果。
   这些是槽边界检查，不是逐节点执行完整版本验证。

节点数取自已完成GPU图的`stats`，没有在每个请求里让CPU重新构图或读GPU元数据。
它依赖隔离程序的固定图身份和在途持有；不能替代生产版本、halo更新与发布规则。

本轮没有把基础稠密组件矩阵整体改成CSR，新增位图用于邻居枚举。
原碰撞暂存、基础稠密容量和超级图大容量仍保留。
共享邻接BFS保留原实现，没有把本轮性能收益推广为共享路径也得到同样优化。

## 4. 逐请求即时提交：主要判断依据

此前只有预先组好的610/3216条查询批次，没有逐请求立即返回的参考数据。
用户本轮明确了实时提交约束，所以只补该缺失范围：

- 地形、图和查询记录仍与旧批量语料相同，两组各610/3216条物理查询。
- 每次只保留一个未完成请求，结果返回后才提交下一条；不设置等待窗口或人为间隔。
- CPU使用两个线程的固定worker池，每条请求包含Executor交付、搜索与结果收集。
  因为只有一个在途请求，该项测的是worker交付延迟，不是两个worker并行吞吐。
- 旧GPU协议从保留的查询类回放，沿用原搜索、单线程打包和两次回读，
  只加可复用单请求槽的记录更新入口；它不读取候选新增的邻居位图。
- 新旧GPU共用同一组已常驻图，查询结果与CPU逐条核对。
- 3轮预热、11轮正式，每轮轮换CPU/旧GPU/新GPU测量顺序。
  请求计时包含主机记录更新、提交、等待、回读和结果数组提取，核对在计时后。
