# C 与生产基线 B：接口对齐后的直接复测

日期：2026-10-19。证据根：`.tmp/interface-aligned-baseline-20261019-v1/`。

## 结论

按用户“把测试接口对齐再测一次”的要求，使用未修改的 B、C 编译物，
补齐同一热 API 和同一冷宏观查询的直接 C/B 对照。基线热接口本身合理；
此前缺口是 C 的测试范围与拿来比较的 B 历史负载没有对齐。
本轮未改变算法、接口语义、fixture 或候选源码。

**distinct 冷查询确有相对原 B 的改善，air 冷查询仍有不利值。**
不能再把 C/R2 的全部正向结果等同于 C/B，也不再拿旧 R2/B 百分比描述当前 C。

- 热 API 的 air：三对 CPU 下降30.21%至44.14%，耗时下降30.52%至42.50%。
- 热 API 的 distinct：两对改善，第二对 CPU +4.52%、耗时+2.82%。
- 冷 distinct：两对查询均值-15.85%/-17.04%，完整操作均值-16.69%/-14.97%。
- 冷 mixed：两对查询均值-17.13%/-25.36%，完整操作均值-16.21%/-23.84%。
- 冷 air：两对查询均值+1.01%/+3.71%，完整操作均值+0.86%/+4.71%；
  第一对 P95 +15.49%，第二对中位数+3.57%。
- 冷三模式两顺序完整分配均下降14.00%至14.59%。
- 冷完整 CPU 原始累计：air +20.83%/+44.00%，mixed 第一对+12.00%；
  短窗口仍有大量零读数，保留不利值，不认定为稳定算法 CPU 效应。
- 热 air 第一对每操作分配+3.22%，热 distinct 第二对约+0.00014%（接近持平）。

当前 C 有明确的负载相关收益和残余不利项，尚不能称整体低于 B。
本轮完成对齐复测，保留所有结果，不调参或重跑以消除不利值。

## 对齐方式与技术校验

B 为 `runtime-maintenance-validation-20261018-v1/B/compiled-v3/main`，
C 为 `component-build-shortcuts-20261019-v1/C/compiled/main`。
两边均使用 B 冻结的相同依赖 JAR、共同 API 支持类和相同工具字节码，
只替换实际生产 main/resource 根。
C 的 classpath 不含 R2 或 B 的生产 main 作为回退。

1474个保护文件在开始和结束均核对哈希，包括既有候选、生产输入、默认 JAR、
旧结果、benchmark 和支持类。每版257个冻结生产 class 的身份核对通过。
类加载日志逐项核对本轮实际使用的生产类来源：
12个热 fork 各62类，4个冷 JVM 各122类，均来自对应 B/C 编译根。

热接口复用基线原始 MaintenanceApiBench.readyGraph 和 ProcessCpuProfiler 字节码，
操作为 `requestBaseGraph().join → componentCount → close`。
Trial setup 发布27个 section，预先构图并用一个 anchor 保持存活；
测量窗口不包含重复冷构图。air/distinct 各使用独立 fork。

热顺序为 B,C / C,B / B,C，Java17、512MiB、单线程，
3×1秒预热、4×1秒测量，gc/comp/process CPU profiler 相同。
共12个测量 fork、123,826,210次测量操作；
48个迭代的 CPU/操作归一化均与原始 CPU 增量和实际操作数闭合。
CPU 包含 JVM 内编译、GC、profiler 等共同成本，不替换为主线程 CPU。

冷接口复用原 ComponentColdProbe/classes-v3 字节码，B,C / C,B 共4 JVM，
air/distinct/mixed 每种24次预热、64次测量。
每次建立新 runtime，发布相同63个 section，检查空派生缓存，
从 `(2,81,8)` 到 `(77,81,8)` 执行 requestMacroQuery，等待静默并关闭 worker。
完整分配使用累计全线程计数。两个变体的起止计量窗口完全相同。
768次测量和288次预热的输入、完整走廊成员摘要、端点、连接和代价跨版本一致；
全部关闭和引用归零断言通过，无失败/陈旧重试。

本轮复用 C 已冻结的正确性证据，未声称重新执行全部契约矩阵。
没有 Minecraft 实体路线、生产接入、提交或推送。

## 当前判断与证据入口

新的 C/B 数据取代“C 尚无直接基线测试”的当前状态；旧 B/R2、C/R2 数据及其门失败
仍是历史事实，不作废、不混池、不拼接百分比。
最明确的剩余问题是 air 冷查询均值/尾部及资源读数，
以及 distinct 热 API 第二对的小幅不利值；不能用热 air 的收益代替冷 air 结论。
源码中的 BuildInput 账面固定项相对 B 仍多8 B，独立于本轮分配实测。

本轮不继续改 C、不追加样本或恢复 C2。
若下一轮研究回退原因，应针对这里的实际不利负载另定范围，
而不是再用 R2 的旧 distinct 热 API 数据描述 C。
