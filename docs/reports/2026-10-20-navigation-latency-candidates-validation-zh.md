第三项普通走廊合段未实施。生产源码、默认 JAR 及三个已有状态文档保持本轮开始时的内容，

## 结论与资格

第一项 A2 的机制、功能、异常清理验证通过，保留为隔离机制与实现候选。
8 格适用路线组的首 Path、实际到达配对中位数分别下降 66.0994、46.8724 ms，
但其中一条路线到达增加 52.0324 ms；同场不适用路线的到达中位数也下降约 47 ms。
这些净差只作探索性观察，**不足以确认 A2 的净收益、稳定加速或生产资格**。
保留的是已经通过机制与功能验证的实现，不将其列为已证明有性能收益的候选。

第二项在诊断价值门停止，未实现、未净测。47 个满足潜在后继模板资格的窗口，
准备至搜索均在同一 server tick 内接上，观察间隔最大 1.8371 ms。
当前没有足够证据支持为 200 ms 目标增加预取资源和生命周期复杂度；
这不是证明预取算法在其他负载中无价值。

**相对原生实际到达增量全面压至 200 ms 的目标尚未达成。**
首 Path 绝对值小于 200 ms 不能代替该目标；两种计时原点、原生失败分母及不利值全部保留。

## 机制与故障控制

七个原 final-window 场景全部通过：初始零边、宏观取消、替换、改块、
预算耗尽、等待后恢复、等待后取消；286 项预算断言通过。
七个场景均实际观察到宏观交付内的内联准备，
`findSegment` 方法入口都在原独立队列 lambda 中、先前 `queue` 返回之后，
没有交付内真实搜索。原探针另行核验真实原生调用数、参数和清理。

七次内联准备观察 wall 中位 0.0204 ms，P99/max 0.2825 ms，
包含真实任务入队。这是少量观察值，不是所有负载硬上界。
活跃 followup 的赋值同时设置 queued，完成回调先清空 followup 再入队；
未观察到 running/queued 均 false 的活跃残留 followup。

新增两个故障控制是因为本候选移动了准备异常边界，属于必要覆盖：

两例都确认在宏观交付内准备，真实搜索、Path 和到达均为零；
注入 setup 错误独立排除，正常关闭后 owner/pending 为零。
故障注入只在隔离诊断 helper 内，未修改候选生产字节，也不作性能样本。
机制及故障门全部通过后，才启动唯一一次 A2 净测。

原机制审计字段 `scheduledRealSearches` 名称不准确，它统计
`findSegment` 方法入口，不是实际原生调用：
waiting-resume 为两次入口、一次真实搜索，waiting-cancel 为一次入口、零真实搜索。
