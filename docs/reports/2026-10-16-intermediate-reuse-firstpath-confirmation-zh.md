# 行复用首次 Path 命中与阶段确认

日期：2026-10-16。方案：`docs/designs/2026-10-16-intermediate-reuse-firstpath-plan-zh.md`。新证据：`.tmp/intermediate-reuse-firstpath-20261016/`。

## 结论

**已确认首次Path前存在真实的跨构建行命中，并定位到一个具体的冷态抵消分支：含门输入的原始行回退。** 可复用分支在两次候选中都更短；含门回退在两次候选中都更长，第一对完全抵消并反转行阶段收益，第二对部分抵消。

一次候选运行中，6个不同含门构建的采样都显示`prototypeReferenceRows`处于解释执行；两次基线采到的该方法均为JIT编译状态。这是具体执行状态差异，尚不能证明JIT是全部耗时差异的唯一原因，也不能判断是尚未编译、反优化还是其他编译调度因素。

方向有继续研究价值；接下来应聚焦当前原型含门回退的冷态执行证据。此次没有改缓存算法或生产源码，没有转向优化其他生产工作，也没有宣布可接入生产。

## 诊断与有效性

从收尾冻结源码建立独立副本，新增原型诊断，baseline/packed使用同一runtime/probe jar、仅模式参数不同。4独立JVM固定AB/BA，同JDK17、堆256m..2048m、JFR设置、复杂混合16实体场景。真实派发均在场景就绪30秒后，目标图冷态通过；64实体全部自然成功、无whole回退、清理通过。

capture/count关闭，trace开启。没有原始源捕获，避免捕获器强持源。JFR DataLoss全部0；每次256个Base构建、每构建6个配套阶段事件，均在该运行所有实体首次真实节点发布前结束；构建编号跨线程唯一，成功发布沿用该编号。没有失败或游离阶段。

通过8项针对性检查：首次未命中、同构建重读、跨体型下一构建命中、行值一致、源/构建身份、finally清理、外部释放后源回收。源编号表为弱键，JFR输出只含元数据；构建token的center/cache引用在finally清除。

每个Rows增加5个long诊断字段，约40B，缓存64项时约额外2.5KiB／worker；候选额外执行命中计数分支。双方共同阶段、发布和请求记录相同，但候选专属命中计数、弱源注册表、事件类首次使用等仍可能交互。因此本轮是机制与阶段诊断，不是净性能矩阵，绝对时长不能替代旧验收。

## 首次Path前命中

计数在每次构建第一次触碰Rows时保存原ready位快照。原ready及快照都有该位才计入`previousBuildHits`；本次构建新填的行再次读取计入`sameBuildHits`。因此没有将同构建重复读取冒充跨构建复用。

以请求UUID关联macroOwner，使用首次宏观WorkerResult的section/version代次集合，再按同Geometry、section、version匹配已完成且已成功发布的构建，且发布时间早于该请求的精确首次节点发布。每请求范围匹配60个构建，16请求共享，去重后240／256个构建。

| 候选独立JVM | 有跨构建命中的请求范围 | 去重跨构建命中 | 其中center命中 | 同构建命中 | 未命中 |
| --- | ---: | ---: | ---: | ---: | ---: |
| packed-r1 | 16／16 | 49712 | 48032 | 32 | 2288 |
| packed-r2 | 16／16 | 48896 | 47408 | 32 | 3104 |

每请求相关范围至少10912次跨构建命中，其中至少10656次center跨构建命中。整个256构建的跨构建命中为54704／53888，单列保留，不冒充上述去重数。

这确认了首次Path之前、结果相关代次范围内已发布的构建确实复用了原始行。**代次集合也包含halo事实；它不是搜索逐图展开记录，不能据此宣称每张图都被该请求实际展开，或每次命中都位于唯一关键路径。** 共享命中没有按16实体重复累加为总收益。

## 冷态行阶段分层

每JVM均为184个`input.hasDoors=false`和72个`true`构建。含门包括halo中的门，不表示72扇门或这些实体必须穿门；该标志按现有语义使整个行阶段回退到`prototypeReferenceRows`，并不执行行缓存命中计数。

下表为256次构建中对应行阶段的调用墙钟耗时和，不是CPU时间：

| 独立JVM | 可复用184构建 ms | 含门回退72构建 ms | 全部行阶段 ms |
| --- | ---: | ---: | ---: |
| baseline-r1 | 25.0192 | 8.8152 | 33.8344 |
| packed-r1 | 8.0265 | 52.7279 | 60.7544 |
| packed-r2 | 8.2328 | 21.5066 | 29.7394 |
| baseline-r2 | 29.4022 | 10.1092 | 39.5114 |

第一对：可复用分支减少16.9927ms，回退增加43.9127ms，全部行阶段反而增加26.9200ms。

第二对：可复用分支减少21.1694ms，回退增加11.3974ms，全部行阶段仍减少9.7720ms。

因此“没有命中”已经不是本场景的解释；暖JMH优势也不能直接代表混合冷态。回退分支是已实测的具体抵消点，幅度有明显运行间差异，仅2个独立JVM／侧，不视为长期效应估计。

## JFR执行状态

直接读取原始JFR的`ExecutionSample`，以相同worker、采样时间落在对应rows事件JFR区间内进行匹配，检查`RecordedFrame.getType()`。没有将不同线程的重叠工作错配。

| 独立JVM | 采到的`prototypeReferenceRows`状态 |
| --- | --- |
| baseline-r1 | 2个均JIT compiled，其中1个为含门分支 |
| packed-r1 | 6个含门样本均Interpreted；其父`RawRowCache.fill`均JIT compiled |
| packed-r2 | 未采到回退方法；仅1个可复用`RawRowCache.fill`样本 |
| baseline-r2 | 4个均JIT compiled，其中2个为含门分支 |

packed-r1的6个含门样本分别属于buildId 28／37／128／137／170／204，并非单个异常构建重复统计。该运行首Path窗口内没有GC。

采样周期10ms，样本稀疏；packed-r2未采到回退方法不能推出它已编译或没有成本。本轮未启用编译及反优化事件，不能断言“回退方法从未编译”，也不能宣称已经证明全部因果。

“启用快路径后原始回退路径热度不同”是符合现象的待检验解释，尚不能排除反优化和编译调度等影响。需要补编译状态证据，不能用测前强制预热冒充冷态优化。

这些记录说明首次节点约0.5秒的链路还包含其他构图与交接工作，本轮未把其中任何一项认定为唯一关键路径，也没有针对它们修改生产。第一对节点变慢约46ms，第二对变快约3.5ms，诊断阶段并未证明请求总体稳定改善。

前三次首次节点窗口没有GC，baseline-r2有一次3.459ms年轻代暂停；没有扣除GC合成净耗时。原封存GC失败和首次Path净对照结果保持不变。

## 下一步边界

当前确认工作已完成：命中时段、跨构建身份、发布编号和分支耗时均有直接证据；慢含门回退与一次运行的解释执行状态差异已定位。

下一轮应只针对该原型的含门回退，补编译／反优化事件或等效直接证据，区分热度不足、反优化和其他编译因素，再提出保留门语义的冷态优化方案。不删除回退、不强制预热改口径、不盲加整服矩阵，不改其他生产优化。
