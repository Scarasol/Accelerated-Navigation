# 原型寻路性能对照报告

日期：2026-10-13

本报告记录当前生产实现与原版同步寻路在隔离原型场景中的实际测量结果。实现和解释只按现行设计 [`2026-10-13-native-detail-navigation-contract-zh.md`](../designs/2026-10-13-native-detail-navigation-contract-zh.md) 进行；废弃设计不作为验收或性能判断依据。

## 结论

两种模式都完成了全部 30 个试验：距离 8、18、28 格分别代表 `<12`、`12–24`、`24–32` 三个区间；并发为 1、4、8、16、32；每个组合重复 2 次，没有失败或超时。

当前实现通常把 `moveTo` 的主要搜索工作移出提交调用。批量提交耗时在并发 32 时仍为亚毫秒到数毫秒级，而原版会在提交调用内完成同步搜索。代价是加速版首次可用 Path 通常要等待约 100–105 ms；实体端到端时间还包含分段执行和任务收尾生命周期。

在本次平坦地面、速度 II、无障碍直线路线中，实体实际到达时间加速版没有优于原版：

- 8 格：加速版每实体从提交到到达约 1.78–2.00 s，原版约 1.60 s。
- 18 格：加速版约 4.10–4.18 s，原版约 3.85 s。
- 28 格：加速版约 6.35–6.40 s，原版约 6.10 s。

因此，本原型证明了“提交调用通常较短、Path 异步发布、共享预算可观测”，没有证明直线路径上的端到端移动更快。加速版的额外时间与首次发布、分段执行和任务收尾开销同时相关，本测试没有把这些因素做因果拆分。

## 测试口径

- 测试实体：固定的成年 Husk，地面行走，不加入自主攻击或漫游目标；永久发光和 Speed II 在两种模式中完全相同。
- 起点和终点：同一高度的平坦石台，直线距离分别为 8、18、28 格。
- 稳定阶段：实体生成后先等待 20 tick，确认落地，再在同一个 `ServerTickEvent.START` 批量提交。
- 加速版：生产服务启用；原版基线通过 `NavigationPolicy` 对 `minecraft:husk` bypass，仍加载同一 Forge、Minecraft、导航 mod 和同一测试世界。
- 原版基线含义：这是“同运行时原版同步路径”，不是卸载导航 mod 的纯净 Minecraft 基线。这样可以把 mod 初始化、Mixin 和世界加载成本保持一致。
- `Path` 就绪：原版在 `moveTo` 返回后立即读取；加速版在 tick 末尾观察到可执行 Path，因此加速版时间是一个不超过一个 tick 采样分辨率的上界。
- 实际到达：实体进入终点 1.05 格内且导航任务结束。报告同时保留批量提交到全部实体到达的时间。
- 空间：`peakHeapDeltaBytes` 是 JVM 已使用堆相对试验开始的峰值增量，反映整个进程的内存压力，不等同于算法的 retained size。
- 两次重复：表中每个组合先对实体级数据取中位数，再对两次重复取中位数；“全部到达”仍取每次批次最后实体到达后再聚合。
- TPS/MSPT：`observedTps` 从批量提交开始计到该试验全部实体完成；`workMsP95` 是探针从 tick START 到 END 采样点的工作时间 P95，是主线程负载代理，不等同于完整 tick 间隔。原始 JSON 另有 `tickIntervalP95Nanos`/`tickIntervalP99Nanos`。共享调度器的 `chargedNanosDelta` 单独保留作内部计费参考。

## 并发和资源观察

加速版在全部并发档位保持约 20 TPS。30 次试验中的最低观测 TPS 为 19.972，原版最低为 19.957；两者没有出现本场景可见的 TPS 崩溃。加速版单次 tick 工作 P95 最大值为 3.752 ms（18 格、并发 32），原版最大值为 2.224 ms（8 格、并发 4）。这说明共享预算把搜索工作压在较小的 tick 区间内，但并发提高后主线程工作仍会出现尖峰。

进程堆峰值不是加速版的优势：代表性并发 32 下，加速版的中位堆增量约为 27.6、42.1、57.9 MB，原版约为 19.4、30.2、25.2 MB。每种模式 30 次试验中有 29 次没有发生 GC，另 1 次发生一次 GC；因此这些峰值没有经过 GC 归一化，不能据此推导长期驻留内存。加速版完整日志中的拓扑 worker 最高 base cache retained bytes 约 72.7 MB；原版同运行时背景拓扑任务约 77.8 MB，说明该项还受到启动和预热行为影响。

加速版的 `nativeCallsDelta` 随并发和距离增加，说明分段执行仍调用真实原版 `PathFinder`；完整运行结束时共有 366 次成功宏观查询、8 次拓扑物理搜索成功，没有失败试验。原版基线没有加速服务记录，`nativeCallsDelta` 为 0 是因为它直接走原版同步调用，不代表没有执行原版 `PathFinder`。本测试直接调用外部 `moveTo`，`nativeDecisionCallsDelta` 为 0，因此它不是 `createPath`/POI 决策查询成本的覆盖测试。

## 限制

本次只覆盖平坦地面直线路径，不能推断楼梯、门、复杂障碍、目标漂移、区块加载或速度 IV 下的端到端结果。并发实体使用独立 z 轴位置，避免拥挤碰撞；结果重点反映提交和分段服务开销。加速版 Path 就绪时间以 tick 末观察为准，且内存峰值是 JVM 级代理量。加速版的“到达”包含生产任务的最终稳定和收尾判定，不是纯粹的物理位移计时；`observedTps` 是试验区间的平均 tick 速率，不是独立的长期 TPS 采样。`workMsP95` 包含同一运行时其他主线程工作，不能单独归因于导航搜索。若要证明复杂城市路线中的总体收益，还需要在真实障碍和区块变化下追加同口径测试。
