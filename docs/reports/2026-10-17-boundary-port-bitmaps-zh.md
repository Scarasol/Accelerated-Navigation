# 连通组件边界候选位图求交验证

日期：2026-10-17。

结论：选择**共享合法锚点行位图、按当前组件筛选、按原位移对齐求交**作为本轮候选。它比新增整section六方向位更适合当前实现，既能在基础层Boundary依赖创建前证明某些组件没有候选，也能让完整Boundary构建只枚举两端匹配的位置。独立差分和运行时契约已通过，完整Boundary函数有局部收益；本轮没有服务器任务数或整体worker净收益证明，不接入默认生产。

证据根：`.tmp/boundary-port-bits-20261017-v1/`。本轮基于当前生产重新冻结输入，没有叠加上一轮Top-K、空格位图或运行时上下文候选。

## 1. 为什么选择这种构型

现有Base的`mayExit/mayEnter`已经用组件包围范围和能力筛选；Super已经有14位潜在出口。地面移动包含水平相邻且高低差一个section的位置，实际是四个水平方向各三种邻接，加正上正下。单纯增加六位摘要没有填补主要缺口。

整section某方向有口，不能代表当前组件到得了这个口；两侧方向都为1，也不能代表开口位置对齐。因此本轮保存位置，并把组件身份留在原压缩标签中：

- 复制构建时已有的`legalMask`，64个long，共512字节，按需提取沿x方向的16位行。
- 转置出256个short，共512字节，供E/W面读取沿z方向的16位行。
- UP/DOWN面沿x取行。组件ID仍由原`componentAt`确认，各属于自己的section，不跨section比较编号。
- 不为每个组件复制六个完整面。碎片化夹具有64个组件，索引数据量仍约1 KiB；对象、数组头和Base引用的估算/实测另计。

一个面的256位仍等价于四个long，但按16位行处理高度变化和水平位移，可以直接隔离行边界。当前short转置避免第二套long行的移位提取；没有宣称它已经在所有硬件上优于其他布局。

宽高、流体和门能力使用原几何键及`deriveLegalAnchors`的结果，不再独立重算侵蚀。参考了Recast官方`rcErodeWalkableArea`实现，原文和哈希保存在`research/`；没有复制Recast算法代码，也没有用体素侵蚀代替原精确碰撞。

## 2. 求交必须匹配原有位移

以下是现有`boundaryLinks`的候选范围，原型全部保留：

| 通道/面 | inset | distance | dy | 水平方向 |
| --- | --- | --- | --- | --- |
| VOLUME水平 | 0 | 1 | 0 | 当前面 |
| VOLUME垂直 | 0 | 0 | 当前面stepY | 无水平位移 |
| GROUND水平 | 0..2 | inset+1..3 | -4..1 | 当前面 |
| GROUND向上 | 0 | 1..3 | -4..1 | N/E/S/W |
| GROUND向下 | 0..3 | 1..3 | -4..1 | N/E/S/W |

水平面取源`inset`行，与邻居反向面的`distance-inset-1`行求AND；目标高度为`sourceY+dy-16*sectionY差`。N/S的行位是x，E/W的行位是z，不对水平面的法向位移做切向移位。

垂直面取源x行，选择目标`sourceY+dy-16*sectionY差`及`sourceZ+directionZ*distance`行，再按`directionX*distance`对齐x位。越出当前目标section的坐标返回零，与原`componentAt`的范围一致；不会从另一个对角section偷取数据。16位源掩码限制了左移的范围，不会跨行绕回。

求交非零后用`numberOfTrailingZeros`和`bits &= bits-1`枚举位置。完整构建仍为每一个匹配位置执行原`collision.open`，然后生成原descriptor、能力mask、位置mask和lowerBound。端点能容纳实体不能证明运动过程能通过。

相对原实现的包含性依据是：每个原Boundary边必先通过源、目标的组件标签检查，再通过同一个descriptor的碰撞检查；复制的合法锚点位与标签存在性一致，位图枚举覆盖同一组端点对。求交没有增加碰撞放行规则。这里证明的是相对当前实现的等价性，不是完整Minecraft物理语义证明。

## 3. 放置位置与依赖语义

隔离实现包含三个位置对照：

1. `indexed-main`：只构建位置索引，Boundary仍走原标量循环，用作完整输出oracle。
2. `intersect-main`：完整Boundary按位求交并只枚举置位候选。
3. `dependencies-main`：再在Base正向/反向宏观扩展中，读取已捕获的两侧拓扑、发现Boundary尚未就绪时，按当前组件检查候选；零则完成该part，非零保留原Boundary依赖。

前置筛选正向限定源组件，反向限定原前向边的目标组件。反向搜索是转置原有向边，不是重新要求物理上能沿反方向跳回。筛选使用完整结构能力范围，未擅自收紧垂直distance=0的能力语义。

邻居缺失时仍产生BASE_CLUSTER依赖；无拓扑、未捕获和过期状态不通过位图解释成零。使用原捕获、有效性、stamp与恢复逻辑，不增加跨revision缓存。已有Boundary直接读取，不重复做前置筛选。本轮没有增加Super Boundary依赖前的组件对位图摘要。

非零匹配不能直接推出精确宏观边，也不能预先知道所有未构建邻居的数据依赖。可直接决定的是“当前有效端点对根本没有结构候选”，从而省掉这一部分Boundary等待与构建。

## 4. 正确性与潜在剪枝量

三种隔离位置均通过：

- 515,840项独立标量xyz枚举与位图行集合比较，覆盖两个通道、六面、14邻接、完整结构位移范围、随机位和行端位。
- 737,280项合法锚点位与组件标签存在性核对。
- 2,520组完整Boundary输出逐项一致，包含873条边、2,898个band；比较descriptor、能力、四个位置word和lowerBound，未仅比较数量。
- 源组件与原前向目标组件的零拒绝均没有删掉oracle中的边。

另有四项定向检查，原循环与位图循环均通过：方向相同但开口错位、同section的两个隔开组件、双端局部组件编号作用域、匹配的WEST方向。重复城市列的任意组件有连接，不会被误用为当前组件一定有连接。

`dependencies-main`通过Core 9项、boundary-recovery 9项、macro-commit 4项、Door控制28项及Door/图导出集成。恢复与反向单向下落用原运行时契约验证。

## 5. Java成本

JDK17.0.18+8、JMH1.37、GC profiler。完整Boundary与完整Base构建按固定B/C/C/B顺序串行运行，每参数两个独立fork；每fork三轮500ms预热、四轮500ms计量。筛选和索引自身成本各两个fork。正式共60个测量fork，均值仅表示这些fork，未获得统计性能资格。

完整`boundaryLinks`，单位ns/op：

| 输入 | 原实现 | 求交枚举 | 变化 |
| --- | ---: | ---: | ---: |
| 平地 | 13,451.6 | 10,625.3 | -21.0% |
| 固定城市列重复邻接 | 5,213.7 | 2,838.7 | -45.6% |
| 开口错位 | 3,363.9 | 314.0 | -90.7% |
| VOLUME全空空间 | 13,452.0 | 12,654.6 | -5.9% |
| 64个内部空腔组件 | 811.0 | 176.6 | -78.2% |

正式城市计时固定`city-column--2`，两侧各4组件、实际2条Boundary边。内部空腔明确是64个非空组件、零跨面边，不能冒充有跨面路线的性能。五组均在正式计时前逐一预检。

平地/城市完整Boundary分配约1,912/2,304 B/op，基本不变；VOLUME约1,384→1,416 B/op，内部空腔约1,504→1,540 B/op。这些小幅分配增加也保留，没有把位运算解释为必然少分配。

组件0的独立前置筛选分别约17.6 / 513.6 / 211.3 / 7.0 / 13.1 ns/op，对应上表五组，均未测到稳态每次调用分配。城市组件0没有匹配，尽管该section的其他组件有两条边；这是组件筛选的真实区别。此表是已知两侧拓扑下的helper成本，不包含捕获、等待集合、队列与任务生命周期。

完整Base构建B→C均值（微秒）分别为36.294→35.524、25.806→23.388、19.781→19.185、50.189→50.007、17.343→17.538。多个fork范围明显重叠，不能从均值下降推断索引免费；例如城市B为28.712/22.900，C为23.117/23.659微秒，VOLUME B为45.923/54.454微秒。新增分配约1,064～1,088 B/Base，估算保留成本约1,088字节。

为区分正的索引构建开销与整方法编译、分配和波动，追加了独立索引构建基准，没有重跑原有完整方法：

| --- | ---: | ---: |
| 平地 | 402.9 | 1,080 |
| 固定城市列 | 276.9 | 1,080 |

稠密VOLUME需转置更多置位，成本明显更高。按本夹具“两侧都新建索引、随后重复同一Boundary查询”的简化静态算术，约需7次VOLUME查询才能抵消两侧索引构建；内部空腔约需2次，平地/城市一次的函数节省已大于两侧独立索引时间。该算术不含缓存、驻留、GC和任务共享，不是实服临界点，也不能据此设一个通用硬门。索引对象约1,080字节与完整Base额外约1,088字节的差别包含对象布局/引用及JIT分配变化。

本构型优先作为GROUND和可复用Boundary查询的候选；稠密VOLUME的驻留与摊销仍需单独评估。最终汇总使用`summary-v2.json`，原50-fork汇总`summary-v1.json`保留。

## 6. 审查、失败原件与继续范围

DeepSeek使用项目已有`tools/review/deepseek-review.mjs`，仅发送自包含文本，禁止工具与联网，配置哈希未变。第一轮答复为REQUEST_CHANGES，脚本因答复未按规定起行而没有识别结论，退出1；原答复仍完整保留。部分意见误把垂直x行公式当作E/W水平公式，并要求把反向搜索改成反向物理移动。本轮用实际代码、原前向payload语义及集合差分回应，没有照单采纳。

第二轮`review-closure-v2`返回`ACCEPT_SCOPED`、本轮必须修改项无、退出0，仅接受已给定实现的局部核验范围。它不替代本地测试，也不批准生产或整体性能。

最初`bench-links-v1`在碎片化夹具上失败：孤立单层空格不满足所选1.4高度，实际组件数零。原批次保留但不计入正式结果；随后改为2×2×2内部空腔并预检64组件、零跨面边，再固定输入运行v2。`harness-v2`还保留一次辅助Java检查的语法编译失败；正式辅助夹具使用`harness-v3`。没有复跑未变化候选以挑选较好的性能fork。

本轮优先保留求交枚举和组件级前置拒绝作为后续候选。后续需量实际命中的BASE_BOUNDARY数量、重复共享程度、索引驻留和完整worker成本，再决定是否组合上一轮优化。索引会增加每个Base的驻留，未解决所有宏观依赖，更没有解决全部运行时锁内业务。本轮未启动Minecraft服务器、未构建或替换发行Jar，61份生产输入及两个默认Jar以`final-seal-v1.json`封存核验。
