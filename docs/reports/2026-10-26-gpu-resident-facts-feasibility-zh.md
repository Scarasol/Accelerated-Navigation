# RTX 5060常驻地形事实与混合体型构图隔离研究

日期：2026-10-26。承接用户“混合体型是怎么混合的，你可以继续研究”。
仅使用RTX 5060 Laptop，继续隔离研究，不修改生产业务源码。
前轮报告为[GPU位图后半阶段研究](2026-10-26-gpu-topology-isolated-feasibility-zh.md)。

## 1. 结论

已把此前仍在CPU上的行准备和精确形状判断移到GPU，
与前轮位图内核在同一有序队列连续执行，只在末尾回读。
508组输入的946,912个32位中间行字与67,056个64位输出字全部与生产结果一致。

事实已常驻时，混合64/256任务的位图阶段中位为0.1349/0.3281ms，
对有效历史CPU的1.9878/9.8062ms下降93.21%/96.65%。
这些数不包括首次事实序列化与上传，所以另补缺失的逐批重新装载计量：
混合64/256为1.0318/2.6041ms，仍分别下降48.09%/73.44%。
但常规体型256的重新装载为3.5384ms，高于CPU的2.7956ms，增加26.57%。

当前证据更支持“共享冻结地形事实，为多种体型执行批量构图”。
不支持把所有单体型冷任务改走GPU；单任务常驻状态也没有中位优势。
没有实现完整GPU拓扑构图或生产接线，不宣称整个导航快96.65%。

## 2. 混合体型具体如何混合

直接复用既有`KernelCorpus.bodies()`，顺序如下。尺寸单位为方块。

| 编号 | 物理宽×高 | 通道 | 接受流体 | 可开门 |
| --- | --- | --- | --- | --- |
| 0 | 0.6×1.95 | GROUND地面 | 否 | 否 |
| 1 | 1.4×2.9 | GROUND地面 | 否 | 是 |
| 2 | 0.9×1.4 | VOLUME体积 | 是 | 是 |
| 3 | 0.125×0.5 | GROUND地面 | 否 | 否 |
| 4 | 0.6×1.95 | GROUND地面 | 是 | 是 |
| 5 | 1×1 | GROUND地面 | 否 | 否 |
| 6 | 2×2 | GROUND地面 | 是 | 否 |
| 7 | 3×3 | GROUND地面 | 否 | 是 |

因此这里的“混合体型”也混合了通道与能力，不能将耗时差全部归因于身体尺寸。
例如0与4尺寸相同，但流体和开门行为不同；2使用体积通道。
这些是算法配置组合，没有声称分别对应某个具体生物。
格宽高使用向上取整值，精确几何仍使用真实物理宽高，未将0.125粗化成完整1格身体。

59种既有地形各配上述8组，构成472个任务的性能池。
语料中每组体型/能力等权覆盖，不代表真实服务器的实体数量或请求占比。
第i次采样从`floorMod(i*97,poolSize)`开始，连续取批量个任务，越界循环；
不是每批固定八等份，也不是把同一个实体的身体在执行中修改。
常规体型池只取编号0，仍覆盖同样59种地形，不表示地形简单。

一个任务是“一个section快照＋一种体型/通道”，不是一个实体并发请求。
混合64任务通常共享8至9个地形快照，256任务共享32至33个；
常规256任务会循环使用59个输入，不是256个独立世界section。
已有的完整拓扑缓存命中时，应直接复用结果，不能为GPU凑批而重复构图。
另有36组宽高边界组合只用于正确性，总计508组，不进入正式性能池。

## 3. 本轮原型

证据目录：`.tmp/gpu-resident-facts-isolated-20261026-v1/`。

CPU先将冻结事实及精确形状序列化为常驻数据：

- 每格保留四个事实标志及形状ID；形状表保留种类、量化盒坐标及开门属性。
- 每个构图输入保留27个邻域事实引用与是否包含门；缺失邻域继续表示缺失。
- 每任务只上传8个32位字，即输入ID、格宽高、通道、真实宽高和两个能力标志。

GPU连续执行`prepare_rows`与前轮原样复用的`legal_anchors`：
先恢复volume/ground/特殊封闭碰撞行，再算合法位置和净空位图。
保留流体过滤、未知形状、严格盒相交、开门地面规则、下方邻域支撑、
偶数宽度对齐与一格体型封闭掩码，没有改宏观或详细寻路算法。
原有完整碰撞行的特殊位移也保持，没有在研究中顺手更正生产语义。

每任务稳态上传由前轮7,456字节降为32字节，末尾仍回读1,056字节。
59个唯一事实对象、29个唯一形状共974,908字节设备常驻数据；
加256任务的查询、行和输出缓冲，共3,162,172字节设备缓冲。
这不是整个Java进程、GPU上下文或完整拓扑的内存占用。

CPU事实采集仍未迁移，GPU不读取世界对象或执行Forge回调。
参考NVIDIA官方指南关于减少传输、批量交付和中间结果保留设备的原则，
但本轮性能结论只来自本项目实测，不套用文献加速倍数。
参考原件仍使用前轮保存的`cuda-best-practices.html`。

## 4. 历史数据与测试口径

复用前轮正式轮换结果`result-all-v2.json`中的5060 CPU及GPU数据。
原生产73份源码/资源、8份历史输入依赖、6份实际编译生产类及前轮30份研究证据
SHA-256全部保持，体型、场景、批量、12轮预热和41次正式采样保持。
新候选与历史数据来自不同JVM，不称本轮同场配对，也不报告新的“41对全胜”。
没有重跑原生、生产游戏矩阵或历史CPU性能基线。

本轮新增两个离线研究JVM：

1. 常驻事实：每批包含scratch重置、查询打包上传、两个GPU阶段、
   阻塞回读、解码和合法/净空位图复制发布；初始化及一次性事实装载另记。
2. 每批重新装载：为相同输入重新序列化事实、分配主机/设备缓冲、上传、
   计算、回读发布，并包含结果比较及本批资源释放，观察缺失的首次装载成本。

第二项是必要新增项，因为第一项无法回答常驻前提是否掩盖了准备成本。
该项复用既有场景与参数，只补候选成本，不使历史CPU失效。
它仍是已经冻结的快照回放、已建立GPU上下文/程序后的装载，
不是冷世界加载、真实worker吞吐或完整服务器延迟。
逐批重新分配较保守，正式缓冲池可能减少成本，但本轮没有把未实现的收益算进去。

## 7. 正确性与尚未实现的部分

508组所有1864字中间行、132字最终位图都逐字相同；
两种测量的所有正式批次也检查完整输出，GPU资源均已释放。
这证明所测位图阶段，不证明完整GPU拓扑对象已经等价。

尤其是生产`build()`还使用`scratch.haloUsed`生成边界快照、邻域版本与指纹依赖；
当前研究只回传位图，没有回传这一依赖使用记录，不能直接替换原生产阶段。
组件标记、方向能力边、稳定组件编号/锚点/排序、完整拓扑发布也未在GPU实现。
下一候选若对接完整构图，必须一起恢复这些已有业务语义，避免动态世界缓存失效缺口。
这不是要求新增多层防御检查，而是补齐现有输出契约。

仍未测真实world采集、worker凑批与排队、修改/取消后的发布、
游戏渲染争用、整场CPU总量、GPU功耗和完整构图收益。
前轮CPU上下文中该位图阶段约占常规/混合完整构图中位的9.11%/37.99%，
因此不能把本轮阶段96.65%的下降写成完整构图或TPS下降同等比例。

## 8. 下一步方向

继续研究后台批量构图有价值，正式GPU接入尚早。
优先减少“原压缩事实/局部形状palette到GPU”的逐格重新解释与临时分配，
让一个冻结事实只序列化、上传一次，供实际缺失的不同体型拓扑使用。
可研究直接传递既有压缩标志和局部形状palette，避免每格重复哈希查找并展平全局形状ID；
这是下一方案方向，尚无该格式的实测收益。

随后应测包含组件、规则连接、依赖和最终快照发布的完整构图流程。
若继续迁GPU，应连续完成这些阶段，减少中间往返；
组件编号和边顺序需与现有确定性结果对齐，不能改变宏观选线。
前台少量请求继续有CPU路径，不为凑GPU批次增加等待。
设备选择、启用与批量策略保留可配置需求，本轮没有添加生产开关。

本轮没有调用1017或冒称外部审查通过。
未修改生产源码、默认JAR、构建依赖，未提交、推送或部署。
报告、两轮原始数据/日志、Java与CL源码、统计脚本和身份保护记录均独立保存。
