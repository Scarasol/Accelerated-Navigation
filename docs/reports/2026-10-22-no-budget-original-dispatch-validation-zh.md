# 取消预算、保留原派发与 worker：隔离验证

日期：2026-10-22。目录：`.tmp/scheduler-no-budget-20261022-v1/`。

本轮 U 三档共 **2688/2688 实际到达**，三个 JVM 均正常退出、清理通过，
`nativeDecisionCalls=0`、`failures=0`。首 Path 整批 P95 对生产 P 和 75ms 方案 B
均为 18 场全部改善；同路线实际到达时差中位数对 P 全部改善、对 B 为 17 改善/1 增加。
取消预算有明确的延迟收益观察，但相邻 tick 间隔和少量尾部、CPU 指标不利，
不是全项胜出，也不据单轮数据授予稳定性能或生产资格。

## 需求纠正

上一轮 I/I2 把取消预算扩大成了在 `submit` 内同步执行已就绪队列，改变了逐实体
`moveTo` 的提交与执行交错；I2 又改了服务初始化次序。这不符合本次要求。
**I、I2 及其后续 profile 定位结果，全部作废用于“只取消预算”的方案评价。**
旧报告、源码、数据与判词完整保留，不改写成新候选的证据。作废说明另见
`supersession.json`；75ms 方案 B、生产 P、同包原生 N 的有效历史不因此失效。

新候选 U 直接复制当前生产，从未采用 I/I2 的导航服务修改。仅隔离副本
`NavigationScheduler.java` 变化：

- 删除额度、补额、扣额、起步余额、墙钟截止、`haveTime` 及搜索步数/时间额度的执行准入。
- `submit` 仍只入队并返回；worker 唤醒仍先回主线程、只入队。
- 仍在原 END 入口和原 `server.tell(TickTask)` 就绪回调派发，不在提交栈内同步清空队列。
- 两个拓扑 worker、宏观寻路、窗口准备、详细寻路及服务生命周期保持生产代码。
- 保留优先级、维度轮转、取消、替换、请求身份、关闭及异步依赖管理。
- `account()` 只观察实际耗时，不再维护预算。兼容字段中 grant、reserve、balance 均为 0，
  表示预算禁用，不表示没有执行成本；CPU、分配和耗时仍取原计量。

队列容量和生命周期检查仍是请求管理，不作为时间预算。一次派发执行当前能够推进的工作，
直到队列清空或仅剩等待依赖的工作；没有另设 75ms 上限，也不能抢占单次原生寻路。

## 尖峰与包络外执行

只看完整 tick 会漏掉就绪回调在 tick 包络之后执行的成本。沿用 B 的固定容量
drain 时间戳账本，每个 drain 两次时钟读取，成本包含在结果内；
P/N 没有该账本，其 extent 缺失保留为空，不为补齐重跑历史。
extent 是 tick 起点至最后所属调度结束的跨度，可能包含间隙，不等于全部 CPU busy。
相邻间隔则是连续两次 tick 起点之差，包含原生等待/睡眠及包络外工作，
不将其倒数冒称持续 TPS。
