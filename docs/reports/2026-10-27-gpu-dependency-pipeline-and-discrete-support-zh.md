# GPU依赖推进隔离验证与主流独显支持核对

日期：2026-10-27。任务依据为
[GPU宏观后端与CPU架构对齐方案](../designs/2026-10-27-gpu-macro-backend-cpu-architecture-alignment-zh.md)。

## 1. 结论与覆盖边界

本轮实现并验证了生产执行器驱动的GPU依赖流水线：
基础图、边界、父图及查询分别依赖实际生产者，多个任务可同时在途，
搜索在其余构图尚未结束时开始。乱序队列及多有序队列两条路径的功能控制通过。

性能不通过。逐图细碎派发的第一版出现显著回退，
合并同依赖任务、取消中间主机回调等待后，最终完整流程中位为
44.5870/163.0758ms，仍比有效历史GPU的29.4608/46.2247ms高51.34%/252.79%。
不能把“同时在途”当作设备上不同内核实际重叠执行，也不能因混合负载胜CPU而忽略旧GPU更快。

这是冻结事实上的依赖执行验证，不是完整生产宏观后端。
真实MacroFlight/完成走廊缓存、world/halo版本接线、按需SharedRows、
真实缺图保状态续行、分层具体连接和完整走廊资产交付、动态设备缓存容量及背压尚未接入。
未修改生产业务、默认包或依赖，未建立生产准入。

其他NVIDIA/AMD独显的官方运行时覆盖已核对；
本机实际计算仅运行RTX 5060 Laptop，没有其他独显的正确性或性能实测。
AMD核显只枚举能力，未执行内核。

## 3. 三份隔离实现

全部位于`.tmp/gpu-macro-dependency-runtime-isolated-20261027-v1/v2/v3/`，
这里的末尾写法分别指三个独立目录；已测源码和原始结果分别保留。

### 第一版：独立图事件与逐组查询

直接复用未修改生产`TopologyTaskExecutor`：
两个worker、原优先级/BUILD许可和合并CONTROL通知。
BUILD任务只提交GPU命令，提交后即释放CPU构图许可，不持有许可等待设备完成。
GPU并发数量不受CPU两个worker限制。

每张基础图分为行准备、合法位图、组件、连接边四条命令；
每个边界、父图单独派发。每个family/图的已有查询分为独立组，
每组有独立上传、搜索和回读缓冲。
主机乱序队列使用显式事件依赖；无乱序时采用上传、两构图、搜索、回读五条有序队列。
共享JNA回调只通知生产CONTROL任务，不在驱动回调内运行导航状态处理。

只适配两个工作组内核的全局偏移编号，几何、组件编号、
边顺序、搜索及同分语义不变。对每张图的四阶段分别建立完成关系。

### 第二版：有限同依赖任务组

第一版把GPU可在一个NDRange中并行完成的工作拆得过碎。
第二版将具有相同生产者依赖集合、会同时就绪的任务分为最多32图的有限组，
通过额外task-ID入口映射到原始内核体。原内核仍保留用于固定配置和核对。
32是本次隔离候选的有限分组上限，不是为某条地形选择的阈值，也没有证明为所有显卡最佳。

不同依赖仍独立推进；没有新增凑批定时器、下一tick等待或主线程预算。
同组图共用命令完成边界，不能声称工作组逐个独立通知CPU。
查询按其所属图任务组及family合并，不更改实际查询内容。
分组描述与固定输入相同，在计时外配置；真实动态请求的分组成本尚未测量。

每次改变共享kernel的task-ID参数及enqueue在同一所有权锁内完成。
每个任务仍有互不冲突的图空间，查询组各有自己的在途暂存。

### 第三版：原生事件直接串联

第二版仍在生产者实际完成、Java回调交回后才提交消费者。
第三版在生产者的事件句柄建立后即可提交后继命令，
由设备wait list保证后继实际计算晚于生产者完成。

“命令已提交”和“设备已完成”分别记录：
提交句柄只用于建立DAG；构图完成事件仍控制结束记账和生命周期，
最终结果仍需实际回读完成才交付。不是提前把未完成图发布成可用资产。
事实上传到构图之间也使用原生事件，不再等待一次中间Java回调。

## 4. 功能结果

两种队列路径均通过以下核对：

- 合法位图、逐格组件标签、组件元数据、能力掩码、代价及邻居位图；
- 边界band、父图展开/凝缩CSR、搜索路径、代价及同分结果；
- 每个设备消费者start不早于其实际生产者end；
- 搜索开始时间早于全部构图完成时间；
- 所有查询和构图完成后才释放事件/缓冲，生产执行器失败任务为0。

最终版单体型2/4/4个基础/边界/父图任务组，10个查询组；
混合15/17/6个构图任务组，27个查询组。
最大在途构图任务组10/38、查询组10/27。
这些计数不代表同时占用SM的内核数量。

## 6. 现有事件能定位到什么

第一版带事件命令数582/3612条；第二/三版48/166条。
第一版各内核事件区间累计几乎等于区间并集，
独立命令没有形成可观的设备执行重叠。
乱序支持允许重排与表达依赖，不保证驱动让不同内核同时执行。

第二版中位对应样本，单体型上传后到首个构图存在18.936ms空档，
其中18.903ms发生在后继命令入队之前；混合为19.114ms，
其中19.025ms发生在入队之前。
单体型另有12.872ms的构图到查询上传空档，其中12.835ms也在入队之前。
因此至少能直接定位到主机中间衔接等待，不能解释成上传带宽慢。
没有进一步线程采样，不能把全部等待细分为JNA挂接、驱动回调或Java唤醒。

## 7. NVIDIA与AMD主流独显支持

实现使用OpenCL C 1.2，不依赖CUDA、NVIDIA专属内核扩展、
warp固定宽度、设备端enqueue或厂商型号白名单。
主机侧目前为Windows JNA `StdCallLibrary`研究绑定；
厂商Linux运行时支持不等于本工程已经验证Linux。

| 独显范围与代表型号 | 官方依据与本轮判断 |
| --- | --- |
| NVIDIA RTX 20/30：2060、3060、3070等 | NVIDIA官方Windows/Linux驱动提供CUDA-capable GPU的OpenCL；符合后述能力条件时可作为本后端候选。未逐卡实测。 |
| NVIDIA RTX 40：4060、4070、4080等 | 同一OpenCL路径，无5060专用依赖；需对应型号驱动、实际编译和oracle控制。未逐卡实测。 |
| NVIDIA RTX 50：5060、5070、5080等 | 本机仅5060 Laptop实测；其他型号仍是条件支持，不外推性能。 |
| AMD RX 6000：6600、6700 XT、6800等 | AMD官方Windows 7.1.1矩阵明确Runtime含HIP和OpenCL，列出这些产品的运行时支持；Adrenalin列表提供驱动产品覆盖依据。需本内核能力及编译核对，未实测。 |
| AMD RX 7000：7600、7700 XT、7800 XT、7900等 | 同一官方Runtime矩阵覆盖，采用AMD OpenCL运行时；不要求用户安装完整HIP SDK。未实测。 |
| AMD RX 9000：9060 XT、9070/9070 XT等 | 同一官方Runtime矩阵及Adrenalin产品列表覆盖；具体设备仍需逐机能力、编译和正确性控制。未实测。 |

核对用AMD 25.10.2是一个已发布且包含所需产品系列的官方驱动样本，
不是宣称它是2026年最新驱动，更不要求新显卡安装不适用的旧驱动。
Khronos认证列表能够证明其中明确列出的实现，不把某张卡的认证外推成整个系列逐卡认证。

实际门槛应以能力为准：

1. NVIDIA/AMD独显及可用OpenCL C 1.2编译器；
2. fp64与全局32位原子操作。精确几何使用double，不为适配换float；
3. host profiling事件、合法的64项工作组及各kernel具体上限；
4. 显存、最大单次分配、端序及当前Windows主机绑定满足要求；
5. 原始内核实际编译成功，并通过CPU oracle检查。

设备预检已按vendor ID、非统一内存、fp64、工作组、端序及编译器筛选，
不再按“5060”名称选择。
编译采用`-cl-std=CL1.2`；本机组件/边内核的实际最大工作组为256，
设备总上限为1024，说明不能只检查设备上限。
预检通过仍不等于整个程序或每张显卡已经通过测试。
未来生产接线应在能力、编译或控制失败时保留CPU后端，
本隔离程序目前是失败即中止，不冒称已经实现生产降级。

乱序不是准入硬条件：无乱序时的五有序队列路径已经在5060强制验证通过，
但这不是AMD驱动正确性或性能实测。
没有安装驱动或额外SDK，没有在AMD核显上运行内核。
消费级fp64速率和驱动策略不同，不能按型号算力直接推导本负载加速比。

AMD 7.1.1矩阵明确区分Runtime和完整HIP SDK，且明确Runtime包含HIP及OpenCL。
本报告只采用该矩阵的Runtime列，不把HIP SDK开发支持列当OpenCL门槛，
也不因部分RX6000的HIP SDK不支持而判本后端不可用。
另保存的可变latest矩阵没有单独作为OpenCL支持结论依据。

## 9. 下一步

依赖事件可以保留为架构方向，但本候选不接生产、不替换有效旧版本。
后续优先研究同一有限任务组内的构图算法粒度：
边界/父图的工作组协作、组件/连接边串行支路，以及能否在同图内合并阶段，
在不引入跨工作组全局屏障、占位自旋或凑批等待的前提下恢复GPU利用率。
不能只扩大组长恢复整场全阶段屏障，也不能继续用更多Java worker掩盖设备结构问题。

完成上述计算粒度研究后，再接实际生产缺图、缓存、版本及资产交付；
当前冻结结果不足以评价Minecraft渲染争用、实体响应/到达、TPS或完整后端准入。
