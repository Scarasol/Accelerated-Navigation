# 原始行复用的 tick p99 定向诊断

日期：2026-10-16。本轮完成阶段诊断，没有形成代码修复。原生产接入的正式净性能 **FAIL 保持，生产发布尚未放行**。旧报告和封存证据只读。

## 范围与方法

用户授权继续根据工具反馈定向优化，并确认探针留在 `.tmp`，不进入生产源码和正式发行包。本轮新证据目录为 `.tmp/intermediate-reuse-p99-20261016/`。

直接测试上一阶段已经冻结的生产基线与生产候选，而非简化内核。保持原场景探针和生产包不变，两臂共同临时加载新的外部阶段探针。只追加复杂场景 AB/BA 两对、四台独立 JVM 和新世界，不执行不变算法的正式净性能重跑，不改变门限。

每台仍在场景实际 ready 后至少 30 秒提交 16 请求，29 秒在另一 tick 检查目标 Base/Super 冷态。实际延迟为 30.009691–30.019028 秒。四台共 64 请求全部自然成功，整段回退为零，停止清理通过，JFR DataLoss 为零。每台实际有 80 次详细寻路，每请求 5 次；请求窗口内各 64 次 Base 构图及配套 anchors 阶段事件。

新的共同观测包括：

- 完整 tick 事件，以及两处 `NativeNavigationSearch.find` 调用的 `try/finally` 阶段事件，80 次调用全部覆盖。
- Base 构图与 `deriveLegalAnchors` 阶段事件。后者包含原始行生成、侵蚀及 sealed-cell 过滤，不能视为纯行填充。
- worker command 阶段与任务类型；`TopologyService.queueServer` 入队、实际执行起止时间。
- 双方相同的 1ms 执行/原生采样、编译、反优化、安全点和锁事件。

CPU 计时使用 `getCurrentThreadCpuTime`，实际最小正增量为 **15.625ms**，多数完整 tick 的增量为零。这是本机计量限制，不能把几毫秒 tick 的“墙钟减 CPU”解释为实际等待时间。本轮以调用墙钟、阶段时间线和采样栈作为诊断依据，没有据 CPU 差值归因为排队或抢占。

四台 launch 时均未观察到其它 Java 进程，不声称消除整段生命周期中的所有操作系统和后台干扰。共同探针仍可能与被测算法发生不同交互，诊断时延不能替代无深度探针的正式成绩。

统计窗口保留提交时刻至最后实体自然终态之间所有相交的、正常返回的完整 tick：`endNanos >= submittedNanos && startNanos <= terminalNanos`。29 秒冷检查在此窗口之外；没有删除首次寻路或其它慢 tick。每台有 622 或 623 个 tick，排序后取 `floor((N-1)*0.99)`，本轮恰为第 8 大值。46.5–51.6ms 的最长 tick 全部纳入，但仅占极少数，所以 p99 仍为约 4.5ms。

在这两对诊断中，候选 Base 合计分别减少 7.7413/7.2431ms，anchors 分别减少 10.7241/11.0278ms。按两台均值，anchors 合计约减少 86.46%，Base 合计约减少 30.36%。这是本轮带探针诊断的阶段观察，不能作为净提速比例。

Base 包含 anchors，不能将两者收益相加。worker 调用墙钟耗时和也不等于关键路径长度或 CPU 时间；anchors 的减少大于 Base 的减少，表明其它构图阶段及测量交互不能忽略。

明确保留这个未解释反向信号：Base 减 anchors 的合计残差由基线均值 **12.09990ms** 增至候选 **15.48365ms**，增加 **3.38375ms**；两对分别增加 2.9828/3.7847ms。因此不能宣称所有构图子阶段都更快。这里仍是同次嵌套调用相减后的 worker 墙钟合计，未拆成标签、边和其它子阶段，也没有证明它的具体原因或对主线程 p99 的影响。

详细寻路数量保持 80 次，调用墙钟合计也未增加。两对 tick p99 的候选减基线分别为 **+0.1579ms、−0.1142ms**；没有稳定复现旧净测量的回退，也没有证明旧回退已经消失。

原正式净矩阵均值为 **5.105850→6.714900ms**，本轮带诊断探针的均值为 **4.487900→4.509750ms**。绝对水平明显不同，不能把两套数据直接比较为版本改善；详细寻路合计减少也仅是这四台诊断中的观察，不能归为行复用带来的寻路加速。

## 尾部时间线

基线两台的 80 次详细寻路均分布在 27 个 tick，候选两台均为 22 个 tick；单 tick 最大调用数分别为 14 和 15。候选的工作分布更集中是本轮可观察事实，尚未证明由缓存单独导致，更未证明它解释旧净验收的差异。

每台最慢 8 个 tick 中，仅 3 或 4 个包含详细寻路，各仅 1 个与 worker Base 构图时间重叠。异线程时间重叠不证明 CPU 竞争；没有重叠也不能排除之前的间接影响。

| JVM | 决定该台 p99 的 tick | 完整 tick ms | 其中详细寻路 ms | 同时有 Base 构图 |
| --- | ---: | ---: | ---: | --- |
| 基线 1 | 698 | 4.3370 | 1.9192 | 无 |
| 候选 1 | 609 | 4.4949 | 0 | 无 |
| 基线 2 | 699 | 4.6388 | 2.1017 | 无 |
| 候选 2 | 609 | 4.5246 | 0 | 无 |

表内 tick 为服务器绝对 tick 编号，不是按时长排序后的索引。

候选 1 的该 tick 采到了 `GroundSegmentWindow.current` 调用链；候选 2 的该 tick 没有主线程样本，不能凭候选 1 的栈替它归因。其它慢 tick 采到节点展开、区块/实体更新、类加载和 ASM/Mixin 等执行路径。

四台最长 tick 都在首次详细寻路附近，约 46.5–51.6ms，采样包含类加载/ASM/Mixin和节点展开。两版共同保留原 `mixin.debug.export=true`，不能把这些采样全部当作纯寻路算法成本，更不能据此解释原净 p99 的唯一原因。

每台 16 个宏观回调均在完整 tick 计时区间之外执行。它们的入队延迟单列保留，没有混入完整 tick 耗时；本轮也没有记录所有调度队列，不能将此推广为所有异步交接均无成本。

从每个 tick 墙钟中减去其中同步详细寻路的调用跨度后，再计算剩余墙钟 p99，两对分别为 3.9266→3.9167ms、3.4093→3.6715ms。这个派生量只用于分层观察，包含其余工作、探针和可能的等待；不是移除详细寻路后的反事实性能，更不是主线程 CPU 时间。

## 线程包含与等待复核

针对审查提出的 E1，直接重读已有四台记录，不追加 JVM。`e1-containment.json` 与独立审计均按实际线程 ID 和单调时间戳核对：

| JVM | tick 主线程 ID | 80 次详细寻路线程 ID | 64 次 Base 线程 ID |
| --- | ---: | ---: | --- |
| 基线 1 | 82 | 82 | 92、93 |
| 候选 1 | 82 | 82 | 93、94 |
| 基线 2 | 81 | 81 | 92、93 |
| 候选 2 | 82 | 82 | 92、93 |

每次详细寻路都在同一 tick 主线程串行执行，并完整落在唯一一个完整 tick 计时跨度内；没有将并行 worker 时间从 tick 中扣除。上述派生量的计算是先对每个 tick 减去本 tick 内的同步调用跨度，再对结果取 p99，**不是两个 p99 相减**。

定义 `C_tick` 为实际 tick 主线程执行的 Base 构图跨度与本 tick 的交集时长，`P_tick` 为其它线程 Base 构图跨度与本 tick 的交集并集时长；并行事件不重复累加。四台在所有完整 tick 上的 `C_tick` 均为零。`P_tick>0` 的 tick 数分别为 2/1/1/2；决定四台各自 p99 的四个 tick 均为 `C_tick=P_tick=0`。这里仅表示直接 Base 构图执行关系，详细寻路是另一类事件，因此基线 p99 tick 内存在详细寻路并不矛盾；经锁竞争、任务到达或发布等途径的间接影响仍未排除。

同时，不能把“异步构图”写成“主线程没有等待”。四台 tick 602 均记录到主线程在 `TopologyWorkerRuntime.publishRequestEvent` 的 monitor 进入等待：基线 1 为 3.2073ms，候选 1 为 3.7188ms，基线 2 为 2.7589ms，候选 2 有 3.0590/1.0124ms 两次。基线 2 的 tick 605 另有 `endServerTick` 的 3.8838ms monitor 等待。这些是本轮真实观察到的锁等待，不证明由行缓存导致，也不证明锁持有者正在执行行填充。

决定四台各自 p99 的四个 tick 中，没有记录到本配置覆盖的至少 1ms ThreadPark/JavaMonitorEnter 事件。这只限定已启用事件及阈值范围，未穷尽 Object.wait、阈值以下等待、自旋和操作系统抢占。因此 E1 确认了线程及同步包含关系、并检出了部分等待，**没有排除全部等待或缓存通过任务到达、发布、竞争等途径影响 p99 的可能性**。

## 当前结论

本轮确认的是：在这四台实际生产包诊断中，原始行相关阶段与完整 Base 构图都更短；详细寻路调用数量及总耗时没有呈现候选增加；尾部由详细寻路和其余主线程工作共同构成。

**原正式 5.105850→6.714900ms 的回退根因仍未定位，没有形成可验证的修复。** 不能宣布缓存无关、旧差异为噪声，或仅凭新诊断接近持平就认为生产可用。

当前没有测量依据支持继续修改 RawRows 来修正 tick p99，因此不实施猜测性的缓存修改，不转向其它生产会话负责的详细寻路、调度、预算、历史预测、偿债、持久化或 Boundary 优化，也不追加不变候选的正式矩阵来寻找通过结果。

这不否定行分层复用本身的阶段收益，但暂停其以“修复 p99”为目标的进一步代码推进。只有找到受证据支持的具体变更并重新通过原净门，才有条件恢复发布评估。原强制穿关闭门场景未通过及既有 Boundary 独立性能门 INCONCLUSIVE 均不关闭。
