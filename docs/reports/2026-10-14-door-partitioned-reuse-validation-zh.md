# 懒惰升级：门能力分离与真实场景复核

日期：2026-10-14。状态：**门能力分离取得限定原型证据；整体共享与持久化方案未通过认证，未送审，未接入生产。**

用户授权继续验证，并指出开门能力可能显著影响路径长度，因此门暂时不适合高档直接复用低档。本轮采用这一边界：不同 `canOpenDoors` 条件不继承已有候选；同标志下的尺寸和流体条件继续研究逐项复用。宏观仍只提供候选，[现行详细寻路契约](../designs/2026-10-13-native-detail-navigation-contract-zh.md) 保持。

## 1. 本轮结论

| 问题 | 判定 | 实际证据 |
| --- | --- | --- |
| 合成门上方反例是否能在完整真实门事实中复现 | 能复现当前构图差异 | 木门开/关、四朝向、两铰链共 16 个场景，旧锚点存在，允许开门后标签变为 -1；铁门对应 16 个控制未丢失。 |
| 这是否已经证明真实实体原有路线被开门能力破坏 | 没有 | 原版详细查询在两种能力下都能到达门顶节点，但测试格心下移 0.01 格仍无碰撞支撑；没有实体执行或到达验证。 |
| 低档有路时是否仍会错过开门捷径 | 是 | 两个封闭房间绕行场景，原版节点折线长分别从约 12.90、18.90 格缩短为 9 格。只以低档无路为升级触发会跳过这些捷径。 |
| 限制为相同开门标志后，所测继承关系是否仍有反例 | 本轮未发现 | 独立重算前轮冻结矩阵中的 2,940 组比较，481,593 次旧锚点、350,550 次组件映射和 222,905 次有向能力边检查，失败 0。 |
| 此限制能否在局部原型中工作 | 在所测范围内能 | 修订原型 1,840 项断言通过；不同标志的零生成额度请求保持未知，首次局部生成和重复请求分别处理，不将低档候选提前交付。 |

**连通复用与路线长度是两个不同条件。** 即使高档物理上可以走低档路线，也不代表优先使用该路线符合当前门策略。用户接受其他能力下的最优性损失，不自动等于接受门捷径被绕过。

## 2. 实现和证据身份

证据根：`.tmp/door-reuse-validation-20261014/`。

- `native-v1/`：前轮 v3 保守继承逻辑的真实场景基线，38 个场景、82 次原版详细查询、224 项驱动断言；完整 JVM 正常退出。
- `native-v2/`：修订继承规则后的隔离局部回归和真实场景运行。回归 1,840 项断言；另一个 Forge JVM 执行相同 38 个场景、82 次查询、224 项断言，正常退出。
- 两个版本的原版节点、查询参数和场景方块摘要一致。重复运行不计为新增 38 个独立场景，也不合并为 164 个不同查询。
- `verification.json`：独立 Node 读取器 2,072 项核对通过，重新计算导出组件图的连通、节点折线长、锚点路径和门顶支撑，并重算较窄能力关系。
- `evidence-identities.json`：冻结源码、事实、图记录、原版结果和发行审计的 SHA-256。旧 1,008 份图记录仍绑定前轮身份，未改写。

五份生产源文件 `BaseClusterTopology`、`BoundaryGeometry`、`IncomingEdges`、`SectionGeometry`、`TopologyService` 按原样冻结、独立编译。`DoorReuseProbe` 是本轮新驱动；`PartitionedLazyProbe` 从前轮冻结原型复制后修改，旧原型保持。

运行使用 Java 17.0.18、Forge 1.20.1-47.3.0。发行依赖来自此前冻结的原始生产 jar 和映射类库，未使用持久化 v4/v5 修改后的缓存。仅在新建临时平坦世界放置测试方块；没有读取或修改用户游戏存档。

发行包审计确认 48 个预算、导航及 Mixin 类条目与冻结原始包逐字节相同。五份构图/采集核心按原样重新编译，其余修改限于研究类和加载研究驱动的元数据。未运行 Gradle 或改写共享构建输出。

## 3. 真实场景和详细查询边界

场景位于 section `(0,5,0)`。门由真实 `Blocks.OAK_DOOR` / `Blocks.IRON_DOOR` 的上下半 `BlockState` 组成，具有一致的 OPEN、FACING、HINGE、POWERED 状态，门下有实心支撑。驱动核对写入后的完整两半状态。

事实来自真实 `ServerLevel`，反射调用未修改的生产 `collisionSample` 和 `addSupport` 核心，生成四位事实和 `SectionGeometry`。这不是原型手写门盒，也不是生产事实队列、并发采集及订阅发布的验收。

详细查询直接使用真实 `WalkNodeEvaluator`、`PathNavigationRegion` 和 `PathFinder.findPath`，传入实际成年 Husk 实例。查询范围来自其 FOLLOW_RANGE，节点额度为该值乘 16，accuracy=0、visited multiplier=1；所有对照固定，未放宽参数。常规对照保持 `canPassDoors=true`，另测 `canPassDoors=false`。

Husk 实例没有加入世界并执行移动。结果是原版搜索得到的 Path、canReach 和节点，不是自动导航接入、分段执行、门交互 Goal 或最终实体到达认证。驱动在 ServerStarted 阶段执行，也不提供 tick 或吞吐性能资格。

## 4. 绕行与捷径

房间只有一个关闭木门捷径和一个普通绕行缺口，起终点相距 9 格。下表长度为原版 Path 相邻节点三维欧氏距离之和；不是耗时、malus 总成本或宏观组件最短距离。

| 场景 | 不开门原版 canReach | 允许开门原版 canReach | 不开门节点折线长 | 开门节点折线长 | 局部锚点长度：不开门 / 开门 |
| --- | --- | --- | ---: | ---: | ---: |
| 无绕行，关闭木门 | false | true | 不报告未到达路径为完整长度 | 9 | 无 / 9 |
| 无绕行，已打开木门 | true | true | 9 | 9 | 9 / 9 |
| 无绕行，关闭铁门 | false | false | 无完整路径 | 无完整路径 | 无 / 无 |
| 无绕行，已打开铁门 | true | true | 9 | 9 | 9 / 9 |
| 关闭木门，绕行缺口 z=11 | true | true | 12.8994949366 | 9 | 17 / 9 |
| 关闭木门，绕行缺口 z=14 | true | true | 18.8994949366 | 9 | 23 / 9 |

原版允许对角线，局部锚点控制仅用平地四方向单位移动，因此两种长度不能混作同一距离口径。开门原版路径含 `WALKABLE_DOOR` 节点。不开门的关闭门无绕行查询返回未到达结果，原始节点仍保留，没有把 partial 当成完整路线。

`canPassDoors=false` 时，关闭木门在 `canOpenDoors=true` 下也不能直达，已打开的门同样不能直接通过；有绕行时仍能绕行。开门权限不能代替其余原版门行为条件，本轮正常比较始终保持这些条件相同。

## 5. 门顶反例的解释

测试将完整门的上半放在 y=82，观察 `(8,83,7)`：

- 16 个木门组合：不开门图有锚点，允许开门图删除锚点。原因仍是 `groundOpen` 对下方可开门形状返回 false。
- 16 个铁门组合：两图保留锚点。
- 全部 32 个组合中，原版查询在两种开门条件下均能到达该门顶节点。
- 真实门板碰撞盒都位于格子边缘。宽 0.6 的身体放在格心，下移 0.01 格也未碰到支撑。

因此，这次将“当前构图非单调”从合成输入扩展到了生产采集核心读取的完整真实门事实。**没有证明这个门顶节点能被实体实际站稳，也没有证明简单恢复被删除的锚点就是正确修复。** 原版搜索的候选节点与实际碰撞支撑仍需区分，不删 `belowDoor` 分支来强行满足包含关系，不增加真实详细搜索前的人工支撑过滤。

## 6. 收窄继承规则

研究原型采用：

1. 原始输入及其依赖相同，导航类型和其余实际构图条件相容。
2. `canOpenDoors` 必须相同。不同标志直接进入目标条件的生成流程，不使用另一标志“已有路”来提前完成查询。
3. 在同标志内部，继续按宽高不增加、流体权限覆盖及现有 MovementKey 掩码研究复用。
4. 局部内核仍限定 GROUND、`heightCells>=2`。不同宽高组合不得逐维拼接。

这是共享记录中的条件隔离，不要求复制全部事实，也没有批准持久化两套完整图。

前轮保守原型只要输入含门且 GeometryKey 改变，就禁止继承。本轮通过新规则允许同开门标志下的尺寸比较；这一变更只发生在研究副本。独立读取器在旧 42 个事实样本、24 个条件的冻结图上重新选择 2,940 个适用比较对，并检查全部 30 个 MovementKey，没有新锚点或连接丢失。这是既有矩阵的重新分析，不是新增世界覆盖，不是任意体型或 NodeEvaluator 的数学证明。

修订原型回归保留前轮 1,774,080 项局部位图核对、768 项随机候选查询对照，并增加无门输入下的跨标志隔离、两种标志的独立重复请求，以及含门输入下同标志尺寸复用控制。

六个真实走廊中，目标开门条件的零生成额度查询均保持 `UPGRADE_BUDGET_EXHAUSTED`。局部生成后与完整生产图一致；有候选的开门场景评估 104 个源锚点的出边，关闭铁门场景评估 98 个后未取得候选。重复或交替查询不增加出边生成。这里不是只检查 104/98 格，也不是生产 CPU 收益。

## 7. 当前边界

本轮支持继续采用“门权限分离，同权限内研究其他能力共享”的方向，不批准全局能力继承，也不解决所有路线最优性问题。相同开门标志下，小体型仍可能拥有大体型图没有的捷径；用户此前允许的最优性损失边界保持。

原型回归的 8 个成本场景仍是现有紧凑组件图合计 41,928B、懒惰锚点图合计 581,184B，约 13.86 倍。门分离没有修复空间退化；不能据此开始给当前锚点表示设计持久化格式或宣称生产提速。

Runtime 并发、失效发布、上层图、真实门交互和实体到达、持久化及生产收益仍待验证。下一步优先研究保留组件压缩的共享入口与局部差异表示。原持久化 v5 的 future 结算缺陷保持，本轮没有使用或修复它。

两次服务器和回归 JVM 已结束。运行边界的保护检查未发现生产源码、测试和共享输出变动；之后另一对话继续变更预算相关工作区文件，未回退这些变化，冻结研究依赖不受影响。

**暂不送审仍有效。** 本轮取得证据并登记，不代表整个研究完成或生产验收通过。
