# 启动期预算历史与负债研究

日期：2026-10-15。承接[首请求时间线验证](2026-10-15-cold-request-timeline-validation-zh.md)，本轮研究方案见[四组受控方案](../designs/2026-10-15-cold-scheduler-causal-plan-zh.md)和[持续期限补充](../designs/2026-10-15-cold-scheduler-hold-plan-zh.md)。

## 当前结论

研究已从“提交时机与等待有关”推进到真实计费账本和受控机制证据：启动历史估计可以持续压低授额，真实旧债及后续新增工作又需要偿还，两者共同参与首请求等待。只提前首次派发，会留下明显的后继排队；后继阶段应纳入整个首 Path 的研究终点。

同包补充的四次重复中，持续到首 Path 的组，实测总等待均值为 265.8248ms；首次派发后恢复原历史估计的组为 481.7543ms。第二次排队均值分别为 74.9744ms / 299.7054ms。这与持续干预的预期一致，支持继续研究启动期预算恢复机制。

这些均值是本次有界实验的描述统计。组间使用不同 JVM，启动状态和实际信用剂量不同，顺序固定而非随机；不能把全部差异归因于一个中介，也不能据此批准清除真实负债、跳过早期高负载记录或改生产预算参数。共享拓扑的图级性能结论没有在本轮扩大。

## 固定输入与分母

所有实际冷请求使用同一 candidate-v5 生产包、成年 Husk、相同平地与 24 个已就绪事实、精确体型图冷态、Base 路线、第 30 tick 提交。保留真实 query、owner、sequence、future、原生详细搜索及真实 Path 资格；没有整条原生回退。

主矩阵为四组各四个独立 JVM，共 16 轮。另三轮详细审计和三轮原 v4 探针参考，分别报告。持续期限补充另八轮，同一个新包内两组各四次；两轮补充接线不混分母。加上主研究三轮接线和一个机制 JVM，本轮保留 36 个实际运行。

所有 JVM 串行，性能实验期间无 DeepSeek 审核或其他 Java 工作。全部新增原型源码、脚本和证据在 `.tmp/cold-scheduler-causal-20261015/`；正式 `src/test` 没有新增本轮原型，生产代码、参数和持久化范围保持。

## 干预语义

生产估计为最近 32 个有效 tick 的非导航耗时 p95 与 EWMA 的最大值；授额为 `clamp(45ms-estimate, 0..20ms)`，每 tick 增长不超过 1ms，上个 full tick 超过 45ms 时再限制为前授额的一半。START 保留旧负债、正余额封顶授额；END 仍要求 500us 最小片、haveTime 和实时截止。

`debt` 只在首次真实 queued END 入口，将当时负余额补至零一次；信用独立记录，累计实际计费保持。首次派发与后续工作可产生新负债，不持续清零。`history` 仅从第 30 tick 起、首次派发前，在 base p95 中排除全局有效记录序号 1–8；EWMA、tail、previousFull、增长限制、真实计费及实时派发门槛保持。有效记录严格来自生产正常完整 tick 的 `record`，不是当前环最早八槽。已滚出的记录不再排除，过滤后为空时回原 p95。

`both` 组合二者。补充的 transient 与 hold 都使用 both，只改变历史干预持续时间：前者首次派发后恢复，后者保持至首 Path。没有新增补零。此处固定排除最早八记录用于研究机制，尚无生产适用性批准。

## 初始计费和一次信用

三轮详细审计的首 tick 导航计费分别为 8.7605 / 6.5812 / 6.5002ms，首授额为 4ms；主要 outer account 来源为 `AcceleratedNavigation.onServerTick`、`SegmentedNavigationService.observe` 与 `observeServer`。提交前一 tick 余额分别为 -6.5848 / -4.1096 / -4.2766ms。tick30 的 intent + move 又分别计费 8.4887 / 13.8964 / 5.5896ms。

这是已经进入生产累计计费的工作，不因当时无请求便自动视为错误费用。详细栈审计有扰动，不能把这些数值称为无探针的净 CPU 成本。主矩阵提交前的余额也并非全部负数，不能据三个审计样本概括所有 JVM。

原读取器已核对负余额补零与剂量等式、累计计费不变、START 债务与封顶、逐 tick final 守恒及 END 所见余额。补充独立账本覆盖 31 个有研究记录的 JVM：19 个有正信用剂量的 JVM 各恰好一次有效注入，其他 JVM 为零；其他 tick 的 `final-refill+navigation` 信用残差全部为零，4 类真实损坏副本全部拒绝，共 4,085 项检查。

没有额外 runtime 计数器。只一次的保证来自生产者 `credit != null` 返回守卫、唯一补零写入路径及完整逐 tick 账本的等价核对。补零之后仍正常记新工作，不能称无债运行；补充各轮窗口最低余额仍可达到约 -22.5 至 -30.7ms。
