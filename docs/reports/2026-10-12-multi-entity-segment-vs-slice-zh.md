# 多实体下的分段与分片认证

本轮回答“实体可能并非一个”时，比较了三种方式：

1. **整条路线分片**：整条宏观路线只启动一次可恢复的原版搜索；
2. **分段、同步调用**：每两个宏观连接生成一个阶段目标，每阶段重新调用原版搜索；
3. **分段、分片调用**：每两个宏观连接生成一个阶段目标，同时保留原版搜索的开放集、节点、目标和评估器状态，在多个调度轮次中继续。

结论是：**生产方向应采用“分段 + 分片”的组合。** 分段负责把搜索空间和单次风险压小；分片负责把一次局部搜索限制在调度片内，并允许多个实体公平推进。两者不是互斥方案。

本轮仍是隔离原型诊断，不修改生产源码、不接入游戏、不写旧工作区或原始存档。实体移动与碰撞执行未在本轮认证；当前结果证明的是多实体计算调度和原版搜索结果一致性。

## 认证前提

上轮有效证据全部复用，生产、原版依赖、图、NBT 和原型输入共388个冻结引用重新核对，漂移为0。没有重跑上轮单实体矩阵。

本轮新增原型文件：

- `SlicedSearch.java`：按1.20.1 `PathFinder`实际循环改造成可暂停 `ResumableSearch`，保存开放集、节点、目标和评估器状态；
- `MultiProbe.java`：多实体、三种方式和共享预算对照；
- `scheduler_fairness.py`：按当前生产调度器常量和队列排序实现的静态公平性模型；
- `read.py`：独立报告读取、字段对账和汇总。

实际原版逐节点控制通过12个比较：分片和同步原版的路径目标、可达状态、节点顺序和展开数一致；暂停后可继续；取消后评估器、开放集和结果均释放。多实体每个实体拥有独立搜索状态，方块输入只读共享。

## 生产调度器的关键事实

当前 `NavigationScheduler` 已经有时间片常量：单片上限1毫秒、每片最多64次展开，见 `NavigationScheduler.java` 第32、34行；运行中的搜索在第292–311行重新入队。

但是同一维度、同一优先级的队列按原始 `sequence` 排序，见第565行。也就是说，搜索A执行一片后重新入队，仍可能排在搜索B前面；维度游标只在不同维度之间轮转。当前代码不能证明同维度多实体公平轮转。

用当前常量建立的队列模型（每个实体需要25片、每 tick最多4片）得到：

| 实体数 | 当前原始序号队列完成 tick | FIFO 轮转模型完成 tick |
| ---: | --- | --- |
| 1 | 7 | 7 |
| 8 | 7、13、19、25、32、38、44、50 | 49、49、49、49、50、50、50、50 |
| 32 | 最后实体200 tick | 最后实体200 tick，前31个在193–199 tick完成 |

总完成时间相同，但当前队列使早提交实体持续占用片段，后提交实体要等到前面任务完成后才获得同等进度。这是静态模型，不把它冒充成实际服务器采样；它足以证明多实体接入前需要单独处理同维度公平性。

“到达情况”中的整条路线失败仍是上轮已知的城市整条搜索部分路径，不是新增失败；分段两种方式的160个实体样本全部到达。

分段同步与分段分片的比较：

- 1个实体：分片中位数增加8.8%，但单次最大调用中位数降低58.5%；
- 8个实体：分片中位数增加4.3%，最大批次从29.51升到40.25毫秒，说明小样本下调度分配存在波动；
- 32个实体：中位数几乎相同（−0.1%），最大批次从168.04降到116.03毫秒，单次最大调用中位数降低57.6%，完成 tick 最大值从40降到29。

整条路线分片相对分段分片的累计批耗时约慢13.4–16.1倍，且城市整条路线仍有业务失败。只做整条分片不能替代宏观分段。

## 选择与边界

推荐的接入结构：

```text
宏观走廊
  -> 每两个连接选择阶段目标
  -> 为该实体建立独立可恢复原版搜索
  -> 每次只执行一个调度片
  -> 达到阶段目标后释放本段状态并生成下一段
  -> 最后一段完成后交给原版 Navigation 执行
```

原因按优先级排列：

1. **准确性**：分片控制只改变搜索的时间边界；12个逐节点控制证明其路径结果与原版同步循环一致。分段阶段目标来自已验证的宏观连接，四条路线的160个多实体分段样本全部到达。
2. **多实体时间行为**：分段把单实体工作量压到毫秒级，分片把最慢一次调用进一步压到约0.26–0.28毫秒中位数，32实体的最坏批次和完成尾部明显收窄。
3. **公平性**：分片只有在调度器真正轮转时才有意义。当前同维度队列按sequence保持原顺序，生产接入必须补充同维度轮转或等价的公平取队；本轮不修改生产，所以不能宣称现有调度器已满足。
4. **复杂度**：单独分段实现较简单；分片需要保存原版PathFinder状态和处理取消、异常、关闭，代码和生命周期复杂度更高。但多实体场景下，单独同步分段仍会把某个阶段的全部搜索作为不可抢占调用，不能满足稳定的主线程上限。
