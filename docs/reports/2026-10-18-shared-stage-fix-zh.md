## 原因与实际复现

原共享路径固定选择`cursor+4`，即使剩余8格全部属于平地，也先搜索第4格，
执行到该处后再搜索终点。当前生产B在`original-accuracy0-v1`中实际复现：

| 项目 | B实际结果 |
| --- | --- |
| 路线 | `(-156,81,-159) → (-148,81,-159)` |
| 原请求 | accuracy=0、range=35、regionOffset=8、visitedMultiplier=1 |
| 最终状态 | SUCCEEDED，实际精确到达 |
| 真实搜索/共享分段 | 2 / 2 |
| 第一次发布目标 | `(-152,81,-159)`，中间段 |
| 第二次发布目标 | `(-148,81,-159)`，最终段 |
| 第二次发布相对提交 | 约1853.6ms |
| 首Path | 83.7532ms |
| 原生整条/决策回退 | 均为0 |
| 关闭 | records/active/pending归零 |

公共分析器判定技术有效，原始输入、节点、发布观察和关闭数据保留。
这确认了“多切一段、多搜一次”的结构原因。它不解释此前C冷首Path全部差额：
此前C在首Path前有22.965ms GC，第二段约1.81s后才发布，不能将首Path增加
约24.7ms直接归因于第二次搜索。CPU剩余差额也没有被准确分解为JIT或GC。

## 修复

F只改`SharedSectionCandidate`和`SegmentedNavigationService`：

- 候选创建时计算一次平地后缀；后缀每步必须同Y、水平曼哈顿距离1。
- 当cursor处于该后缀，且剩余步数**严格小于**原range时，直接选择最终目标。
- 转弯平地可以合并；跳跃、落差、空隙、小range保留原4锚点规则。

锚点仍只是宏观候选，实际发布仍来自真实原生搜索。最终目标、accuracy、
range、regionOffset、visitedMultiplier、能力、实际落地/到达和有界恢复均保留。

## 原生range边界补正

首版Fv1使用`剩余步数 <= range`，其内部oracle也使用同一边界，因此即使检查
通过，仍漏掉一个确定性退化。继续审核实际游戏Jar的`PathFinder`字节码后发现，
其邻居入队要求`walkedDistance < range`，等于range不会入队。

使用冻结的Fv1编译类和真实`PathFinder`搜索循环复现：8步、accuracy0、range8，
Fv1选择终点8，但原生搜索`canReach=false`；旧规则先0→4、localRange16，
再4→8、原range8，两次均`canReach=true`。这是Fv1候选缺陷，不是环境无效。
原件见`native-range-repro-v1/run.log`和`native-pathfinder-bytecode-v1.txt`。

Fv2改为严格`<`，并补真实原生搜索循环回归：距离5..15的等号、nextUp浮点边界、
旧两段可达及新选择器边界，共44次真实原生循环、66项断言。NodeEvaluator只提供
水平单位步，搜索算法本身直接调用实际游戏类的private loop；它证明原生range语义，
不能冒充实体真实行走、碰撞世界或完整导航生命周期验证。
旧F/E源码、包及检查保留，续验使用v2。修改依据见`protocol-v2.md`。
