# NT-L4原样复跑与负向定位

日期：2026-10-23。承接用户“再跑一次看看是不是波动，如果负向持续确定一下负向的根因”。
证据目录：`.tmp/detail-nt-long4-rerun-20261023-v1/`。
前轮[NT-L4隔离验证](2026-10-23-detail-nt-long4-isolated-validation-zh.md)及原封存不改。

## 1. 结论

**原样复跑再次出现搜索分配增长和两条约3秒延后，不能仅凭一次复跑将其抹为波动。
后续定位确认：秒级延后来自不同宏观通道及交接点导致的实际绕行；
搜索分配增长并非同一JAR必然发生，但具体触发原因仍未唯一闭合。**

实际扩段64条仍少64次搜索，59条到达提前、5条延后，全部长段可达、无长段恢复。
该组搜索wall合计下降2.6972ms，到达差中位提前1062.66ms，最大延后103.97ms。
候选的有限扩段价值仍保留；不能据本轮宣布整体详细搜索降本或生产准入通过。

两条慢路线在未改NT包上也出现，未改NT-L4也能返回历史NT的短通道。
这是路径内容随运行输入/状态变化，不是相同路径计时抖动。
分配方面，即使完全沿用原启动方式，附加任何JFR之前的前四场也能恢复低分配；
因此不能把前两次+34.62%/+35.90%直接解释为扩段分支固定增加的工作量。
但本轮没有捕获高分配状态的调用栈，不能进一步声称已证明由某个回调对象或某项JIT决定导致。

## 4. 秒级负项的具体原因

正式复跑的256/8、tile23/slot1与slot5仍分别比NT晚3040.81/2987.26ms，
各两次搜索、零恢复、未扩段。首段仍9候选、9返回节点，末段12返回节点；
NT历史为11候选、首段5节点，末段6/5节点。

新TRACE诊断观察到了相反的版本对应：

| 内容 | NT诊断长通道 | NT-L4诊断短通道 |
| --- | --- | --- |
| 宏观组件链 | `(8,5,-5)/1 → (8,5,-4)/0 → (8,5,-5)/0` | `(8,5,-5)/1 → (9,5,-5)/0 → (8,5,-5)/0` |
| 记录的连接lowerBound合计 | 2 | 2 |
| 首段最终到达的交接节点 | `(136,81,-65)` | `(143,81,-70)` |
| 首段候选与节点摘要 | 匹配两次正式NT-L4 | 匹配历史NT |
| slot1到达ms | 5146.3639 | 2057.1410 |
| slot5到达ms | 4998.6524 | 1949.1913 |

长通道先去相邻section，再从远侧交接点折回终点。
NT诊断两次搜索合计仅0.0890/0.0660ms，不能解释约3秒时间差。
同一短/长可见路径摘要在两个版本间反转，确认这种长尾不是扩段候选独有，
且这些请求stride始终为2，未进入扩段选择。

[此前单变量回放](2026-10-23-macro-dependency-input-cause-zh.md)
已经证明依赖交付批次可改变等代价通道。
本轮确切定位到通道和交接点差异，但未补录历史两条的完整available批次，
**不能将此前机制直接冒充这两条历史运行的完整触发链证明**。
同样，不把本轮诊断的到达差当作新的候选收益。

## 6. 搜索分配：已缩小范围，未唯一闭合

正式两次增长相近，不能忽略。
但四次诊断均未保留约69MiB状态；
最后一次完全原启动，JVM参数仅归一化输出目录后与正式复跑逐项相同，
全部五项构建artifact身份、Java、模板及server properties对齐，
只在第3场FINISH以后才启动外部JFR。

附加JFR之前的前四场搜索分配：

| NT历史 | NT-L4首轮 | NT-L4复跑 | NT-L4原启动诊断、附加前 |
| ---: | ---: | ---: | ---: |
| 23.530472MiB | 31.139290MiB | 31.489883MiB | 23.360016MiB |

其中128/8的tile0/slot0单目标平地请求，搜索次数和返回摘要保持，
NT历史14,272B，NT-L4首轮20,912B，复跑20,800B，
最后一次附加前已恢复14,272B。
128/28同一路线亦从NT-L4的75,840/76,736B恢复到52,992B，与NT一致。
所以“启动采样必然把分配降下去”也不能当作已证明原因；
原样启动本身就能进入不同分配状态。

JFR确实采到已有的BlockPos/MutableBlockPos、Node、EnumSet、形状对象、
ChunkPos、Operation数组及CallbackInfoReturnable。
三份LogCompilation的Region.getBlockState编译中均记录了消除CallbackInfoReturnable，
部分PathFinder包装数组也被消除。
这证明此类成本会受运行时优化影响，但记录到的恰是低分配状态，
**不能证明正式高状态的18.32MiB增量就是这些回调，也不能证明全部属于JIT或展开量变化**。
JFR权重是采样估计，不是精确按类分配分账。

本轮的最窄结论是：不能将约35%增长全部认定为该JAR必然增加的固有成本，
分配存在运行状态相关变化；仍缺高分配状态下的具体分配点及对应展开量，
也未排除候选间接改变时序或存在局部固定开销。
保留这个缺口，不以低分配诊断替换正式结果，不继续用整矩阵反复重跑来碰状态。
