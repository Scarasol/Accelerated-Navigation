# 按组件结构减少 Base/Boundary 构建：验证与一次针对性调整

日期：2026-10-19。证据根：`.tmp/component-build-shortcuts-20261019-v1/`。

## 一、结论

用户授权的三项工作已经完成：实际机会计数、干净 R2 上的隔离实现与正确性、
完整 worker 冷查询对照。随后按用户“正面收益高于负面，允许在这一版上针对性调整”
的新授权，又完成一次 C2 调整及独立三臂对照。

**保留首版 C 的构图减量实现及正面证据；不采用 C2，不接入生产。**
C 两轮对照的全部模式/顺序，查询 wall 均值及中位数均低于各自 R2，
完整操作分配均下降。首轮 mixed 第一对完整操作 CPU 高 2.94%，旧预定门未全过；
这一结果和旧判定不改写。用户随后允许一次 C2，不等于追认旧门通过。

C2 正确性全部通过，但相对 C 的 air wall 均值两顺序高 21.70%/7.54%，
中位数高 18.83%/7.48%；distinct 和 mixed 的额外收益不足且有反向值。
按追加前固定的选择规则停止 C2，本轮不继续 C3 或实现扫描。
本轮也没有运行304格 Minecraft 实体路线、取得稳定 CPU 收益或生产/发行资格。

## 二、版本与具体修改

| 名称 | 来源及范围 |
| --- | --- |
| O | 未修改的 `.tmp/runtime-maintenance-validation-20261018-v1/R2/main`，使用其 `compiled-v3`；属于旧连续空气段 R2 |
| I | O 的独立诊断副本，只加实际构建/循环计数；不参与性能比较 |
| C | 从干净 O 复制，仅改 BaseClusterTopology 和 SuperClusterTopology 两份源码 |
| C2 | 从已冻结 C 复制，只再修改 BaseClusterTopology；当前未采用 |
| D | 上轮执行 helper 诊断件，未使用、未叠加或重开 |

C 的修改：

1. `buildGroundEdges` 在组件数为0或1时返回已有的空局部边表示。原逻辑只生成
   不同组件之间的边，这两种情况不可能有边；保留相同数组长度和内存估算。
2. `boundaryLinks` 在原参数、体型和邻接检查之后，任一端组件数为0时直接构造
   与原空结果相同的数组。**两端各一个组件仍正常构建 Boundary**。

合法锚点、组件标号、Base 元数据、halo/stamp、签名、原 scalar/run 引用语义、
发布校验、缓存和 owner 生命周期均未修改。候选运行时源码与 R2 相同。

C2 的追加修改只针对组件整理：

- 完成合法锚点生成后扫描已有64个 word；无合法锚点时省略4096格组件种子扫描。
- 空图的统一标签已知为0；非空图的统一标签只计算一次，并传入 `compactLabels`，
  省去此前内外各一次的重复判断。
- scratch 仍先按原逻辑清零，boundarySnapshot 和全部版本捕获继续执行。

这是构图执行减量，没有删除 Super 的八子图依赖，也没有拆分 Base/Boundary
失效契约、引入图级引用聚合、旧快照继续计算或 `ALL_AIR` 专用所有者。

## 四、正确性与保护

同一份 `ComponentDifferential` 分别加载实际 O、C、C2 编译类：

- 46组输入、8种体型/通道，共368种源 Base 构型；包括门、流体、支撑与缺失 halo、
  空图、单组件、多组件、城市列语料、负坐标、GROUND/VOLUME 及复用 scratch。
- 每版23,184条规范结果记录逐项匹配；每版3,014,656次标签读取，
  包含 scratch 被后续构建复用后的旧图稳定性复核，不当作同数量独立地形。
- 每版20,608次 Boundary 调用和1,840项参数/不兼容拒绝检查。
- 对照包含原始标签存储、baseLabel、组件元数据、边数组、float 位、
  port 行、halo、boundary 输入的事实身份与顺序、反向索引和 retainedBytes。
- 跨 JVM 不比较包含枚举身份的原始图签名；签名构造源码未改。
  规范图内容及所有输入成员另行比较。

C、C2 各通过原实际方法91,668项断言：
11,115个失效构型及1,008,893次版本写序、
9,073个引用状态场景（4,963个异常场景）、6,048个摘要变换。
三个结果摘要与旧 R2/D 检查一致；各77项真实 owner 账目通过。
Core、Boundary recovery、Door、Worker、Shared stage、Shared runtime 六组契约
各通过，包含 Shared stage 的99,951检查/41构型路线/643组件证明，
Shared runtime 的1,296检查。它们不是本轮 Minecraft 到达数。

`correctness-gate.json`、`c2-correctness-gate.json` 还限制实际源码差异：
C 相对 O 只有前述两个文件；C2 相对 C 只有一个文件且精确匹配追加改动。
999份保护文件和原 C 冻结源码在最终封存再次校验。

## 五、首轮完整冷 worker 对照

四个独立 JVM，顺序 O,C / C,O。各 JVM 每种模式24 warmup+64 measured，
Java17、512MiB、同一 `classes-v3` harness，无深计数、agent、JFR或编译参数干预。
每次查询均实际创建 runtime、执行宏观依赖与构图，随后等工作静默并关闭。

查询 wall 统计到结果返回。完整操作 CPU/分配统计从请求开始至静默和关闭完成，
包括共同资源采样及 metrics 读取，不含发布 fixture 和结果哈希。
768次测量均成功，输入、走廊组件成员、端点数、连接数及代价跨版本匹配，
关闭后的引用 map、active bytes 和 Base 留存归零。

下表为 C 相对同对 O，负数为降低；两项数值分别对应两种执行顺序。

| 模式 | 查询 wall 均值 | 查询 wall 中位数 | 完整操作 CPU | 完整操作分配 |
| --- | ---: | ---: | ---: | ---: |
| air | -11.99% / -8.43% | -16.31% / -6.39% | -9.68% / -6.33% | -14.30% / -13.50% |
| distinct | -14.50% / -17.90% | -15.48% / -20.25% | -2.50% / -41.86% | -14.61% / -13.49% |

这些结果均保留，不能用后两种输入较 R2 变好掩盖 C2 较 C 的空气退步。
新增 mask 扫描、方法布局或编译变化可能相关，但没有逐方法因果证据，
本轮不认定具体退步根因。

本组 CPU 不支持强收益解释：例如第一顺序 O/mixed、C/mixed 和 C2/air、
C2/distinct 的64次短窗口累计读数均为0；第二顺序 C/mixed 也为0。
其他原始窗口累计值从15.625ms至2,750ms不等，累计编译及任务次数均保留。
0 不代表实际未使用 CPU；与0组成的比例及几何均值记为 null，
不能写成节省100%或通过 CPU 门。非零比例也不作独立算法 CPU 因果解释。
没有为解决此现象再扩矩阵或更换主要指标。

追加规则要求 C2/C 每个模式/顺序 wall 均值及中位数不得退步超过3%，
且至少两种模式的跨顺序 wall 均值几何均值改善3%。
air 两顺序明显未过，distinct/mixed 额外改善也不足；
CPU 含不可判定项，不能补作通过。因此 `selectionPassed=false`、`selected=C`。
选择 C 表示保留隔离研究候选，**不等于 C 已通过原 CPU 门或生产批准**。

权威数据为 `c2-cold/`、`c2-cold-analysis-v2.json`。
首轮与追加轮分别报告，不把逐阶段百分比相加或混池造一个样本数。

## 七、技术失败与修正

1. 正确性分析器最初要求纯图对照日志必须加载 TopologyWorkerRuntime，
   但该驱动不实例化 runtime。分析器在性能开始前拒绝；改为核对实际加载的
   两个图类，完整 worker 日志仍核对运行时及全部实际加载的生产类。
   源码与已完成正确性 JVM 未改变，原失败保存在 `technical-failure-v1.json`。
2. 首次四个性能 JVM 使用“存活线程分配之和”，worker 关闭后计数回落，
   1,056条记录的完整操作分配均为负，分析器拒绝。
   `cold/`、原编译类及 `technical-v1/` 保留；候选未改。
   按 `allocation-retry-protocol.md` 只作一次四 JVM 技术重试，
   改用本机 JDK17 支持的 `getTotalThreadAllocatedBytes()` 累计计数；
   新旧样本不混合。首版权威四 JVM 为 `cold-v2/`。
3. 三臂第一分析未保护零 CPU 分母/分子，曾出现未经支持的-100%和无穷比例。
   原 `c2-cold-analysis.json` 保留，`technical-analysis-v3.json` 说明修正。
   v2把涉及0的 CPU 比例和几何均值记为 null，并禁止用 null 通过 CPU 门；
   没有重跑 JVM，wall、分配及保留 C 的选择未改变。
4. 最终封存器的完整类表正则最初未去掉 CRLF 行尾，匹配计数为0而拒绝；
   修正为逐行清理行尾后核对全部实际生产类来源，并保留三种关键实现类的必需检查。
   `audit-corrections.json` 保留修正说明，没有改变候选或重跑测量。
