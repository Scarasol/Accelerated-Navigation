# 第8步：当前版本成本归因

日期：2026-10-18。范围：用户要求的成本归因，结合侧边分析、日志、Spark和JFR，
补测当前源码的304格冷首次与温热重复。不实施生产优化，不改变宏观快照、
当前性、预算、TTL或真实寻路参数，不提交、推送或替换默认发行包。

## 一、结论与下一方向

1. **存在不同观测口径的成本中心，不能混成一张CPU账本。** 实际游戏中的运行时维护热点，
   与静态冷查询中的父图依赖及交接成本，都有证据，未证明相互独立；
   游戏全局样本不能分账给某次冷查询。
2. **游戏负载优先调查失效传播。** 重新读取原JFR后，858个模组worker活动wall样本中，
   469个归入runtime；其中失效175、引用81、事件应用64、构建管理62、查询依赖61、
   其他26。失效约占全部模组样本20.4%，对应分配采样权重约1.93GiB。
   这是定位优先级，尚未测出其中可避免的份额。
3. **冷长路线存在完整父图依赖放大。** 深诊断记录304个新Base、36个完成Super、
   38个已申请父图entry；只有20个Base直接展开，但288个用于已完成Super聚合，
   另外16个属于已申请父图，不能称为284个或16个“无用图”。
4. **Boundary主要是不同图之间的计算，不是同一边反复算。** 1852次调用中，
   Super内部1440次、跨Super392次、跨Base20次；有向Base对象对共1832组，
   仅20次重复。后续重复调用的插桩wall累计3.1765ms，不能以这次重复调用为由优先增加全局缓存。
   未来不同查询的复用价值未测，不能外推为所有缓存无收益。
5. **不能照搬深插桩的阶段占比。** 首Path前97,782次引用维护方法调用，说明交接有数量级成本；
   其119.8733ms独占wall含大量诊断开销，不能当作生产引用维护耗时或可省上界。
6. **下一窄方向应先量同批事件的重复失效检查及引用转换。** 保持现有当前性契约，
   先记唯一受影响视图/父级、重复访问、真正发生的退役及引用状态转换。
   如果主要是重复组织工作，再选择一个等价减量候选；若重复少，则回到冷父图依赖。
   本轮不恢复旧闭包矩阵，也不因本报告自动实施延迟失效或旧版本宏观查询。

本轮完成有界成本归因，足以支持下一项计量；不是全成本CPU账本闭合，
不代表第8步优化、稳定净收益或发行验收完成。

## 三、实际游戏负载：运行时成本在哪里

### 3.1 活动wall样本

两个worker共921个活动样本，其中858个带可识别模组栈帧。
其余63个没有模组栈帧，包括unknown_Java、not_walkable及反优化等未能归属的栈，
不将它们直接判为与模组无关。这里的ExecutionSample来自wall模式，
不能按采样间隔换算CPU，也不能把runtimeTransition的宽度解释为锁等待。
469/858=54.66%是占可识别模组样本；占全部worker已观察样本为469/921=50.92%。
若将63个未知样本全部归runtime，上界为532/921=57.76%；这是归属上下界，
不是统计置信区间，后续细分也不声称覆盖未知样本。

## 四、当前静态冷长路线：依赖怎样放大

沿用既有304格平地路线：`(-156,81,-159) → (148,81,-159)`，实体实际体型
width=0.6、height=1.95，GROUND；自然移动和真实到达判定保持。
每场在ServerStarted与sceneReady后均真实等待至少30秒。
事实及预热缓存已有数据，**冷指实际体型派生图和宏观走廊首次使用，不是整个世界全冷**。

深诊断冷首次首Path为393.4822ms，实际到达68,935.4034ms；
温热重复为7.8086ms和68,597.1920ms。冷首次1个物理宏观搜索，
温热完成走廊缓存命中1次、新物理宏观启动0次。两场各20次真实原生详细搜索。
这是同一JVM的顺序观察，不能写成稳定冷暖提速。

### 4.3 等待与阶段成本

MacroQuery观察到完成的Super依赖35、SuperBoundary49、BaseBoundary20。
已配对等待在提交至首Path窗口的并集为262.7297ms。
另3个Super依赖缺少completion观察，若保守延伸至首Path，并集上界350.8000ms。
搜索成功时清理或取消可能产生这种记录；不补造结束时刻，也不直接当作泄漏。
关闭指标归零。这个区间只描述已观察MacroQuery依赖，不等于整个冷请求的全部等待。

首Path前，worker同线程嵌套按独占wall分区，跨线程累计412.8679ms：

| --- | ---: |
| 引用维护 | 119.8733 |
| runtime其余入口 | 68.8826 |
| Boundary核 | 64.4456 |
| 依赖与交付组织 | 62.2368 |
| 构建管理 | 38.1252 |
| 宏观展开 | 19.9125 |

## 五、观察者控制及技术失败

深插桩采集反射字段、线程CPU、分配计数和大量引用，可能扰动执行时间、分配和留存。
因此只增加一组关闭深插桩的同路线冷暖控制；首次技术失败后，以新目录重试一次。
关闭后仍有共同轻探针及agent空hook，并不是完全无诊断的生产发行包。

首次控制`current-observer-off-v1`的两场均SUCCEEDED并实际到达、JVM退出0，
但ServerStopped处理器调用已关闭的`NavigationScheduler.forServer`而抛异常，
未写出shutdown.json，启动包装器退出1。**该次技术无效，不纳入通过控制。**
修正仅位于诊断探针：启动保存scheduler引用，LOWEST关闭检查读取该引用；
不删除生产关闭保护，不补写失败运行的凭证。

修正后的`current-observer-off-v2`技术检查通过，两场均SUCCEEDED、实际到达、
各20次真实原生搜索，关闭records与scheduler待办归零。没有外部Java并行。

| 同路线顺序观察 | 深插桩冷 / 暖 | 关闭深插桩冷 / 暖 |
| --- | ---: | ---: |
| 首Path ms | 393.4822 / 7.8086 | 251.3998 / 5.9151 |
| 实际到达 ms | 68935.4034 / 68597.1920 | 68795.6355 / 68600.7507 |
| 全自然窗进程CPU ms | 3921.875 / 1859.375 | 4875.000 / 1718.750 |
| 全自然窗分配字节 | 148058032 / 97433376 | 147830032 / 97123208 |
| 新物理宏观启动 / 完成缓存命中 | 冷1/0，暖0/1 | 冷1/0，暖0/1 |

表的两列来自**两个不同JVM运行**，各值均为对应运行的全自然观察窗；
“深插桩”是该运行模式，不是“全窗”的一个子集阶段。
CPU来自OperatingSystemMXBean进程计数差，分配来自ThreadMXBean全线程累计分配计数差；
它们是受支持计数器的读数，不是上一节JFR分配采样权重，也不是细阶段独占成本。

这里只是各一台JVM，未交错也没有A/A。关闭后的冷首Path更低，CPU却更高，
不能将142.0824ms全部定为观察者成本，也不能扣掉某个比例还原“纯生产阶段耗时”。
深插桩会改变排队和取消时序；结构计数也是该次观察，不能保证另一运行完全相同。
全自然窗包含约69秒实体移动及背景，资源差额不是冷构建CPU或某个方法的成本。
关闭后细阶段及图身份未测，空events或null图计数不表示没有构建。

## 六、下一项的边界
