# 速度 IV 与分段交接：诊断及改进建议

日期：2026-10-13。

唯一架构依据是 `docs/designs/2026-10-13-native-detail-navigation-contract-zh.md`。本报告记录现有实现、运行证据、网络原始资料和建议修改顺序。它是待实现和验证的方案，不是修复后的验收结论，不替代现行契约。

## 1. 结论

优先改善中间段的进度记录及交接时机：

1. 在当前真实原版路径的末节点阶段，记录实体实际经过目的组件的事实。原版节点自然耗尽后，落地位置已经向前移动时，可以使用仍有效的经过记录交接，减少返回刚经过的阶梯。
2. 提前准备至多一个下一段宏观窗口。到交接时，仍从真实实体位置、使用真实能力和现行参数调用原版 PathFinder，不从预测位置预先计算并拼接移动路径。
3. 正确记录连续 tick 的落地稳定状态，补充分段恢复原因及末节点附近的运动证据。

最终目标继续要求真实最后段可达、真实最终位置满足 accuracy；中间进度记录不能产生任务成功，也不能把 partial 改写成可达。

## 3. 原版机制核对

核对了当前项目实际使用的映射 JAR：

`build/fg_cache/net/minecraftforge/forge/1.20.1-47.3.0_mapped_official_1.20.1/forge-1.20.1-47.3.0_mapped_official_1.20.1.jar`

使用本机 JDK 17 的 `javap -c -p` 检查：

- `PathNavigation.tick`。
- `PathNavigation.followThePath`。
- `PathNavigation.shouldTargetNextNodeInDirection`。
- `MoveControl.tick`。
- `MoveControl.setWantedPosition`。
- `Path.getEntityPosAtNode`。

确认：

1. 宽 0.6 的实体，通常节点推进的 X/Z 容差为 0.45；垂直条件是与节点 Y 的差小于 1。容差不根据速度扩大，节点推进也不要求落地。中间节点还存在原版转角提前推进逻辑，不能概括成必须精确踩中节点。
2. Forge 的推进参考位置使用 `(width+1)/2` 偏移；本机 `Path.getEntityPosAtNode` 的移动目标使用 `(int)(width+1)*0.5`。不能将两者都简化成方块中心，并据此设计交接阈值。
3. `tick` 在当前 Path 耗尽后停止向 MoveControl 交付下一节点，但 MoveControl 的 JUMPING 状态会继续设置移动速度，直到落地转入 WAIT。
4. `setWantedPosition` 在 JUMPING 状态不会将状态强制改为 MOVE_TO。段间切换不能假定发布新目标就会立刻中止原有跳跃。

网络原始资料：

- Forge 官方 1.20.1 `PathNavigation` 补丁，与本机字节码的推进条件相符：`https://raw.githubusercontent.com/MinecraftForge/MinecraftForge/1.20.1/patches/minecraft/net/minecraft/world/entity/ai/navigation/PathNavigation.java.patch`
- Forge 官方 1.20.1 `MoveControl` 补丁，明确存在依实际步高触发的 JUMPING 分支：`https://raw.githubusercontent.com/MinecraftForge/MinecraftForge/1.20.1/patches/minecraft/net/minecraft/world/entity/ai/control/MoveControl.java.patch`
- Recast/Detour 作者文档，描述根据实际移动位置调整当前走廊，并处理移动误差：`https://recastnav.com/classdtPathCorridor.html`
- Craig Reynolds 的 Path Following 原始说明，区分沿路径继续前进与追逐一个固定点，并说明速度及转弯能力影响跟随：`https://www.red3d.com/cwr/steer/PathFollow.html`

后两项仅用于判断交接方向是否合理，不是 Minecraft 行为证据，不是引入新移动引擎、NavMesh 查询或自定义转向算法的依据。

## 4. 当前实现中的问题

### 4.1 进度只在节点耗尽并落地后结算

`SegmentedNavigationService.observe:674-696` 在节点未耗尽时不进行段完成结算。耗尽后满足稳定条件才排队 `settle`。

`settle:712-719` 要求此时实体的位置仍属于该段目的组件。`GroundSegmentWindow.contains:49-53` 精确匹配 section、修订和 componentId。

因此，实体可能在运动中经过中间接力位置，落地后已位于后续阶梯；实现没有保留经过事实，会回到当前段重选目标。日志中的楼梯折返与这条机制相符。真实经过尚需新增采样确认。

### 4.2 全局最终节点保护不能直接套到所有中间段

`deferFinalAdvance:562-568` 只保护任务最后一段。

如果简单给每个中间段加上同样的“等待落地稳定且仍在目标层”限制，移动控制可能持续追逐刚越过的节点，增加停走和振荡。中间段的交接目标应与最终任务目标分别处理。

### 4.3 当前稳定计数不严格表示连续 tick

`observe:638-640` 在 queued 或 preparing 时跳过采样；`previousY` 和 `stable` 的更新在这之后。

等待期间若发生起跳、下落或换层，下一次样本的 Y 偶然与旧值一致，计数仍可能继续累加。问题是样本不连续，而不是应该给每个中间段新增水平速度归零条件。

### 4.4 下一段准备完全在交接之后启动

`settle:718` 再排队 `nextSegment`，之后准备窗口，再排队真实详细搜索。异步等待和共享预算可能拉长段间节点供给的间隙。

预取可以降低窗口准备等待，但它不能单独解决目的组件错位造成的恢复。

## 5. 建议修改顺序

### 第一阶段：有效的实际经过记录

对真实分段地面移动增加一个当前段经过记录，包含请求代次、段发布序号、目的组件及修订、实际位置、tick 和原版节点序号。

记录条件：

- 仅用于中间段。
- 当前真实原版结果 `canReach=true`。
- 原版执行已进入末节点阶段或正常耗尽；不能只因之前路过同一组件就提前推进。
- 实际采样位置确实属于当前目的组件。
- 当前窗口、原版读取输入、实体、控制来源和请求代次均有效。
- 当前段没有原生 stuck-stop。

空中样本只作为实际经过记录，不作为落地成功，也不立即结束任务。旧段自然耗尽后，在原版允许更新路径的真实位置交接；首轮实现可以继续使用现有物理落地条件，以控制改动范围。此时可接受有效经过记录或当前位置确实属于目的组件，不强求落地后仍占据同一阶梯。

如果从未采到有效经过事实，仍走现有有限恢复。不能凭“位置更靠近最终目标”“落到更高一层”或原版调用了 advance 就跳过组件。

经过记录在新段发布、当前段重新搜索、输入失效、窗口过期、宏观刷新、原生停止、替换、取消、换维度和关闭时失效。不能只绑定 cursor：宏观刷新会重置 cursor，同一 Path 句柄也会复用。

对 partial 不建立可用于直接交接的可达记录。最终目标不使用历史经过记录代替当前实际到达。

### 第二阶段：一个下一段窗口的预取

当前路径接近耗尽时，开始准备现有走廊内的下一段窗口，最多保留一个。

- 当前窗口继续承担当前路径的输入当前性检查。
- 使用单独的预取状态，不能复用会暂停当前观察的 `work.preparing`。
- 不提前生成从假想交接点出发的原版移动 Path。
- 实际交接时检查预取窗口修订、任务代次、走廊位置及实际起点所需 sections；不符合就释放并按原流程准备。
- 详细搜索仍在共享 END 预算内，从当时真实位置调用 `NativeNavigationSearch.find`。
- 每段 sections 上限、节点限额、accuracy、range 规则、恢复上限及宏观算法不扩大；不强制加载区块。
- 预取失败不提前破坏仍有效的当前段，资源随取消、失效和停服清理。

优先预取窗口而非整条详细路径，避免移动起点已经改变却继续使用预测起点的搜索结果。

### 配套修改

- 稳定计数每个实际 tick 更新，或用上一采样 tick 检查连续性；最终到达继续使用真实连续稳定状态。
- `recover` 标明原因，区分 partial 耗尽、无节点、候选耗尽、落地超时、原生停止和目的组件未到达。
- 只在段末有限范围记录每 tick 位置、deltaMovement、onGround、节点 index/count、目的组件命中、经过记录、搜索及发布 tick。
- 原版跳跃状态可以在测试探针中读取；生产不增加全体实体的无限逐 tick 日志。

预计涉及 `SegmentedNavigationService` 的观察、结算、窗口准备和清理，以及测试探针。真实详细搜索后端、原版节点数据、宏观拓扑算法和尸壳效果等级继续按现行职责处理。

## 6. 不作为首选的方案

| 方案 | 判断 |
| --- | --- |
| 对所有段直接复制最终节点落地拦截 | 可能让中间点成为必须停留的目标，增加追点和振荡 |
| 给每段新增 X/Z 静止条件 | 增加停走，不解决遗漏经过事实 |
| 放宽目的组件、把相邻层算到达 | 可能接受错层，丢失真实进度依据 |
| 单靠更大 accuracy 或增加恢复额度 | 改变原参数或掩盖恢复问题 |
| 拼接从预测位置算出的下一段路径 | 与真实起点和实际原版输入不一致 |
| 只预取下一窗口 | 能减等待，但目的组件错位仍会恢复 |
| 将效果改回速度 II | 用户设置应保留；速度 IV 是有价值的压力场景 |
| 新增段末减速 | 可能有用，但属于新的移动执行策略，需独立说明和验证 |

若原版对照在同一楼梯、相同路径和速度 IV 下也反复追点，则说明还存在原版高速跟随的独立限制。此时才评估通过原版 navigation speed modifier 做局部段末减速。不能直接改实体位置、清除速度向量或偷偷降低药水等级；也不能宣称交接改动保证任意速度、任意急转角都流畅。

## 7. 验证与验收

先建立同一局部几何、同一初始精确位置的三组对照：

1. 现有分段执行。
2. 原版详细路径直接执行。
3. 修改后的分段执行。

每组分别验证速度 II 和速度 IV。原版对照只用于归因，不加入生产的整条原版回退。

重点覆盖日志中的两处楼梯：Y=74 到 Y=78，以及 Y=85 到 Y=89。记录实际节点列表，不能仅以相同 nodeCount 假设路径完全相同。

验收应确认：

- 实际经过接力组件并向后续阶梯落地时，不再因丢失经过记录而强制返回刚经过的目标。
- 未实际经过目的组件、下落至错误位置、原版 stuck-stop 和原生 partial 仍得到真实恢复或终态。
- 平地和楼梯分别比较反向移动 tick、同一段重搜数、恢复原因、节点空档、总耗时和原版实际搜索成本。
- 两段连接处的门、区块卸载、输入变化、取消、替换和换维度不会消费失效记录或泄漏预取窗口。
- 最后段仍严格使用原生可达和真实最终 accuracy；最终 partial 仍为 EXHAUSTED。
- 原 Navigation/Goal/Brain/POI 生命周期、发行 Mixin、共享预算及关闭后的零记录、零待办保持通过。
- 如主张完整路线资格或性能改善，须重新跑现行契约要求的四条原参数路线，不能用局部楼梯代替。

实现完成后，按用户此前要求提交 DeepSeek 独立验收，只使用现行契约、最终改动和本轮新证据。不能把本报告的分析或此前通过结论当作本次实现已验收。

## 8. 根因确认与方案共识

2026-10-13 的只读诊断在生产逻辑未修改的前提下完成。独立探针共 15 项检查通过，并交换了速度 II、速度 IV 的执行顺序。DeepSeek `plan-consensus-v2` 使用现行契约、当前实现摘录和诊断证据独立审查，正常退出，明确返回：

```text
ROOT_CAUSE_CONFIRMED
CONSENSUS
```

共识根因是：速度 IV 增大了末段后的残余水平位移；当前真实 Path 耗尽当帧，实体已经处于旧段目的组件、已落地，MoveControl 已为 WAIT，但仍有约 `0.193` 格/tick 的水平位移。实体随后滑出旧段目的组件，服务在稳定等待后再以漂移后的当前位置执行 `window.contains`，因此触发恢复并沿旧段回头。速度 II 的同一楼梯分段对照为 0 次恢复、0 个反向 tick；速度 IV 为 5 次恢复、55 个反向 tick。原版连续路径在速度 IV 的同一局部对照中可达且无反向 tick，因此当前现象主要是分段交接的事后位置重判，不能归因成原版搜索无路。

方案共识如下：

1. 第一阶段只改善中间段：记录真实实体在末节点阶段实际进入目的组件的事实，绑定 request、段发布序号、窗口修订和原版输入当前性；旧 Path 耗尽且记录有效时，从当时真实位置重新调用原版 PathFinder。记录只能推进宏观段游标，不能成为真实搜索前的资格闸门，不能跳过真实搜索，不能把 partial 当成功，也不能改变最终 accuracy。
2. 稳定计数修正必须单独验证，不能改变最后段 `finalArrival`、`EXHAUSTED` 和真实连续稳定语义。
3. 第二阶段才评估最多一个下一段宏观窗口预取；不预生成详细 Path，交接仍从真实位置搜索，并纳入预算、取消、停服和迟到回调清理。

仍待实测：生产修改后的经过记录覆盖率、速度 IV 恢复和反向 tick 是否降到 0 或仅保留真实搜索可解释的恢复、输入失效时记录作废、最后段及 partial 终态、其他楼梯和 city-backward 路线，以及预取是否确有可测收益。DeepSeek 原始记录：[plan-consensus-v2](../../.tmp/navigation-speed-root-20261013/deepseek-answer-plan-consensus-v2.txt)。
