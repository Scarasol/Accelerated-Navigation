# 导航算法与数据结构评估独立审核

日期：2026-10-17。

审核结论：**算法评估需要修订。** 主交接第十九节和原评估中的部分源码解释错误，部分淘汰条件没有相应证据，不能沿用“算法方向的正确性已经审核闭合”的理解。原记录明确保留了“候选未实现、性能未证明”，这一范围说明成立。

本轮扫描生产导航、调度、Base/Boundary/Super、共享结构、测试和相关报告，重点复核第十九节、算法评估原件及其两轮文本审查。没有修改生产源码、默认 Jar、旧报告、原交接或旧实验数据；没有启动 Minecraft 性能实验或再次请求外部模型批准。新增内容为本报告和独立审计目录。

## 发现

### 1. [P1] “城市图”统计混合了人工夹具、搬移后的城市列和受控平地捕获

位置：[原评估第19行](2026-10-17-algorithm-structure-evaluation-zh.md:19)、[主交接第667行](../agent-process/tasks/navigation-performance-handoff-20261017-zh.md:667)。

`admitted-graphs-v1.json`确有1370份快照，但生成器`OriginalDump.java:18–24`先枚举夹具及21种GeometryKey，全部在`Fixtures.SECTION=(0,0,0)`构图，再追加两组运行捕获。重新追溯生成器、夹具、二进制输入和consumption记录，得到：

| 来源 | 快照数 | 坐标和语义 |
| --- | ---: | --- |
| 39个人工夹具 × 21种GeometryKey | 819 | 全部统一到(0,0,0) |
| 11个城市列section夹具 × 21种GeometryKey | 231 | 原列的高度身份转成夹具名称，构图同样统一到(0,0,0) |
| 同体型运行捕获 | 64 | 受控石地/空气场景 |
| 混合体型运行捕获 | 256 | 同类受控场景 |

因此，1050/1370=76.64%的快照来自夹具枚举。320个运行捕获覆盖64个section坐标，只有2种中心sourceFingerprint；它们也不是城市路线捕获。对应原报告已写明受控世界为x0..95/z0..31、y80石地/y81..86空气。

“65个section、包围盒覆盖22.6%”计算的是统一原点夹具与受控平地坐标的混合集合，不能解释成城市空间覆盖率。49个指纹、23种GeometryKey和top10=40.2%作为该混合文件的原始计数正确，但不能作为城市频率分布或实际缓存基数。

修订：先标明来源并分组统计；城市结构判断使用保留原section坐标、邻接及输入身份的城市数据。该混合语料仍适合差分正确性验证。

### 2. [P2] 检查压缩标签有没有-1，不能判断组件覆盖

位置：[原评估第32行](2026-10-17-algorithm-structure-evaluation-zh.md:32)。

`BaseClusterTopology.componentAt:172`实际解码为：

```java
int label = baseLabel + componentLabels.get(cellIndex(x, y, z));
return label == 0 ? -1 : label - 1;
```

导出的`componentLabelValues`是非负压缩值；零绝对标签才表示没有组件。故“没有-1，所以标签覆盖100%”不是有效的组件覆盖解释。若“100%”只是指4096个字段都已序列化，则它与是否出现-1无关，也没有用于算法筛选的信息量。

按真实编码重算5,611,520格：4,455,773格没有组件，占79.404%；1,155,747格具有组件，占20.596%；465份快照组件数为0。完整结果保存在`corpus-audit.json`。

这里的20.596%仍然是混合语料上依赖体型/channel的组件成员比例，**不是原始碰撞几何的自由空间密度，也不能预测Boundary空扫命中率**。原报告拒绝直接外推空扫率的决定可以保留，编码解释必须纠正。

### 3. [P2] Boundary没有输出“BFS并列路径”，不应冻结其内部遍历顺序

位置：[原评估第61行](2026-10-17-algorithm-structure-evaluation-zh.md:61)、第88和92行。

`BoundaryGeometry.open:65`只返回boolean；BFS到达goal后直接返回true，没有前驱链、路径输出、路径权重或按扩展数截断。调用者`SuperClusterTopology.addBoundaryMask:345`只消费该布尔值。

`pointClear`和`segmentClear`是障碍存在性判断。`blocksAtCut`通过严格重叠区间反复扩展covered，求的是覆盖闭包；扫描顺序可能改变轮数，不改变有限矩形集合的闭包。BFS在固定邻接关系上的邻居顺序也不改变可达性。

独立差分直接调用当前生产类，再与仅加入计数的副本、反转矩形顺序及BFS邻居顺序的副本比较：

| 检查 | 结果 |
| --- | ---: |
| `open`三方对照 | 41,000次，零差异 |
| 进入BFS | 1,092次 |
| true / false | 18,120 / 22,880 |
| 最大矩形数 | 144 |
| point/segment/cut排列检查 | 6,000项，零差异 |

输入为现有42个夹具（含11个城市列夹具）与40个确定种子的部分盒夹具。这是隔离正确性检查，不代表服务器收益或全输入证明。

修订：索引必须保证候选障碍不漏检、严格接触语义和最终boolean一致；Boundary内部顺序不是对外契约。宏观`pendingDependencies`返回的依赖列表会被调用者消费，其并列选择与顺序仍应保持；两者不能混为一谈。

### 4. [P2] 用“三维世界”排除二维索引，判断对象错位

位置：[原评估第73行](2026-10-17-algorithm-structure-evaluation-zh.md:73)、[主交接第660行](../agent-process/tasks/navigation-performance-handoff-20261017-zh.md:660)。

`BoundaryGeometry.open:87–103`先把盒子投影到沿运动方向的s和高度y，并扣除横向不相交盒，随后处理四坐标二维矩形。它已经是二维配置空间中的可达性问题。

所以不能以“世界是3D、四叉树是2D”作为排除本地二维索引的依据。是否划算要比较矩形分布、剪枝量、构建与访问成本。当前也没有证据要求采用四叉树；“尚未证明值得实现”比“维度不匹配而淘汰”准确。

原评估也未拆开算法复杂度：设有效矩形数R，坐标压缩网格最坏有O(R²)个点，每条邻边调用O(R)的`segmentClear`，BFS组合上界为O(R³)，scratch为O(R²)；`blocksAtCut`反复全扫的上界为O(R²)。这些是随R变化的代码上界，不表示真实负载达到最坏情形，但足以说明应测BFS进入率及尾部工作量，不能只看矩形数p95。

### 5. [P2] D的p95≈64不是有效的Java实现前置门

位置：[原评估第11行](2026-10-17-algorithm-structure-evaluation-zh.md:11)、第67和69行、[主交接第658行](../agent-process/tasks/navigation-performance-handoff-20261017-zh.md:658)。

“64附近交叉”来自Node计时。现存原件只有结果JSON，未见对应基准实现、输入生成、随机种子、循环次数和计时原件；`same=true`也无法从现存材料独立重放。它可以保留为未复核的探索记录，不能据此设置Java的硬阈值。

p95还会遗漏少量昂贵调用。例如99次D=8、1次D=32768，p95仍为8；在D·log2(D)的未排序比较工作模型中，最后一次占99.52%。这只是逻辑反例，不是计时结果，说明“p95不到64就不值得做”不成立。矩形数p95的单门槛存在同样问题。

当前真实复杂度应写成：全排序O(W+D log D)，有界堆O(W+D log K+K log K)，W为所有依赖等待节点的扫描量。`pendingDependencies:164–170`还包含每依赖Stream、Float装箱、Map.entry及终端结果构造；小D的减量候选不等于强行上堆。

修订：按调用成本加权分布与Java完整方法测量筛选，比较现有Stream全排、小数组和有界堆，并计入W、构造及分配。保留当前列表的选择与并列顺序。宏观依赖阶段约21MB是聚合账本，不能全部归给这个排序方法；现有agent没有单独插桩`pendingDependencies`。

### 6. [P2] 有2×2×2 SuperCluster，不足以淘汰所有HPA式结构改进

位置：[原评估第77行](2026-10-17-algorithm-structure-evaluation-zh.md:77)、[主交接第660行](../agent-process/tasks/navigation-performance-handoff-20261017-zh.md:660)。

`SuperClusterTopology.build:99–107`构建的是子组件有向图的SCC凝聚；其数据包含聚合、出边、代价和witness。这个事实只能说明已有一层抽象，不能推出入口选择、局部距离摘要、跨层细化或依赖闭包改进必然重复已有工作。

当前没有必要据此启动一个新框架。应把整套替换列为低优先级，把具体结构改进按冷构图、访问规模及细化成本另行评价。“存在分层所以淘汰所有相关思想”缺少中间论证。

标准JPS不能直接替换当前不规则有向加权图，且详细阶段有原版参数与真实执行契约，维持暂不替换的决定合理。它和HPA式结构选择不是同一项排除理由。

### 7. [P2] 把所有方向的证据都列为任一候选的前置门，会制造无关阻塞

位置：[原评估第83行](2026-10-17-algorithm-structure-evaluation-zh.md:83)。

“继续任何候选前必须补齐”随后同时列出D分布、Boundary轨迹、三种oracle和Java/server测量。若按字面执行，验证Top-K要等待碰撞位图证据，验证Boundary布尔等价要等待宏观依赖分布，均没有正确性上的依赖关系。

修订：各候选只补与自身有关的最小测量和正确性检查，再决定是否进入隔离成本比较。服务器正式验收需要计量、身份、失败分母和噪声控制；这些要求不应成为离线等价性检查的统一前置大工程。本轮顺序差分已在没有新增server基线和D直方图的情况下完成。
