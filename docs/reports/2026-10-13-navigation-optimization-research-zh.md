# 动态预算、接入开销与面寻路研究

日期：2026-10-13。状态：候选方案研究，不是已实现优化或性能验收。

唯一现行架构依据是 [原版详细寻路接入契约](../designs/2026-10-13-native-detail-navigation-contract-zh.md)。本文讨论用户本轮提出的优化候选；动态预算会改变现行固定约 4ms/tick 条款，必须作为明确的预算修订处理，不能称为已经符合原条款。旧方案、旧审查不作为本文规范。

## 判断

优先处理预算限流、重复接入工作和段间准备等待。当前证据不足以认定更换寻路算法是最划算的第一步。

建议使用“近期非寻路负载估计 + 当前 tick 实时余量 + 有上限的动态预算”，不要因上一 tick 小于 50ms 就无限派发。上一 tick 的空闲不能证明这一 tick 能消化所有积压；原版搜索是不可抢占的原子调用，任何外层预算都不能保证单次调用绝不越过截止时间。

“面寻路”暂按导航网格 NavMesh 理解，尚未确认朋友所指的具体实现。NavMesh 可以独立研究宏观候选层，但直接用它生成实体详细路径会改变现行“真实原版 PathFinder 决定详细可行性”的职责边界。它不是本轮低风险优化的前提。

## 证据与不能推出的结论

原始对照见 [高并发比较报告](2026-10-13-navigation-high-concurrency-comparison-zh.md)。本次只重分析已有正式数据，没有运行新的动态预算压测。

512 并发、两次重复的中位数如下。单位 ms：

| 距离 | 原生 PathFinder 总搜索 | 全观察期导航累计计费 | 全部首条 Path 就绪 |
|---:|---:|---:|---:|
| 8 | 50.22 | 284.14 | 2034.30 |
| 18 | 113.95 | 609.75 | 3108.77 |
| 28 | 156.23 | 1054.85 | 7732.72 |

累计计费包括准备、调度、发布、运行期观察和同步回调，观察期分别约 7.91、14.25、20.80 秒。它不是“首条 Path 之前的计算”，不能用这一列除以 4ms 推导首条路径的等待，或把它与原生搜索的差额全部归为某个函数。

真实搜索调用数分别为 850.5、1105、1144，原版各为 512。首次移动后的到达 P50 仍增加 32.06%、56.95%、55.81%。因此“只放开首次搜索”不能解释或解决整个行走阶段的额外耗时。

现有逐 tick 数据没有预算额度、剩余余额、负债、可运行队列与后台依赖等待的分别计时，不能量化 4ms 限流占总等待的百分比。`pendingRequests` 也不能直接解释为“已经具备输入，只等预算”的任务数。

成功率回退必须单独处理。512 并发的两次重复中，每距离共有 1024 对输入：

| 距离 | 原版成功、我们失败的路线 | 数量 |
|---:|---|---:|
| 8 | 门洞 | 24 |
| 8 | 单墙 | 16 |
| 18 | 门洞 | 28 |
| 18 | 单墙 | 16 |
| 18 | L 形拐角 | 16 |

这些是双方配对结果，不是简单相减后的净失败数。我们在其他路线也有原版未成功的样本。重新逐 trial 检查后，上述非成功终态均为 EXHAUSTED；重分析结果的 `terminalEvidence` 保留距离、重复轮次、地形、原始 actor 下标、原版是否成功与我们的终态，`trials.terminalHistogram` 枚举每轮全部 512 个请求的终态。512 并发中，8/18/28 格各轮的所有非成功请求分别为 20/32/8，均为 EXHAUSTED。不能把延时降低当作成功率修复，也不能只凭地形名称推断碰撞或宏观候选的具体根因。

## 动态预算候选

### 计时与控制

50ms 是目标 20 TPS 的每 tick 时间窗口，不是应该尽量用满的安全额度。建议先取 45ms 为主线程派发目标截止点，留下约 5ms 余量；它仍不是硬保证。

必须测量实际工作耗时，排除等下一 tick 的休眠。上次报告的 START 至探针 END 工作时间也不能直接等同于完整服务端 MSPT。新的测量边界应覆盖高优先级 START 提交、其他订阅者和 tick 尾部；不能用晚于提交的普通 START 监听器当作完整 tick 的起点。

将近期完整 tick 工作分成已经准确计费的导航工作和其余主线程工作，避免用“包含本调度器的总 MSPT”直接作为基础负载，形成预算放大、缩小的反馈振荡。

可先验证以下控制结构，数值是试验起点：

```text
baseEstimate = max(近期非导航工作耗时的 EWMA, 近 32 tick 非导航工作的 P95)
desiredBudget = clamp(45ms - baseEstimate, 0ms, 12ms)
```

预算扩张每 tick 最多增加约 1ms；超出工作目标或负载升高时快速缩减，具体减额规则在控制器试验中确定。冷启动历史不足时从现行 4ms 起步。允许额度低于 4ms，基础工作已经很重时可为 0，不设无条件最小执行量。

每 tick 按选定额度补充时间余额，正余额上限随额度变化，不囤积几十 tick 的闲置额度；保留已经发生的负债。进入 END 后，实际派发量同时受剩余余额与本 tick 到 45ms 截止点的实时余量限制。准备、发布、回调和观察仍计费，不能通过缩小统计口径取得表面改善。

每次开始任务前再次检查时间；原子搜索超支后立即停止继续派发，并记录超支和负债。必要时按任务类型记录完整任务成本的近期高分位数，改进启动成本估计；不能只拿 PathFinder 内部耗时估计整个操作。

12ms 上限不是最优值结论。先比较固定 4/8/12ms 与动态上限 12ms，决定是否有证据继续扩大上限。

### 公平性

途中补段可根据“距离当前真实节点耗尽的剩余时间”适度提高调度紧迫性，减少已开始行走的实体停在段尾；首次路径请求仍保留等待老化和机会，避免持续补段饿死新请求。保留跨维度公平和已有玩家优先级。

若基础工作持续逼近截止点，延迟累积无法仅靠调度解决。应明确上报排队、过载和现行超时结果，不能偷偷扩大 TTL 或在截止点后强制执行所有积压。

### 验证

固定同一 jar 的算法行为、路线、实体、输入参数和计时口径，对预算模式做单变量比较。至少保持 128/256/512 并发、三距离和八类地形，增加持续补充请求，以及约 10/30/40/48ms 的可控主线程基础负载。人工负载用于验证调度器，另外保留实际服务器负载场景，不能把忙等测试当作生产性能。

记录完整 tick 工作 P95/P99/max、>50ms 次数、首条 Path P50/P95、段间等待、实际到达、吞吐、成功率、主线程分配和 GC。预算日志还应有额度、已计费时间、负债、停止原因、可运行任务数和依赖等待任务数。

至少五次独立重复或根据方差增加重复，交换运行顺序；预热与冷缓存分开。动态方案应同时证明等待降低和尖峰受控，不能只报告平均 TPS。

可增加“原版同步 findPath 原子任务也经同一预算调度”的辅助组，帮助隔离调度影响；该组会改变原版同步提交时序，必须另命名，不替换真实原版同步基线。

## 接入开销的优化顺序

| 优先级 | 已确认的代码行为或测试现象 | 候选修改 | 边界 |
|---|---|---|---|
| P0 | 固定 4ms 正余额上限；大量工作分散到后续 tick | 补齐阶段计时，再验证动态预算 | 是预算条款修订，收益未实测 |
| P1 | `prepare` 遍历全部 records，`capacity` 再扫描同一集合 | 建立 Navigation 到少量请求的索引和待收养计数 | 保留同意图复用、两个未收养上限、替换/取消清理 |
| P1 | 最后段窗口扫描 4096 单元生成候选，而最后段搜索直接传最终目标 | 区分仅保留当前性视图的末段窗口，省掉未使用候选生成和邻域候选 | 保留窗口版本、视图引用、原参数和实际详细搜索 |
| P1 | 导航 tick 与 END observe 会重复调用 window/proof 当前性检查；contains 也再次检查 | 先减少同一无变更调用区间内的重复检查，再评估版本缓存 | 不得简单缓存到 tick 结束；同 tick 修改也必须使结果失效 |
| P2 | 原生搜索次数增加；nextSegment 在当前段结束后的 settle 中启动 | 最多预取一份后续宏观数据依赖，紧迫补段获得有界优先级 | 详细 PathFinder 仍从交接时真实位置搜索 |
| P2 | 门洞、单墙、L 角存在双方配对成功率回退 | 先捕获当前候选、每次 native partial、末端和原版 stuck-stop，再定点修复 | 不扩大原参数，不伪造成功，不恢复资格过滤 |
| P3 | 短程也可能跨 section 产生多次搜索 | 独立评估段长度和短程后端选择 | 会改变现行分段策略，先做候选方案与独立验证 |

`prepare`/`capacity` 的全表扫描使 N 个不同 Navigation 集中提交时存在 O(N²) 的请求记录访问。按 Navigation 建索引后，本次每个 Navigation 只有少量记录，提交索引工作可降为近似 O(N)；这不是整个寻路算法变成 O(N)，也不证明它已是最大的墙钟热点。

末段候选扫描属于窗口准备开销，主要在 worker 上发生，不能据此声称省掉了同等主线程耗时。它的价值在于减少无用工作、对象创建和准备依赖；需要计时证实占比。

`NativeQueryProof.capture` 当前保存 region 内 chunk 身份和版本，最多 256 项；region 超出此上限时直接返回 null，不能把 null 视为有效证明。非空结果的 `current` 会逐个检查；`GroundSegmentWindow.current` 也检查持有视图。可以减少同一调用里的重复检查，或在完整 mutation/lifecycle epoch 覆盖后复用检查结果。复用评估限于真实存在且身份匹配的快照，不能以“这一 tick 已检查过”跳过后来发生的方块修改、卸载重载或发布替换。

已有 base/corridor cache：当前 [运行时源码](../../src/main/java/com/scarasol/acceleratednavigation/topology/TopologyWorkerRuntime.java#L110) 的 `completedCorridors`、`replayCompletedCorridor`、`cacheCompletedCorridor` 实现了走廊缓存，base 视图也有留存管理。原始结果的 `topologyEnd.worker` 记录 `baseCache`、`corridorCache` 与 `completedCacheHits`；重分析保留各轮 `cacheAtTrialEnd`。这是累计快照，不能将 hits 直接当成某一轮命中率。首先补请求级命中与准备时间统计，不重复增加同样的缓存。可复用不可变版本数据，但不能无条件共享实体的可变 Path、NodeEvaluator 或候选可行性结论。

预取优先只准备下段 section 的不可变拓扑数据及依赖，不提前产生详细节点。预取必须有数量/字节上限，绑定请求和段代次，失效、替换、取消、完成、超时和关闭均清理引用。若实际位置或宏观版本变化，交接重新准备当前输入。

中间段稳定/落地判断与原生真实交接仍需保持。不能仅为省时去掉稳定判断，重新引入速度 IV 的惯性折返；也不能改变最后段到达、accuracy、partial 和 EXHAUSTED 语义。

短程原版直达可以研究“在任务选择阶段明确选原生后端、仍受调度预算”的方案。它会改变现行分段策略，需要单独定案；禁止在已经选择分段后因候选失败偷偷转整条回退。不能单凭直线距离小就假设实际绕行长度小。

## 面寻路、流场与现有宏观拓扑

### NavMesh

若朋友所说的面寻路是 NavMesh，它将可导航表面组织为多边形及其连接，搜索多边形走廊，再求走廊内的具体路线。Recast 从输入三角形体素化、筛选、区域化，生成多边形导航网格；Detour 提供查询、路径走廊和直线路径接口。

在大面积连续表面上，这种表示有机会减少搜索状态。Recast 官方也提供 tiled navmesh、局部重建和流式加载；Detour 有按最大迭代次数推进的 sliced findPath。Java 生态有 Recast4j，可用于隔离原型，不必先做 JNI。

这些能力不等于“对 Minecraft 本项目已更快”。需要计入几何提取、agent 尺寸对应的网格生成、楼层和掉落连接、方块修改后的局部重建、区块卸载、版本同步与持久化成本。本项目还需保留原版门、流体、malus、能力与模组 NodeEvaluator 规则；独立 NavMesh 详细路径不是原版详细搜索的等价替代。

现行宏观层已经有 section 组件、边界连接、候选走廊及缓存，不是完全逐方块从头搜索的基线。项目 10 月 6、7 日已参考 Recast/NavMesh 的连接与紧凑表示；这段参考史只作为技术来源，不恢复旧设计的规范地位。针对已有实现可进一步借鉴成品持久化、按热点预热和分块更新，见 [冷图准备补充研究](2026-10-13-navmesh-cold-preparation-research-zh.md)。比较 NavMesh 应针对已有宏观实现，不能只与未优化的体素 A* 比较。

本项目若研究 NavMesh，建议先作为独立宏观候选原型：它只输出候选连接和版本，最终详细节点仍交给真实原版 PathFinder。即使原型通过，也需要明确的宏观架构变更，不能混入本轮接入开销优化。

比较项目包括：构建/更新时间、查询 P50/P95、驻留内存、失效后重建、候选可用率、最终原版成功率、路径长度，以及静态/动态/多层地形。地图不变时的查询速度不能代替更新成本。

### 流场

如果朋友实际指流场寻路，则是另一类方法：对共享目标或目标组建立可复用的方向/势场，多个实体利用同一场移动。其共享价值与目标、能力和环境版本的重合程度有关。

当前 512 并发测试有 512 对不同起终点，不应借换成同一目标后得到的结果证明原工作负载改善。流场可以作为同目标追击/大群体的独立研究项；用流场直接控制实体也会改变现行原版详细路径执行边界。

## 推荐实施批次

1. 先补齐完整 tick、调度排队、宏观依赖、详细搜索、发布、段间等待的计时，并单独验证动态预算；其他算法行为保持一致。
2. 分别提交请求索引、末段未使用候选精简、重复当前性检查优化，每项独立验证语义和性能。预算与这些开销削减分别报告贡献。
3. 单独验证一个后续宏观依赖预取，以及补段紧迫性调度；同时回放速度 II/IV、变化输入和完整取消/关闭生命周期。
4. 对成功率回退路线做逐次详细结果归因，再定点修复；NavMesh 与短程策略另做隔离原型。

全程沿用真实原版结果、同一参数和失败终态。任何收益百分比都必须来自实际对照，本文没有承诺动态预算会带来固定倍数加速。

## 独立方案审查

DeepSeek v4.1 Flash 对补证后的完整候选方案给出 `CONSENSUS_WITH_GATES`，必须修改项为“无”。接受 P0 计时与动态预算、P1 请求索引/末段候选精简/重复检查、P2 单份宏观依赖预取与失败归因、P3 NavMesh/短程策略隔离原型的顺序。

共识附带实测门槛：准确的完整 tick 计时，固定/动态预算单变量比较，保留真实原版同步基线，逐项报告收益，≥5 次独立重复，冷热缓存分开；补请求级缓存命中与准备统计。任何源码实施还需验证同 tick 修改、取消替换、速度 II/IV、partial 与关闭清理。本轮未修改生产代码，也未进行新的动态预算性能测试。
