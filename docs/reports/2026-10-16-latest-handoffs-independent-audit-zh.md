## 结论

两份交接保留失败、未完成状态和生产限制的做法基本诚实，主要数字能复算，但不能直接照其中的恢复步骤继续推进：性能分析器存在验收漏检和超时排除问题，缓存原型违反 FIFO 声明，待补测试自身也有错误。

快照去重有真实但局部的价值，优先考虑分层恢复中重复组件的场景。fill 映射预计算可以低优先级保留。固定弱引用槽缓存按现状应停止推进。当前证据不支持“已经全面超过原生”，也不能解除旧 RawRows 正式 FAIL 或 Boundary 的 INCONCLUSIVE。

## 发现

### 1. [P1] 缺少整个场景也会被分析器标成完整矩阵

位置：`.tmp/current-performance-reference-20261016/analyze.mjs:38`、`:48`、`:198`；`seal.ps1:15`。

`validateRun()` 只检查文件中实际存在的 trial，没有要求每台恰好包含预定的六个正式 cell，也没有检查 cell 唯一性、实际实体数与并发的一致性，以及目录版本与 trial 版本的一致性。`complete` 只要求六个 run 名称齐全，没有逐 cell 覆盖要求。seal 对汇总的检查同样只到 run 名称层。

独立反例从原第一对记录构造六份合成 run，删除每台两个 512 并发 cell。分析器退出 0，输出：

```text
ANALYZED formalRuns=6/6 rows=24 cells=8
complete=true
```

预定完整矩阵应为 36 个正式 trial、12 个版本/场景 cell。反例保存在 `missing-cell-counterexample/`。现有第一对确实包含完整六 cell，未发现其已发生场景漏算；这是后续补测与封存的门存在漏洞。

### 2. [P1] 汇总排除了超时 trial 的成功率和资源成本

位置：`.tmp/current-performance-reference-20261016/analyze.mjs:166`。

所有 metric 都先执行 `rows.filter(item => !item.timedOut)`，包括成功率、物理到达率、CPU、分配和 tick 指标。虽然原始行和 `timedOutCount` 保留，版本对照的率、范围和成本仍会只使用未超时子集，违背“失败不从分母剔除”的协议意图。

独立合成反例让三台加速 JVM 中一台在 8×512 场景全部超时、零成功。分析器仍输出 `complete=true`，该 cell 为 `sampleCount=3`、`timedOutCount=1`，但成功率和 CPU 的贡献数均只有 2，成功率最小值也漏掉零成功运行。该例的三台成功率为 `[0, 0.9609375, 0.9609375]`，中位数恰好不变，不能据此忽略缺失的失败和资源成本。

现有第一对没有超时，本问题尚未改变其数值。应保留超时作为功能结果，并报告其截至截止时刻的成本；完成时延可以单列为未完成或条件统计，不能统一把整条试验丢出所有指标。

### 3. [P2] 性能交接把观测窗口长度标成全批到达时间

位置：性能交接表第 27 行；探针 `PerformanceComparisonProbe.java:384`、`:449`。

表内的 `2099.98 / 2239.44ms` 等值来自 `batchFinishNanos`。探针在所有实体进入终态后继续观察 10 tick，再结束窗口，因此该值不是到达时间；部分实体 EXHAUSTED 时它仍有值。

原始记录复算示例：

| 场景 | 后端 | 真实物理到达 | 最后已到达实体时延 ms | 表中窗口长度 ms |
| --- | --- | ---: | ---: | ---: |
| 8×1 | 原生 | 1/1 | 1501.2156 | 2099.9812 |
| 8×1 | 加速 | 1/1 | 1644.6944 | 2239.4381 |
| 8×32 | 加速 | 30/32 | 2562.2281 | 3108.6964 |
| 28×512 | 加速 | 504/512 | 14216.1805 | 14765.0384 |

存在未到达实体时，“全批到达时间”应为空；最后成功者时延必须明确是条件统计。窗口长度可以继续用于说明成本累计区间。

### 4. [P2] 固定槽缓存遇到弱引用空洞后不再按 FIFO 淘汰

位置：临时候选 `BaseClusterTopology.java:1199`、`:1202`、`:1203`。

候选选择任意最先找到的空槽后，总把 `cursor` 改成该槽下一位，破坏了尚存条目的插入时间顺序。

可确定复现：先插入 64 个 source，手动清除第 32 槽的 WeakReference 以模拟合法的引用清除状态，再插入两个新 source。第一次复用第 32 槽，第二次淘汰第 33 个 source，却保留最早的第 0 个。结果见 `fifo-counterexample.json`。

这不直接产生错误几何结果，但违背方案明确保留的最老条目淘汰语义；交接“FIFO 通过”覆盖不足。旧测试没有断言这一交错状态下的最老淘汰。候选每次 row 查找还要线性访问最多 64 个弱引用，现有 JMH 未显示稳定收益，不建议为它继续增加维护复杂度。

### 5. [P2] 尚未运行的缓存补测含错误 oracle

位置：`.tmp/intermediate-reuse-light-p1-cache-20261016/harness/RawRowsIdentityCacheChecks.java:136`。

该测试从 `Fixtures.flat()` 出发，只把 `(4,4,4)` 一个格子的 flags 清零，却要求整条 row 等于 0。其它 15 个格子仍有 VOLUME_OPEN，正确打包值为 `0xFFEF`，即 `65519`。

本轮编译并运行交接所指的最终测试，确实在这里报 `stale weak slot returned an old row`。另以逐格 flags 独立打包得到期望值 `65519`，候选实际返回值也为 `65519`。这是测试错误，不能据该失败判定缓存返回了旧行。原交接明确说该补测尚未运行，这一状态说明是准确的。

### 6. [P2] P0 的收益范围被人工极端输入放大，验证门也未对准修改层

位置：P0 harness `ComponentSnapshotDedupChecks.java`；生产 `TopologyWorkerRuntime.java:7609`；轻量方案 P0 最小验证。

普通 TopologyGraph 已通过 `bindingsByCluster[componentId]` 复用同一组件端点，因此人工构造 1024 个不同 endpoint 指向一个组件所获得的降幅，不能视为普通路径的典型收益。

本轮使用真实 worker 分别跑普通与分层路径：

| 路线 | endpoint 映射项 | 唯一组件身份 | 基线快照实例 | P0 快照实例 |
| --- | ---: | ---: | ---: | ---: |
| 普通跨 section | 4 | 4 | 4 | 4 |
| 分层、3 个 witness 段 | 9 | 5 | 9 | 5 |

逐 endpoint 的 4096 格成员哈希、映射规模和 cost 均一致。P0 的组件 key 与只读位图设计成立，并有真实分层重复可削减；普通路径则新增第二张 map 的查找及分配。需要测实际重复率与成本份额，才能决定全路径启用是否值得。

另外，2380 语料原本针对 Base 构图和 scratch 数组；P0 修改的是宏观结果提取，不修改 Base 构图。仅重跑这套图哈希不会覆盖 P0 的去重逻辑。它应使用真实宏观结果、成员位图、分层拼接、缓存重物化、取消及上限作为主要验证门，而不是机械复制 B/C 的指标。

## 方案价值与后续顺序

| 方向 | 判断 | 理由 |
| --- | --- | --- |
| 同包原生 bypass 对照 | 保留并修正测量工具 | 负载入口、世界和 Jar 对齐，有助于比较真实体验；只有一对，尚不具备三对范本资格 |
| ComponentSnapshot 去重 | 保留为有条件候选 | 分层路线存在真实重复，成员语义一致；须量化普通路径额外开销与实际重复率 |
| RawRows 固定弱槽缓存 | 按现状淘汰 | FIFO 不成立；三轮均值 single/complex 约慢 3.67%/3.62%，不能断言稳定回退，但没有支持接入的收益证据 |
| fill 映射预计算 | 低优先级保留 | 扩充差分零差异；三轮均值 single/complex 约快 1.20%/5.88%，波动较大，无端到端收益结论 |

三轮 JMH 均值与交接一致。本轮只复算已有 JMH，没有重跑性能或证明其随机顺序、null-control 全部可追溯。fill 当前实现主要是 27 项 source lookup、循环不变量外提和位运算替换，不是方案所列完整几何预计算及新无门快路径都已完成。

优先顺序应是：修正性能分析完整性和超时统计，明确窗口与到达口径；再取得可信的当前版本对照，针对首次 Path 和重复详细搜索确定成本份额；最后才决定是否推进 P0 或 fill。现有一对中，8/28 格单实体的首 Path 分别从原生约 `0.42/0.47ms` 到加速约 `95.00/94.80ms`，而 28×512 的详细搜索从 512 次到 1116 次，分配从约 538MiB 到 1018MiB。这些比继续猜测弱缓存实现更值得做定向诊断，但不能仅凭现有记录认定具体根因。

当前对照使用坐标 `moveTo`、accuracy=1，而共享 section 分支要求 accuracy=0；因此这套范本也不能代替共享分支或长距离分层路线的性能验收。
